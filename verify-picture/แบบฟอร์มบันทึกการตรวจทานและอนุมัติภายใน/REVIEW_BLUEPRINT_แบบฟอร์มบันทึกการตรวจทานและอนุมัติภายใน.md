# Review Blueprint — F-TMP-006 แบบฟอร์มบันทึกการตรวจทานและอนุมัติภายใน

วันที่จัดทำแผน: 23 พฤศจิกายน 2026  
วัตถุประสงค์: ตรวจเก็บตก logic และการทำงานของระบบ production โดยยึด FRD-F-TMP-006 v1.0 เป็น baseline และแยกผลที่พิสูจน์แล้วออกจากข้อสันนิษฐาน

> เอกสารนี้เป็น “แผนตรวจ” ไม่ใช่ผลรับรอง ไม่มีรายการใดถือว่าผ่านจนกว่าผู้ตรวจจะทำจริงและแนบหลักฐาน

## 1. ข้อสรุปสำหรับผู้ตรวจ

- ไม่ต้องวนตรวจ layout ทุกหน้าซ้ำ ให้ทำ UI sanity เฉพาะสิ่งที่กระทบการทำงาน เช่น ปุ่มผิดสิทธิ์ ช่องถูก disable ผิดสถานะ ข้อความเตือนไม่ขึ้น และ PDF ข้อมูลตกหล่น
- ให้ยึด FRD หมวด `03_LOGIC`, `05_RULES`, `06_TESTS`, `07_LOCKED_DECISIONS` เป็นหลัก แต่ต้องตรวจ governance gap ก่อน เพราะ FRD ระบุ AI-DEFAULT 12 ข้อและ OQ ค้าง ขณะที่ระบบขึ้น production แล้ว
- รอบนี้ควรเน้น happy path 1 รอบเพื่อสร้างฐานข้อมูล จากนั้นเล่น flow เสี่ยง: ตีกลับแล้วส่งใหม่, เปลี่ยน DOA ระหว่างรอ, กดซ้ำ/กดชนกัน, ลองข้ามสิทธิ์, ยกเลิก, PDF snapshot, notification และ audit
- ห้ามใช้ข้อมูลจริงที่เป็นความลับเพื่อทดลอง destructive flow บน production ควรใช้บัญชี/ข้อมูลทดสอบที่ PM อนุมัติ และประสานผู้รับ notification ก่อนยิง event

## 3. บัญชีและข้อมูลทดสอบที่ต้องเตรียม

| Persona | ใช้ทดสอบ |
|---|---|
| Owner A | สร้าง แก้ ส่ง ตีกลับ ส่งใหม่ ยกเลิก |
| Owner B | พยายามดู/แก้ร่างของ Owner A |
| Approver step 1 | ตรวจสอบ/ไม่ผ่านการตรวจสอบ |
| Approver step 2 | อนุมัติ/รับทราบ/ไม่อนุมัติ |
| Chain member แต่ยังไม่ถึงขั้น | ทดสอบห้ามตัดสินก่อนลำดับ |
| Outsider | ทดสอบไม่เห็นเอกสารและเดา URL ไม่ได้ |
| Business Development admin | เห็นทั้งหมดและยกเลิกได้ แต่แก้/อนุมัติแทนไม่ได้ |
| Tenant B (ถ้ามี environment รองรับ) | ทดสอบ RLS และเลขเอกสารข้าม tenant |

ชุดข้อมูลขั้นต่ำ:

- D1: 1 แถว สถานะปิด ข้อมูลครบ
- D2: 3 แถว มีเปิด/กำลังดำเนินการ/ปิด และแถวปิดไม่มีผู้รับผิดชอบกับข้อคิดเห็น
- D3: 15–24 แถว เพื่อทดสอบ PDF ข้ามหน้า
- D4: แถวนอกระบบ 1 แถว และไฟล์แนบชื่อไทย/ชื่อยาว/ชนิดที่อนุญาต
- D5: DOA 2 ขั้น; ถ้าทำได้เพิ่มชุด 1 ขั้นและ 6 ขั้นใน environment ที่ปลอดภัย

## 4. ลำดับการตรวจที่แนะนำ

### P0 — ต้องทำก่อน เพราะถ้าผิดมีผลต่ออำนาจอนุมัติหรือข้อมูล

#### RV-01 สร้างร่างและเลขเอกสาร

1. Owner A สร้าง D1 และบันทึกครั้งแรก
2. จดเลข IRV, ผู้จัดทำ/ตำแหน่ง/ฝ่าย และข้อมูลหัวบริษัท
3. แก้ไขและบันทึกซ้ำหลายครั้ง
4. เปิดใหม่จากรายการ

คาดหวัง: ออกเลขครั้งแรกเพียงครั้งเดียว; เลขไม่เปลี่ยนเมื่อแก้; snapshot ผู้จัดทำและหัวบริษัทไม่ถูกเปลี่ยนย้อนหลัง; audit มี create/update; ไม่มีเลขซ้ำ

อ้างอิง: FN-03, BR-09, API-03/04, DEC-11

#### RV-02 Validation หลักและวันที่

ลองทีละกรณี: ไม่มีแถว, เว้น required ทุกช่อง, วันที่ตรวจทานอนาคต, วันที่พิจารณาอนาคต, ไม่เลือกสถานะสุดท้าย, สถานะที่ต้องมีวันที่มีผลแต่ไม่กรอก, สถานะที่ไม่ต้องมีวันที่แต่พยายามคงค่าเดิมไว้

คาดหวัง: บล็อกตาม VR-01..04; วันที่อนาคตไม่ผ่าน; เมื่อเปลี่ยนเป็น “อยู่ระหว่างแก้ไข/ไม่อนุมัติ” วันที่มีผลต้องถูกล้างทั้งหน้าจอและข้อมูลหลังเปิดใหม่

อ้างอิง: FN-01, BR-04, BR-15, VR-01..04, EC-01

#### RV-03 Warning ต้องไม่กลายเป็น Block

1. ใช้ D2 เลือก “อนุมัติครบถ้วน” ทั้งที่ยังมีรายการเปิด
2. ทำแถวสถานะปิดโดยเว้นทั้งผู้รับผิดชอบและข้อคิดเห็น
3. บันทึกและส่งอนุมัติ

คาดหวัง: แสดงคำเตือนและจำนวนรายการถูกต้อง แต่บันทึก/ส่งได้; warning ยังอยู่เมื่อ reload; server เป็นผู้คำนวณ ไม่ใช่หลอกได้ด้วยการแก้หน้าเว็บ

อ้างอิง: FN-02, BR-03, BR-05, AC-03/06

#### RV-04 Resolve DOA และห้ามอนุมัติตัวเอง

1. เปิด modal ส่งอนุมัติและเทียบจำนวน slot กับ DOA กลาง
2. ตรวจค่า role-line-manager และ role-gm ที่ resolve จริง
3. เว้น assignee, เลือก Owner A เป็นผู้พิจารณา และเลือกคนไม่ครบ
4. ส่งเมื่อข้อมูลครบ

คาดหวัง: จำนวน/บทบาทตรง DOA; owner ไม่อยู่ในตัวเลือกและ backend ปฏิเสธ SELF_APPROVAL; ส่งได้เฉพาะ draft; chain ถูก snapshot

อ้างอิง: FN-04, BR-DOA-01/02/04, VR-05, AC-08

#### RV-05 ลำดับอนุมัติและการข้ามสิทธิ์

1. หลังส่ง ให้ approver ขั้น 2 และ chain member ที่ไม่ใช่ขั้นปัจจุบันเปิดใบ
2. ตรวจว่าเห็นข้อมูลแต่ไม่มีปุ่มตัดสิน
3. ถ้าทำ API test ได้ ให้ยิง decide โดยบัญชีดังกล่าว
4. ให้ขั้น 1 อนุมัติ แล้วจึงให้ขั้น 2 อนุมัติ

คาดหวัง: ข้ามลำดับไม่ได้และสถานะไม่เปลี่ยน; ขั้น 1 สร้างแถว source=doa; ขั้นสุดท้ายทำให้ approved; owner/admin อนุมัติแทนไม่ได้

อ้างอิง: FN-05, BR-DOA-04, TC-D03, Permission Matrix

#### RV-06 ตีกลับ แก้ และส่งใหม่

1. ขั้นปัจจุบันกด reject โดยไม่ใส่เหตุผล
2. ใส่เหตุผลแล้วตีกลับ
3. ตรวจสถานะ, เลขเอกสาร, banner เหตุผล, audit และแถว source=doa
4. Owner แก้ข้อมูลแล้วส่งใหม่
5. เทียบ chain รอบใหม่กับ DOA ปัจจุบัน และทำจนอนุมัติ

คาดหวัง: ไม่ใส่เหตุผลไม่ได้; กลับ draft; เลขเดิม; ประวัติเดิม append-only; แถว DOA รอบก่อนยังอยู่และแก้/ลบไม่ได้; resolve chain ใหม่เมื่อส่งรอบใหม่

อ้างอิง: FN-06, BR-DOA-03, EC-08, DEC-09/16

#### RV-07 Freeze chain เมื่อ DOA เปลี่ยน

1. ส่งใบ A ด้วย DOA ชุดเดิม
2. ให้ผู้ดูแลที่ได้รับอนุญาตเปลี่ยน DOA กลาง
3. ตรวจใบ A และสร้าง/ส่งใบ B

คาดหวัง: ใบ A ใช้ chain เดิมจนจบ; ใบ B ใช้ chain ใหม่; PDF และประวัติของแต่ละใบตรง snapshot ของตน

อ้างอิง: BR-DOA-02, EC-05

#### RV-08 สิทธิ์ดู/แก้และการไม่เปิดเผยข้อมูล

ทดสอบ Owner B, outsider, chain member, admin ด้วยรายการ ค้นหา direct URL PDF CSV และไฟล์แนบ

คาดหวัง: ร่างเห็นเฉพาะ owner/admin; ผู้อนุมัติเห็นหลังส่ง; คนไม่มีสิทธิ์ได้ 404 ไม่ใช่ 403 ที่บอกว่าเอกสารมีอยู่; admin เห็นและยกเลิกได้ แต่แก้ร่าง/ตัดสินแทนไม่ได้; CSV/PDF/attachment ใช้สิทธิ์เดียวกัน

อ้างอิง: FN-10, BR-13, API-02/09/10/11, TC-D01..07

#### RV-09 Tenant isolation

ถ้ามีบัญชีคนละ tenant ให้ลองค้นหา เปิด UUID เดา ดาวน์โหลด PDF/attachment และ export CSV ของอีก tenant

คาดหวัง: ไม่พบข้อมูลทุกช่องทาง; เลข unique ภายใน tenant ตาม contract; ไม่มีชื่อหรือ metadata รั่ว

อ้างอิง: §0.7, API common, DB tenant_id/RLS

#### RV-10 กดซ้ำ กดชนกัน และข้อมูลไม่ซ้ำ

1. เปิดใบเดียวกันสอง tab
2. tab A แก้และบันทึก; tab B บันทึก version เก่า
3. double-click ส่ง/อนุมัติ/ยกเลิก หรือส่ง request ซ้ำด้วย Idempotency-Key เดิม
4. ให้สอง session พยายามตัดสินขั้นเดียวกันพร้อมกัน

คาดหวัง: version เก่าได้ STALE; event/แถว source=doa/audit/เลขเอกสารไม่เกิดซ้ำ; มีผู้ชนะเพียงหนึ่ง request; สถานะสุดท้ายสอดคล้อง

อ้างอิง: API §2.3, EC-06

### P1 — ต้องทำเพื่อรับรอง flow ธุรกิจครบ

#### RV-11 ยกเลิกทุกเงื่อนไข

ทดสอบ owner ยกเลิก draft/pending, admin ยกเลิก draft/pending, outsider ยกเลิก, เหตุผลว่าง, และพยายามยกเลิก approved/cancelled

คาดหวัง: เฉพาะ owner/admin และเฉพาะ draft/pending; เหตุผลบังคับ; pending step ถูก skipped; approved ยกเลิกไม่ได้; audit เก็บ actor/reason/time

อ้างอิง: FN-07, BR-10, VR-06, API-08

#### RV-12 Notification

1. ยกเลิกใบ pending
2. อนุมัติใบที่ยังมี open_items
3. อนุมัติใบที่ไม่มี open_items
4. ตรวจผู้รับ จำนวนครั้ง deep link และข้อความ

คาดหวัง: irv_cancelled ส่งให้ผู้พิจารณาขั้นปัจจุบัน; irv_approved_open_items ส่ง owner เฉพาะเมื่อมีรายการค้าง; DOA notification ไม่ถูกยิงซ้ำโดย feature

อ้างอิง: FN-09, XT-01

#### RV-13 PDF และ approved snapshot

สร้าง PDF ใน draft, pending, approved, cancelled และ D3/DOA หลายขั้น แล้วเทียบข้อมูลกับหน้าจอ

คาดหวัง: ทุกสถานะ 2 หน้า; หน้า N/2; หัวตารางซ้ำ; อย่างน้อย 10 แถวตรวจทานและ 3 แถวอนุมัติ; 15–24 แถวไม่หาย; ตารางลงชื่อ = ผู้จัดทำ + 1 ต่อ DOA step; วันที่ พ.ศ.; approved เก็บ approved_final และไม่เปลี่ยนย้อนหลังแม้ master ชื่อ/โลโก้/พนักงาน/DOA เปลี่ยน

อ้างอิง: FN-08, BR-11/12, AC-11/14, XT-02

#### RV-14 แถวอนุมัติ manual เทียบกับ DOA

1. เพิ่ม manual row แบบไม่ครบและแบบครบ
2. หลังส่ง/ตีกลับ/อนุมัติ ตรวจ manual row กับ source=doa
3. พยายามแก้หรือลบ source=doa ผ่าน UI และ API

คาดหวัง: manual ต้องครบ 4 ช่อง; source=doa สร้างจาก server เท่านั้นและแก้/ลบไม่ได้; ลำดับไม่ชนหรือทับกัน; PDF แสดงทั้งสองชนิดถูกต้อง

อ้างอิง: FN-01/05/06, BR-06, VR-02, TC-D07

#### RV-15 Config-driven behavior

ใน environment ที่เปลี่ยน config ได้อย่างปลอดภัย ให้เพิ่ม/เปลี่ยน review_statuses หรือ final_statuses แล้วเปิด session ใหม่

คาดหวัง: UI, validation, open_items, warning และ PDF ใช้ config เดียวกัน; ไม่มีค่า เปิด/กำลังดำเนินการ/ปิด hardcode จนคำนวณผิด; ค่าที่ถูกถอดจาก config เดิมต้องมี migration/การแสดงผลที่ไม่ทำเอกสารเก่าเสีย

อ้างอิง: FN-01/02, BR-01, DEC-04

#### RV-16 CSV ตามตัวกรองและสิทธิ์

กรอง status/final_status/dept/mine_to_act แล้ว export ด้วย owner, approver และ admin

คาดหวัง: จำนวนและรายการตรงหน้าจอ/สิทธิ์; ไม่ export ใบที่มองไม่เห็น; encoding ภาษาไทยถูก; ไม่มี field ภายในหรือ PII เกินความจำเป็น

อ้างอิง: API-10, AC-13

#### RV-17 Attachment lifecycle

แนบ ดาวน์โหลด ลบไฟล์ก่อนส่ง แล้วทดสอบหลัง pending/approved/cancelled ด้วยแต่ละ persona

คาดหวัง: สิทธิ์ตรงกับเอกสาร; ไม่มี orphan attachment; approved ไม่ถูกแก้ attachment หากนโยบายถือเป็นส่วนของเอกสาร; ชนิด/ขนาดไฟล์ไม่ปลอดภัยถูกปฏิเสธตาม Document Center

อ้างอิง: API-11, Document Center dependency

#### RV-18 Audit และการแก้ย้อนหลัง

หลังครบ flow ตรวจ create/update/submit/approve/reject/resubmit/cancel และ actor/time/note

คาดหวัง: append-only; ลำดับเวลาและ actor ถูก; ไม่มี update/delete audit; การแก้ข้อมูลก่อน/หลังเหตุการณ์ตามสิทธิ์; approved ล็อกแก้ไขทุกช่อง

อ้างอิง: §0.7, DB internal_review_audit, BR-10

## 5. Business-sense checks ที่ FRD ยังตอบไม่พอ

รายการต่อไปนี้ไม่ควรถูกตัดสินเป็น bug ทันที ต้องให้ PM/BA ตอบก่อน แต่ควรยกเป็นความเสี่ยง:

1. เอกสารไม่ผูกโครงการหรือเอกสารต้นทาง ผู้ตรวจจะตาม trace ว่าตรวจเรื่องใดได้เพียงพอจริงหรือไม่
2. “อนุมัติครบถ้วน” ทั้งที่ข้อแก้ไขยังเปิดเป็นเพียง warning อาจไม่สอดคล้อง control ขององค์กร แม้ตรง FRD
3. admin ยกเลิก pending ได้ แต่ FRD ไม่ระบุว่าต้องแจ้ง owner ด้วยหรือไม่ ปัจจุบัน event ระบุเฉพาะผู้พิจารณาขั้นปัจจุบัน
4. การแก้/ลบ attachment หลัง approved ไม่ถูกกำหนดชัด หากไฟล์แนบเป็นหลักฐานควร immutable หรือ versioned
5. การเปลี่ยน config แล้วเอกสารเก่ามีสถานะที่ไม่อยู่ใน config ใหม่ ไม่มี migration/compatibility rule
6. ผู้อนุมัติถูกลาออก/ปิดบัญชีระหว่าง pending ไม่มี delegation/reassign/SLA/escalation rule ใน FRD
7. Retention ระบุเพียง “ตาม Policy Center” แต่ไม่กำหนดระยะเวลา การลบ และ legal hold
8. ไม่มี dashboard ข้ามใบตาม scope จึงต้องยืนยันว่า CSV เพียงพอต่อการติดตามข้อแก้ไขค้างจริง

## 6. วิธีบันทึกผลต่อเคส

ใช้รูปแบบเดียวกันทุกเคส:

| ช่อง | สิ่งที่ต้องจด |
|---|---|
| Test ID | RV-xx |
| Build / เวลา | production build และเวลา Asia/Bangkok |
| Persona / ข้อมูล | บัญชีบทบาทและเลข IRV; หลีกเลี่ยงรหัสผ่าน/PII |
| Steps | ขั้นที่ทำจริงแบบทำซ้ำได้ |
| Expected | อ้าง FRD/มติ |
| Actual | ข้อความ/สถานะ/เลขที่ที่เห็นจริง |
| Evidence | screenshot ก่อน-หลัง, PDF/CSV, notification, request id ถ้ามี |
| Result | Pass / Fail / Blocked / Not run |
| Severity | Critical / High / Medium / Low |

เกณฑ์ severity:

- Critical: ข้ามสิทธิ์/ข้ามสายอนุมัติ, tenant data leak, ข้อมูลเสีย/หาย, อนุมัติซ้ำหรือผิดคน
- High: เลขเอกสารซ้ำ, สถานะ/ผลอนุมัติ/PDF หลักฐานผิด, approved ถูกแก้, notification ทำให้ผู้รับผิดคนดำเนินการ
- Medium: ผิด FRD แต่มีทางเลี่ยง, audit/CSV/attachment ผิดบางส่วน
- Low: ข้อความ/ตำแหน่ง/ภาพที่ไม่กระทบการตัดสินใจ

## 7. เกณฑ์ปิด review

- Gate 0 มีคำตอบหรือระบุข้อค้างและผู้รับผิดชอบชัดเจน
- P0 ทุกเคสถูก run และไม่มี Critical/High ค้าง
- P1 ถูก run ครบ หรือระบุข้อที่ตรวจไม่ได้พร้อมเหตุผล/ความเสี่ยง
- ทุกรายการ Fail ทำซ้ำได้ มี expected/actual/evidence และผูก FRD
- แยก “ผิด FRD”, “FRD ยังไม่ชัด”, และ “ข้อเสนอปรับ control” ออกจากกัน
- รายงานสุดท้ายต้องบอกทั้งสิ่งที่ตรวจและสิ่งที่ไม่ได้ตรวจ ห้ามสรุปผ่านจากคำบอกเดิมของ tester
