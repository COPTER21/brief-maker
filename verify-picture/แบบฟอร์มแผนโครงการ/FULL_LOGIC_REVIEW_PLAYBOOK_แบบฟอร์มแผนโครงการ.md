# Full Logic Review Playbook — แบบฟอร์มแผนโครงการ (F-TMP-004)

วันที่จัดทำ: 25 พฤศจิกายน 2569  
วัตถุประสงค์: ใช้ตรวจระบบจริงหลังขึ้น Production โดยเน้น Business Logic, Workflow, Permission, Data Integrity และ Integration ตาม FRD ไม่ใช่ตรวจความสวยงามของ Layout

> เอกสารนี้เป็น “แผนตรวจ” ยังไม่ใช่ผลรับรอง ระบบจะถือว่าผ่านได้ต่อเมื่อผู้ตรวจทำเคสจริงและมีหลักฐาน

## 1. ข้อสรุปจากการอ่าน Context

ควรอิง FRD เป็นฐานหลักตามที่ PM/BA กำหนด โดยใช้ลำดับอ้างอิงดังนี้:

1. `05_RULES` — กฎธุรกิจ, validation, state, permission และ edge case
2. `03_LOGIC` — การคำนวณและผลข้างเคียงของแต่ละ action
3. `06_TESTS` — Acceptance Criteria และ deny cases
4. `02_API` / `04_DB` — ใช้ตรวจความถูกต้องที่มองจากหน้าจออย่างเดียวไม่ได้
5. `07_LOCKED_DECISIONS` — ใช้ตรวจว่าระบบทำตามมติเดิม แต่ไม่ควรเหมารวมว่ามตินั้นถูกต้องทางธุรกิจ

ไม่ควรเริ่มจากไล่กดทุกปุ่มแบบสุ่ม เพราะจะได้ coverage เยอะแต่พลาดความเสี่ยงหลัก ควรสร้างเอกสารหนึ่งใบแล้วพาเอกสารนั้นผ่านวงจรชีวิตจริง จากนั้นจึงแตก branch ไม่อนุมัติ, ยกเลิก, สิทธิ์ผิดคน, ข้อมูลชนกัน และ integration

### จุดที่ต้องระวังก่อนรับรอง

- FRD ระบุว่ามีมติ `AI-DEFAULT` 14 ข้อ และ OQ-02 ยังรอลูกค้ายืนยัน จึงตรวจได้เพียงว่า “ระบบตรง FRD” แต่ยังรับรองไม่ได้ว่า “FRD ตรงธุรกิจ” จน PM/BA ยืนยัน
- OQ-03 ระบุ role admin และ `role-line-manager` ยังมีประเด็นกับ DOA master แต่ feature ใช้ role เหล่านี้จริง
- OQ-07 ยังไม่ตัดสินว่าผู้รับผิดชอบหลักที่ไม่ใช่ผู้จัดทำควรเห็นใบหรือไม่ ปัจจุบัน FRD ให้แก้สถานะกิจกรรมได้ แต่ไม่ให้เห็นใบใน permission matrix ซึ่งเป็นความขัดแย้งเชิงใช้งานที่ต้องพิสูจน์ในระบบจริง
- Logic และ DB ยังมีคำว่า `TODO: DOA engine` ต้องยืนยันจากระบบจริงว่า wire แล้ว ไม่ใช่ใช้ approval จำลองหรือ hardcode
- FRD บอกว่าไฟล์ `approved_final` ไม่ re-render หลังแก้สถานะกิจกรรม แต่ PDF ปัจจุบันแสดงสถานะล่าสุด ต้องแยกตรวจ “ไฟล์อนุมัติฉบับเก็บถาวร” กับ “PDF ที่กดดูปัจจุบัน” ว่าตั้งใจให้ต่างกันจริง
- ข้อความยาวส่วนที่ 2–3 อาจทำ PDF เกิน 2 หน้า (OQ-05) ทั้งที่ AC-15 คาด 2 หน้า ต้องให้ PM/BA ชี้เกณฑ์ตัดสิน
- ข้อมูล FRD ระบุสถานะ `Ready for Dev` หลังปิด OQ-03/04/06 แต่ context ที่ได้รับยังแสดง OQ เหล่านี้ค้างอยู่ ควรขอหลักฐาน decision ล่าสุดก่อน sign-off

## 2. ขอบเขตที่ควรตรวจ

### ต้องตรวจรอบนี้

- สร้างและแก้ร่าง
- สูตรวันที่, จำนวนวัน และยอดงบ
- validation ทั้งแบบบล็อกและแบบเตือน
- การออกเลข PJP และการไม่ออกเลขซ้ำ
- สายอนุมัติแบบ dynamic, ลำดับคนพิจารณา และการ freeze สาย
- อนุมัติ, ไม่อนุมัติ, ส่งใหม่ และยกเลิก
- สิทธิ์ดู/แก้/ตัดสิน/ยกเลิก/อัปเดตสถานะทุก persona
- งบที่อนุมัติโดยผู้อนุมัติขั้นสุดท้าย
- การล็อกข้อมูลหลังอนุมัติและการแก้ได้เฉพาะสถานะกิจกรรม
- audit trail, notification, PDF, CSV และไฟล์แนบ
- concurrent update, กดซ้ำ, refresh และ error recovery
- การแยก tenant และการไม่เปิดเผยใบที่ไม่มีสิทธิ์

### ไม่ควรเสียเวลาตรวจซ้ำเป็นหลัก

- ระยะห่าง, alignment, สี, responsive และ layout ทั่วไปที่ทีม UI รับรองแล้ว
- pixel-perfect ของ prototype เทียบ production ยกเว้น UI ทำให้ผู้ใช้เข้าใจ logic ผิด เช่น ปุ่มผิด role, สถานะผิด หรือยอดผิด

## 3. เงื่อนไขก่อนเริ่มบน Production

- ขอ test tenant หรือชุดข้อมูลที่ PM อนุญาตให้สร้าง/อนุมัติ/ยกเลิกได้ ห้ามใช้เอกสารธุรกิจจริงทดลอง branch
- เตรียมบัญชีอย่างน้อย 6 แบบ: ผู้จัดทำ, ผู้ตรวจสอบขั้น 1, ผู้อนุมัติขั้นสุดท้าย, ผู้รับผิดชอบหลักที่ไม่ใช่ผู้จัดทำ, admin ฝ่ายพัฒนาโครงการ และคนนอกสาย
- ตั้งชื่อข้อมูลทดสอบด้วย prefix เดียวกัน เช่น `RVW-20261125-...` เพื่อค้นหาและแยกจากข้อมูลจริง
- ตกลงกับทีม Notification ว่าจะใช้ inbox ทดสอบหรือผู้รับจริง เพราะบางเคสยิง event จริง
- ขอผู้มีสิทธิ์ดู audit/API/log ช่วยยืนยันผลที่หน้าจอพิสูจน์ไม่ได้ เช่น idempotency, event ถูกยิงครั้งเดียว, RLS และ approved_final
- บันทึก build/version, tenant, user, เวลาเริ่ม และเลข PJP ของทุกใบ

## 4. ชุดข้อมูลหลัก

### DS-A — Happy path

- วันที่โครงการ 2–31 มกราคม 2570 → ต้องได้ 30 วัน
- KPI 1 รายการ
- กิจกรรม A: 2–11 มกราคม → 10 วัน, อยู่ในช่วง
- กิจกรรม B: 20–31 มกราคม → 12 วัน, อยู่ในช่วง
- งบ 50,000.25 + 30,000.50 + 0.00 → รวม 80,000.75
- ความเสี่ยง 1 รายการ
- ผู้จัดทำ, ผู้รับผิดชอบหลัก และผู้อนุมัติเป็นคนละคน

### DS-B — Warning path

- กิจกรรมเริ่มก่อนหรือจบหลังช่วงโครงการ
- ผู้อนุมัติกรอกงบมากกว่างบที่ขออย่างน้อย 1 รายการ
- Expected: มีคำเตือน แต่ยังบันทึก/ส่ง/อนุมัติได้

### DS-C — Reject/resubmit

- ส่งอนุมัติ → ขั้น 1 ไม่ผ่านพร้อมเหตุผล → กลับร่าง → แก้ข้อมูล → ส่งใหม่
- Expected: เลข PJP เดิม, งบอนุมัติเดิมถูกล้าง, resolve สายใหม่, ประวัติเดิมยังอยู่

### DS-D — Long/extreme

- KPI 4, กิจกรรม 12, งบ 8, ความเสี่ยง 6
- ข้อความส่วน 2–3 ยาวหลายย่อหน้าและมีภาษาไทย/อังกฤษ/ตัวเลข
- DOA 6 ขั้นถ้าระบบกลางรองรับ
- Expected ตาม FRD: ตาราง dynamic, PDF dense และเกณฑ์จำนวนหน้าต้องให้ PM/BA ยืนยันกรณีข้อความยาว

## 5. วิธีรันที่แนะนำ

ใช้ 4 journey ก่อน แล้วค่อยยิง negative cases:

1. Journey A: สร้าง → บันทึกร่าง → แก้ → ส่ง → อนุมัติครบทุกขั้น → อัปเดตสถานะกิจกรรม
2. Journey B: สร้าง → ส่ง → ไม่ผ่าน → แก้ → ส่งใหม่ → อนุมัติ
3. Journey C: สร้าง → ยกเลิกตอนร่าง และสร้างอีกใบ → ส่ง → ยกเลิกตอน pending
4. Journey D: ใช้บัญชีผิดสิทธิ์ลองเปิด URL ตรง, เรียก action และดูรายการ

ทุก action ให้ตรวจ 5 ชั้นเสมอ: สิ่งที่กด → ข้อความ/สถานะบนจอ → เปิดใหม่แล้วยังอยู่ → audit ถูกคน/เวลา → side effect เช่น PDF/notification/CSV ถูกต้อง

## 7. Business Sense Review — คำถามที่ต้องให้ PM/BA ตอบ

คำถามเหล่านี้ไม่ควรตัดสินแทนด้วยผลเทส เพราะเป็นนโยบายธุรกิจ:

1. ผู้รับผิดชอบหลักที่ไม่ใช่ผู้จัดทำ “ต้องเห็นใบ” หรือไม่ หากต้องอัปเดตสถานะกิจกรรม เขาจะเข้าถึงจากที่ใด
2. เมื่อกิจกรรมนอกช่วงโครงการ เหตุใดจึงอนุญาตให้ส่ง/อนุมัติได้ ควรเป็น warning หรือ block ในธุรกิจจริง
3. งบอนุมัติเกินงบที่ขอควรทำได้จริงหรือไม่ ใครรับผิดชอบ และต้องมีเหตุผล/วงเงิน/DOA เพิ่มหรือไม่
4. งบที่อนุมัติเป็น 0 และค่าว่างหมายถึงคนละอย่างหรือไม่ FRD ปัจจุบันให้ค่าว่าง = ยอดที่ขอ
5. หลัง approve แล้วไม่ส่ง Budget เป็นพฤติกรรมถาวรหรือเฉพาะ release นี้ ผู้ใช้จะนำยอดอนุมัติไปทำงานต่ออย่างไร
6. การเปลี่ยนสถานะกิจกรรมควรมี note, วันที่ดำเนินการจริง หรือหลักฐานหรือไม่ ปัจจุบัน FRD เก็บเพียง from/to ใน audit
7. เอกสารที่ถูก “ไม่อนุมัติ” กลับเป็นร่าง จึงไม่มีสถานะ rejected ผู้บริหารต้องการรายงานจำนวนที่ถูกตีกลับหรือไม่
8. admin ยกเลิก pending ได้โดยไม่ใช่ approver จริงหรือไม่ และควรแจ้ง owner ด้วยหรือไม่ FRD ระบุแจ้งเฉพาะผู้อนุมัติขั้นปัจจุบัน
9. เลข PJP ที่ออกตั้งแต่บันทึกร่างและยกเลิกภายหลัง ยอมให้เลขขาดช่วงหรือไม่
10. PDF เก็บถาวรควรเป็น snapshot ตอนอนุมัติ หรือควรสะท้อนสถานะกิจกรรมล่าสุด ควรมีชื่อ/ป้ายแยกสองฉบับหรือไม่
11. ผู้อนุมัติทุกคนเห็น attachment ที่อาจมีข้อมูลลับได้ทั้งหมดหรือไม่
12. retention, การลบไฟล์แนบ, และสิทธิ์ดาวน์โหลดหลังพนักงานย้ายหน่วยงานเป็นอย่างไร

## 8. เกณฑ์ตัดสินผล

### Critical — หยุดรับรองทันที

- ข้ามสิทธิ์, ข้ามลำดับอนุมัติ หรือข้อมูลข้าม tenant
- เอกสาร/ยอดเงิน/สถานะสูญหายหรือผิด
- อนุมัติซ้ำ, เลขซ้ำ, event ซ้ำ หรือ approved_final ผิดใบ
- ผู้จัดทำอนุมัติใบตนเองได้

### High — ไม่ควร sign-off จนแก้และ retest

- สูตรวัน/ยอดงบผิด
- reject/cancel/approve ไปผิด state
- งบอนุมัติหรือผู้รับ notification ผิด
- PDF/CSV ใช้ข้อมูลผิดหรือรั่วข้อมูล
- audit ไม่บันทึก action สำคัญ

### Medium

- validation ผิด FRD แต่มีทางเลี่ยงที่ไม่ทำให้ข้อมูลเสีย
- error recovery, stale handling, filter/export หรือ attachment ผิดบางกรณี

### Low / Suggestion

- ข้อความสื่อสารไม่ชัด, label ชวนเข้าใจผิด หรือขั้นตอนใช้งานไม่ลื่น แต่ logic ถูก

Sign-off ที่น่าเชื่อถือควรมีอย่างน้อย:

- Critical/High ค้าง = 0
- เคส RV-01 ถึง RV-65 มีผลหรือมีเหตุผล `BLOCK` ที่ PM/BA รับทราบ
- คำถาม Business Sense ข้อ 1–10 มี decision owner และหลักฐานยืนยัน
- Retest เฉพาะจุดหลังแก้ พร้อม regression ของ journey ที่เกี่ยวข้อง

## 10. แผนรันแบบใช้เวลาคุ้ม

- รอบ 1 — 60–90 นาที: Journey A + RV-37 ถึง RV-48 เพื่อจับ logic และ permission ที่เสี่ยงสูง
- รอบ 2 — 60 นาที: Journey B/C + validation RV-11 ถึง RV-18
- รอบ 3 — 60–90 นาที: PDF, CSV, notification, audit และ Document Store
- รอบ 4 — 45–60 นาที: concurrency, idempotency, tenant isolation และ error recovery โดยมี dev/ops ช่วยดู log
- รอบปิด: สรุป FAIL/BLOCK, ขอ PM/BA ตัดสิน policy gap แล้ว retest เฉพาะจุดพร้อม regression journey
