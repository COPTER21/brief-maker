### §3.1 ⭐⭐ ทำไมจุดตัดถึงเป็น **action** ไม่ใช่ช่วงจำนวนเงิน — **ข้อสำคัญที่สุดของใบนี้**

**Payroll คือ feature ที่การใส่วงเงินลง matrix น่าดึงดูดที่สุดในทั้งระบบ** — ยอดรวมของรอบเป็นตัวเลขที่ใหญ่ ชัด และวางอยู่ตรงหน้าอยู่แล้ว การเขียนกติกาแบบ *"รอบเกิน 5 ล้านต้องถึงกรรมการผู้จัดการ"* อ่านแล้วเข้าท่ามาก **และเราไม่ทำ** ด้วยเหตุผลสี่ข้อ:

1. **ยอดรวมของรอบไม่ใช่มาตรวัดความเสี่ยง** — ยอดรวมโตตามจำนวนพนักงาน ไม่ใช่ตามความผิดปกติ · บริษัทที่โต 3 เท่าจะข้ามเส้นวงเงินทุกรอบตั้งแต่เดือนหน้าโดยที่ **ไม่มีอะไรผิดปกติเลย** ผลคือขั้นผู้บริหารสูงสุดกลายเป็นตรายางประจำเดือน ซึ่งแย่กว่าไม่มีขั้นนั้น · **สิ่งที่วัดความเสี่ยงจริงคือ "ต่างจากรอบก่อนแค่ไหน" และ "รอบนี้เป็นรอบชนิดอะไร"** — ซึ่งคือธงสองตัวที่เราใช้
2. **วงเงินใน matrix คือแหล่งความจริงที่สอง และมันจะเก่าเงียบ ๆ** — วันที่ **HR Configuration ประกาศอัตราประกันสังคม/เพดาน/ขั้นบันไดภาษีเวอร์ชันใหม่** หรือวันที่ **Salary Structure ประกาศกระบอกเงินเดือนใหม่** ยอดรวมของรอบจะขยับทั้งบริษัททันที แต่ **เส้นวงเงินที่ DOA ไม่ขยับตาม** — matrix จะผิดตั้งแต่วันนั้นโดยไม่มีใครรู้ · นั่นคือการ hardcode ค่าที่มี `effective_date` ในอีกรูปแบบหนึ่ง ซึ่งผิด **`P-8`** (HR Config) และ **`P-8′`** (Salary Structure) ตรง ๆ
3. **ยอดรวมของรอบเป็นข้อมูล RESTRICTED สูงสุดในโมดูล** — การส่งมันเข้า `GET /doa/resolve` แปลว่าตัวเลขค่าจ้างรวมของทั้งบริษัทไหลออกไปอยู่ในระบบอนุมัติกลางและใน log ของมัน ซึ่งมีขอบเขตสิทธิ์คนละชุดกับ Policy Center ที่ปกป้องข้อมูลค่าจ้างอยู่ · **ธงบูลีนกับจำนวนคนไม่รั่วอะไรเลย ตัวเลขเงินรั่วทุกอย่าง**
4. **นี่คือหลักการเดียวกับที่ใบพี่น้องเคาะไว้แล้วสามใบ** — **OT** เลือก action จากธง `over_cap` (คำนวณจากเพดานที่ HR Config เผยแพร่) แทนการฝังจำนวนชั่วโมงเป็น band · **Leave** เลือก action จากประเภทการลา แทนการฝังจำนวนวัน · **Employee Movement** เลือก action จาก (`sub_type`, `has_pay_change`) แทนการฝังจำนวนเงินหรือเปอร์เซ็นต์การขึ้นค่าจ้าง — **ใบนี้ใช้หลักเดียวกันกับ (`run_type`, `has_material_variance`)** และเป็นใบที่หลักการนี้มีค่าที่สุด เพราะเป็นใบเดียวที่มีตัวเลขเงินจริงให้เอาไปฝัง

**วิธีที่ประกาศไว้ในใบนี้ (ทั้งวงจร):**
```
เกณฑ์ "ต่างอย่างมีนัยสำคัญ"  ← อ่านจาก HR Configuration (payroll_review.variance_threshold · มี effective_date)
        │
        ▼
has_material_variance  ← Payroll คำนวณธงเอง (PREBRIEF §3.5 ขั้น R · BR-24)
        │
        ├── run_type ─────────────┐
        ▼                         ▼
   action_id = f(run_type, has_material_variance)     ← ฟังก์ชันตายตัว ไม่ใช่ดุลพินิจ (FN-47)
        │
        ▼
   GET /doa/resolve(action_id, employee_count, period_code, company_id)   ← ⛔ ไม่มีจำนวนเงิน (FN-49)
        │
        ▼
   approval_chain (2–5 ขั้น จากของจริง)   → เก็บ config_version_ids ไว้บนรอบเป็นหลักฐานว่าตัดสินด้วยเกณฑ์เวอร์ชันไหน
```

**ผลคือ invariant สองข้ออยู่ครบพร้อมกัน:** สายอนุมัติมาจาก DOA 100% (ไม่ hardcode chain) **และ** ค่าที่มี `effective_date` ยังอยู่ที่เจ้าของเดิม 100% (ไม่ hardcode legal parameter)

**กรณี `has_material_variance = null`** (ยังไม่มีเกณฑ์ให้อ่าน — `OQ-STD-PAY6` · S-31) → **`f()` คืน `payroll_approve_run_variance` คือสายที่ยาวกว่า** · **ปลอดภัยไว้ก่อน ไม่ใช่ปล่อยผ่าน** — นี่เป็นการเลือกทางที่เข้มกว่าเมื่อไม่รู้ ซึ่งเป็นคนละเรื่องกับการ default ค่าตัวเลข (FN-45)

**ทางเลือกที่ต้องให้ Architect เคาะ (`OQ-DOA-P2`):** ถ้า DOA Engine รองรับ **มิติจุดตัดที่ไม่ใช่เงิน** (`threshold_key: payroll_run_type` แบบ enum + `payroll_has_material_variance` แบบ boolean ที่ feature ส่งเข้ามา) ให้ยุบเหลือ **1 action หลาย set** ได้ — แต่ **ห้ามใส่จำนวนเงินหรือเปอร์เซ็นต์เป็นขอบของ set เด็ดขาด** ไม่ว่าจะเลือกทางไหน

### §3.2 กติกาอื่นของสาย

- **`role-comp-admin` เป็น step 2 ของทุก set** — เป็นขั้นที่ **ต้องเห็นตัวเลขจริง** และเป็น role เดียวกับที่ Salary Structure อนุญาตให้เห็น `base_amount` · เหตุผล: คนที่รับผิดชอบโครงเงินเดือนต้องเห็นก่อนว่ายอดที่จะจ่ายสอดคล้องกับอัตราที่ตัวเองดูแลหรือไม่ (ตระกูลเดียวกับ step 4 ของ set 4 ใน `F-HR-MOVE`)
- **`role-mgr-finance` เป็นขั้นสุดท้ายของ set 1** — เพราะการปิดรอบสร้าง **ภาระเงินสด** (ท่อ FC ใน `CSQ_BRIEF`) การเงินต้องรู้ก่อนที่ไฟล์โอนจะออก
- **`role-internal-audit` มีเฉพาะ set 5 (กลับรายการ)** — การกลับรายการรอบที่ปิดแล้วเป็นการกระทำเดียวในระบบนี้ที่ลบผลของรอบที่จ่ายไปแล้ว จึงต้องมีคนนอกสายปฏิบัติการเห็น `[DEFAULT — รอยืนยัน]`
- **มติ 2026-08-17 (บังคับ):** ทุก slot ต้องเลือก **"คน" ในตำแหน่ง** — แสดง **avatar + ตำแหน่ง + ชื่อ** ไม่ใช่ role id ลอย (FN-50)
- **จำนวน slot บนหน้าจอ = จำนวน step ที่ resolve ได้จริง (3 · 4 หรือ 5)** — html **ห้ามวาด slot ตายตัว** (FN-50)
- **SoD (BR-27 · FN-50):** ผู้จัดทำรอบเซ็นอนุมัติรอบของตัวเองไม่ได้ · กรณี HR Payroll Officer เป็นคนเดียวกับ `role-mgr-hr` ให้ engine ขึ้นไปหาผู้บังคับบัญชาเหนือขึ้นไป `[DEFAULT — รอยืนยัน]` (`OQ-DOA-P1`)
- **ส่งใหม่หลังไม่อนุมัติ = `resolve` สายใหม่ทั้งสาย** — และ **ชั้นของสายเปลี่ยนได้ถ้าธง `has_material_variance` เปลี่ยนหลังแก้** (FN-51)
- **ระหว่างรออนุมัติ การคำนวณถูกล็อก** (T-07) — ผู้อนุมัติจึงมั่นใจได้ว่าตัวเลขที่เห็นคือตัวเลขที่จะถูกปิดรอบ
