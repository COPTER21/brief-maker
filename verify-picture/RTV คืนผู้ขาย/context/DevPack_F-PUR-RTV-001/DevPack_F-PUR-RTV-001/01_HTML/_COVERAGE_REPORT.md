## 2. ★ ข้อค้นพบสำคัญที่สุดรอบนี้ — `baseQty()` ไม่ทำตาม PREBRIEF §3.3

### 2.1 อาการ

`baseQty(grnCode, ln, reasonCode)` (บรรทัด 1007–1014) รับ `reasonCode` มา **แต่ใช้จริงเฉพาะค่า `'over'`**:

```js
if (gl.movedOut) return 0;
if (reasonCode === 'over') return gl.over || 0;
if (gl.qcFail > 0) return gl.qcFail;        // ← ไม่ดู reasonCode เลย
return Math.max(0, gl.recv - gl.qcFail);    // ← ไปถึงเฉพาะเมื่อ qcFail = 0
```

PREBRIEF §3.3 กำหนดว่า **ฐานคืนได้ขึ้นกับเหตุผล**:

| เหตุผล | ฐานคืนได้ตาม PREBRIEF §3.3 |
|---|---|
| QC ไม่ผ่าน | `จำนวนที่ QC ไม่ผ่าน` |
| รับเกิน | `จำนวนที่รับเกิน` |
| **ผิดสเปค / อื่น ๆ** | **`จำนวนที่รับเข้า − จำนวนที่ QC ไม่ผ่าน`** (ของที่เข้าคลังปกติ) |

โค้ดไปถึงบรรทัดสุดท้าย **ก็ต่อเมื่อ `qcFail = 0`** → เมื่อบรรทัดมีของไม่ผ่าน QC อยู่แม้แต่ชิ้นเดียว การเลือกเหตุผล **"ผิดสเปค"** หรือ **"อื่น ๆ"** จะได้เพดาน = จำนวนที่ไม่ผ่าน QC ไม่ใช่ของดีในคลัง

### 2.3 ผลกระทบเชิงธุรกิจ

**S-20** (`เหตุผลคืน = ผิดสเปค / อื่น ๆ`) ระบุชัดว่าเป็นกรณี *"ของ **ผ่าน QC** ตอนรับ แต่พบภายหลังว่าไม่ตรงสเปค"*
แต่ในโค้ด ถ้าบรรทัดนั้นมีของไม่ผ่าน QC ปนอยู่ ผู้ใช้จะคืน "ของดีที่ผิดสเปค" ได้ไม่เกินจำนวนที่ไม่ผ่าน QC
→ **S-20 เดินไม่ถึงในชุด mock ปัจจุบัน** เพราะบรรทัดที่ `qcFail = 0` มีอยู่ 2 บรรทัด และทั้งคู่ติดเงื่อนไขอื่น (`over > 0` / `movedOut = true`)

ตัวอย่างรูปธรรม: รับตลับหมึก 100 · ไม่ผ่าน QC 12 · ต่อมาพบว่าใน 88 ที่ผ่าน QC มี 30 ที่รุ่นผิด → ระบบยอมให้กรอกได้สูงสุด **12** ไม่ใช่ 88
