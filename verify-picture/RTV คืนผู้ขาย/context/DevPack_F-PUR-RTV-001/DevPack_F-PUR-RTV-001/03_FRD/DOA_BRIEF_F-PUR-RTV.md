## 2. Approval Actions

| Action | Trigger | สถานะก่อน | ผลเมื่ออนุมัติครบ | ผลเมื่อส่งกลับแก้ | ผลเมื่อปฏิเสธ |
|---|---|---|---|---|---|
| **ส่งอนุมัติใบคืนสินค้า** | ผู้ใช้กด "ส่งอนุมัติ" ที่ wizard step 5 | `ร่าง` | `อนุมัติแล้ว` — **ปุ่มบันทึกส่งคืนเปิด (stock ยังไม่ขยับ)** | กลับ `ร่าง` แก้ต่อได้ · เลข RTV เดิมคงอยู่ | `ยกเลิก` (สถานะปลายทาง) |
| **ส่งอนุมัติซ้ำหลังถูกส่งกลับแก้** | แก้แล้วกดส่งอนุมัติอีกครั้ง | `ร่าง` | `อนุมัติแล้ว` (สายใหม่ตาม **มูลค่าใหม่**) | กลับ `ร่าง` | `ยกเลิก` |

> **ไม่มี** DOA ที่ `กลับรายการ` — จำกัดด้วยสิทธิ์ (หัวหน้าคลัง) + เหตุผลบังคับแทน → ดู DOA-Q3

## 3. Matrix ที่จะไปตั้งค่าที่หน้า DOA กลาง

**ฐานวงเงิน = `มูลค่าที่คืนรวม` (รวม VAT) หน่วย = บาท · `amount_to: null` = ไม่จำกัด · ช่วงต่อเนื่องไม่ทับ ไม่มีรู**

| set | amount_from | amount_to | departments | chainMode | steps (ลำดับ slot) |
|---|---|---|---|---|---|
| 1 | 0 | 50,000 | merged | sequential | slot 1: หัวหน้าคลัง |
| 2 | 50,001 | 500,000 | merged | sequential | slot 1: หัวหน้าคลัง → slot 2: หัวหน้าแผนกจัดซื้อ |
| 3 | 500,001 | *null (ไม่จำกัด)* | merged | sequential | slot 1: หัวหน้าคลัง → slot 2: หัวหน้าแผนกจัดซื้อ → slot 3: ผู้อำนวยการสายงาน |

`[DEFAULT — รอยืนยัน]` ทั้ง 3 set — จุดตัดวงเงินและจำนวนชั้นยังไม่ผ่านการเคาะจากเจ้าของกระบวนการ (owner: **Strike** · pin `OQ-RTV-02`)

> จุดตัดของ RTV ตั้งไว้ **ต่ำกว่า PO** (50,000/500,000 เทียบกับ 100,000/1,000,000) โดยเจตนา — การปล่อยของออกจากคลังมีความเสี่ยงของหายสูงกว่าการก่อภาระผูกพันซื้อ `[DEFAULT — รอยืนยัน]`

**Gate check**
- G2 ทุก set มี `amount_from` + `amount_to` ครบ ✅
- G3 ช่วงต่อเนื่อง 0→50,000 · 50,001→500,000 · 500,001→null — ไม่ทับ ไม่มีรู ✅
- G4 set สุดท้าย `amount_to: null` ✅
- G5 `approval_scope = document_sign` ✅
- G6 ค่าที่ยังไม่ยืนยันติด `[DEFAULT — รอยืนยัน]` ครบ ✅
- G7 ไม่มีสายอนุมัติ hardcode ใน HTML/เอกสาร feature — HTML ใช้ mock ที่ resolve จากรูป DOA entry + marker `FWD-WIRE: DOA engine` ✅
- G1 role master (`references/doa-contract.md`) **ไม่มีในเลนนี้** → เขียน slot เป็น "นิยามตำแหน่งที่ทะเบียน DOA ใช้ดึงคน" แทน role id · ผู้ตั้งค่าต้อง map เป็น `role-*` จริงตอนกรอกที่หน้า DOA กลาง — **บันทึกเป็นข้อจำกัดของรอบนี้ ไม่ใช่การแต่ง role เอง** (เหมือน F-PUR-PO)

| **ยอดเปลี่ยน → สายเปลี่ยน** | mock ต้องมีอย่างน้อย **2 tier** ให้เห็นจริงว่าข้ามจุดตัดแล้ว slot เพิ่ม (§8 ของ PREBRIEF: `RTV-2026-0005` 1 ชั้น · `RTV-2026-0006` 2 ชั้น) |

**ข้อห้ามใน code**
- ❌ `const APPROVAL_CHAIN = [...]` ในไฟล์ feature
- ❌ business rule แบบ "ถ้าเกิน 50,000 ให้หัวหน้าจัดซื้อเซ็น" ใน FRD/feature — นั่นคือ**ข้อมูลใน DOA**
- ✅ เขียนแทนว่า: *ระบบ resolve สายจาก DOA entry ณ เวลากดส่งอนุมัติ (ฐาน = มูลค่าที่คืนรวม) แล้ว snapshot ลง `approval_chain`*
- ✅ จุดที่ยังต่อ engine ไม่ได้ → ใน .md ใช้ `TODO: DOA engine` · **ใน HTML ใช้ marker `FWD-WIRE: DOA engine`** (convention เลน · _RUNNER_BRIEF §2.11)

## 6. Business Rules ที่ต้องมี (ส่งต่อ FRD Phase B)

| BR | เนื้อหา | ตรงกับ PREBRIEF |
|---|---|---|
| BR-DOA-01 | ส่งอนุมัติได้เฉพาะสถานะ `ร่าง` | §5.1 |
| BR-DOA-02 | สาย resolve ตอนส่ง แล้ว **freeze** — แก้ทะเบียน DOA ทีหลังไม่กระทบใบที่ส่งไปแล้ว | §7 |
| BR-DOA-03 | ส่งกลับแก้ → `ร่าง` · ประวัติเก็บ **append-only** | S-09 · BR-12/BR-22 |
| BR-DOA-04 | ผู้ขอคืน/ผู้สร้างเซ็นอนุมัติใบตัวเองไม่ได้ (segregation of duty) | `[AI-DRAFT]` |
| BR-DOA-05 | **แก้มูลค่าหลังถูกส่งกลับแก้ → re-resolve สายใหม่ + เลือกคนจริงใหม่ทุก slot** | S-17 · BR-11 |
| BR-DOA-06 | **ของออกจากคลังไม่ได้จนกว่าใบจะ `อนุมัติแล้ว`** (ไม่มีทางลัด) | BR-09/BR-13 |
