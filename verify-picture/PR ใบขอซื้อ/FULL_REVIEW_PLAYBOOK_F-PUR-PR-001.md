# Full Review Playbook — F-PUR-PR-001 ใบขอซื้อ

วันที่จัดทำ: 2026-10-15  
ฐานอ้างอิงหลัก: `context/DevPack_F-PUR-PR-001/DevPack_F-PUR-PR-001/03_FRD/`  
วัตถุประสงค์: ตรวจ logic และการทำงานของระบบที่ขึ้น production แล้ว โดยไม่รับรองแทนสิ่งที่ยังไม่ได้ทดสอบจริง

## 1. ข้อสรุปก่อนเริ่ม

ให้ใช้ FRD เป็น **เกณฑ์ตัดสินหลัก** แต่ไม่ใช่หลักฐานว่าระบบ production ทำงานถูกแล้ว เพราะ pack นี้มีทั้งค่าที่ยังเป็น `[ASSUMED]`, `[AI-DEFAULT]`, mock, TODO, open question และ declaration ที่ระบุ `wire_status: pending`

รอบนี้ไม่ควรเสียเวลารีวิว layout ซ้ำทั้งหมด ให้ดู UI เฉพาะเมื่อมีผลต่อ logic เช่น ปุ่มตามสิทธิ์ สถานะ ยอดรวม คำเตือน และประวัติ

ผลแต่ละข้อควรเป็นหนึ่งใน 4 ค่า:

- `PASS` — ทดสอบจริงและตรง FRD
- `FAIL` — ทดสอบจริงและขัด FRD
- `BLOCKED` — ทดสอบไม่ได้เพราะข้อมูล/สิทธิ์/integration ไม่พร้อม
- `NEEDS-BA` — พฤติกรรมจริงมีได้หลายแบบและ FRD ยังเป็น assumption/open question

ห้ามใช้คำว่า PASS จากคำบอกว่า “tester ผ่านแล้ว” โดยไม่มีหลักฐานของรอบนี้

## 2. จุดเสี่ยงที่ต้องยืนยันก่อนรับรอง production

| ระดับ | จุดเสี่ยง | สิ่งที่ต้องพิสูจน์ |
|---|---|---|
| P0 | DOA brief ยังเขียน `wire_status: pending` | production resolve สายจากทะเบียน DOA จริง ไม่ใช่ mock/hardcode; snapshot สายไว้กับใบตอนส่ง |
| P0 | วงเงิน 50,000 / 500,000 เป็น `[ASSUMED]` | ขอค่าจริงจากหน้า DOA/config แล้วทดสอบ boundary ตามค่าจริง ห้ามสรุปจากตัวเลขใน FRD อย่างเดียว |
| P0 | ผู้ขอห้ามอนุมัติใบตัวเอง | ทั้ง UI และ API ต้องกัน; เปลี่ยน URL/ยิง request ตรงก็ต้องถูกปฏิเสธ |
| P0 | ยอดเงินต้องคำนวณฝั่ง server | แก้ payload ยอดรวมจาก client แล้ว server ต้องคำนวณใหม่จาก line items |
| P0 | กดส่ง/อนุมัติซ้ำและทำพร้อมกัน | ต้องไม่เกิดเลขเอกสารซ้ำ สถานะซ้ำ ลายเซ็นซ้ำ หรือ event ซ้ำ |
| P0 | สิทธิ์ดูข้อมูลราคา/ผู้ขาย/งบ | ผู้ไม่มีสิทธิ์ต้องเปิดใบไม่ได้หรือไม่เห็นข้อมูล confidential ตาม role |
| P0 | ยกเลิกใบที่มี PO อ้างอิง | ต้อง block จริงเมื่อ W3 พร้อม; ถ้ายังทดสอบไม่ได้ให้ `BLOCKED` ห้าม PASS |
| P1 | Budget Control ใน FRD เป็น mock | ยืนยันกับ PM/BA ว่า production ยอมให้เป็น “จำลอง” จริง และงบไม่พอเตือนแต่ไม่ block |
| P1 | ปุ่มสาธิตต้องถูกถอดก่อน production | ต้องไม่พบ `ทดสอบสถานะโหลดผิดพลาด` และ `ทดสอบไฟล์ไม่ผ่านเงื่อนไข` |
| P1 | ค่าที่เป็น `[AI-DEFAULT]` | concurrency: คนแรกชนะ, edit conflict, duplicate submit ต้องให้ BA รับรองหรือจัดเป็น `NEEDS-BA` |
| P1 | Event/สำเนา/ประวัติ | ตรวจ log หรือระบบปลายทางว่าถูกยิงหนึ่งครั้ง ถูกผู้รับ และ audit append-only |

## 3. สิ่งที่ต้องเตรียม

### 3.1 บัญชีผู้ใช้

- U1 ผู้ขอซื้อ
- U2 หัวหน้าหน่วยงาน/ผู้อนุมัติขั้น 1
- U3 ผู้จัดการจัดซื้อ/ผู้อนุมัติขั้น 2
- U4 CFO/ผู้อนุมัติขั้น 3
- U5 เจ้าหน้าที่จัดซื้อแบบดูอย่างเดียว
- U6 ผู้ใช้คนละหน่วยงานที่ไม่มีสิทธิ์
- U7 ผู้ดูแล DOA/Document Configuration (ใช้ดูค่า config ไม่ควรแก้ production โดยไม่มีอนุญาต)

ห้ามให้ U1 ซ้ำกับ U2/U3/U4 ในชุด happy path เพราะจะชนกฎ self-approval

### 3.2 ข้อมูลทดสอบ

- ใบต่ำกว่า threshold, เท่ากับ threshold, สูงกว่า threshold 0.01 บาท และยอดสูงสุดที่อนุญาต
- สินค้าในทะเบียน และ free-text นอกทะเบียน
- รายการ VAT: ไม่คิดภาษี, บวก VAT, รวม VAT แล้ว
- ส่วนลดรายบรรทัดแบบ %, แบบจำนวนเงิน, ส่วนลดท้ายบิล, WHT
- ศูนย์ต้นทุน: งบพอ, งบไม่พอ, และไม่เลือก
- ไฟล์ PDF/JPG/PNG/XLSX ต่ำกว่า 10 MB; ไฟล์ชนิดผิด; ไฟล์เกิน 10 MB; ชื่อไฟล์ยาว/ภาษาไทย
- ใบที่มี PO อ้างอิง (ถ้า W3 production ใช้งานแล้ว)

ใช้ข้อมูลทดสอบที่ระบุชัดและล้าง/ยกเลิกได้ ห้ามทดลองยกเลิกเอกสารธุรกิจจริง

## 4. ลำดับทดสอบหลัก

### Quick Run — การใช้งานจริง Create / Update / Delete

> คำว่า Delete สำหรับใบ PR ในฟีเจอร์นี้หมายถึง **ยกเลิกเอกสาร (Cancel)** ไม่ใช่ลบข้อมูลออกจากระบบ เพราะ FRD กำหนดให้ประวัติเป็น append-only และไม่มีการลบใบถาวร ส่วนที่ลบจริงได้คือไฟล์แนบขณะเอกสารยังเป็น draft

#### CRUD-01 — Create: สร้างและบันทึกร่าง

1. Login เป็น U1 ผู้ขอซื้อ แล้วกดสร้างใบขอซื้อใหม่
2. กรอกหน่วยงาน วันที่เอกสาร วันที่ต้องการใช้ ประเภท เหตุผล และศูนย์ต้นทุน
3. เพิ่มสินค้าในทะเบียน 1 รายการและรายการ free-text 1 รายการ
4. ใส่จำนวน ราคา ส่วนลด VAT และผู้ขายแนะนำ
5. แนบไฟล์ PDF 1 ไฟล์ แล้วกดบันทึกร่าง
6. ออกจากหน้า กลับเข้ารายการ และเปิด draft เดิม

Expected:

- สร้างได้เพียง 1 ใบ สถานะ `draft`
- ยังไม่มีเลข PR จริง
- ข้อมูลหัวเอกสาร รายการ ยอด ผู้ขาย และไฟล์แนบยังอยู่ครบ
- history มีรายการสร้างหนึ่งครั้ง
- ผู้ใช้ที่ไม่มีสิทธิ์เปิดใบนี้ไม่ได้

#### CRUD-02 — Create negative: สร้างข้อมูลไม่ครบ

ลองแยกครั้งละกรณี: ไม่กรอกช่องบังคับ, วันที่ต้องการใช้ก่อนวันที่เอกสาร, ไม่มีรายการครบ, จำนวนหรือราคาเป็น 0, มีแถวว่าง, สินค้า+หน่วยซ้ำ

Expected: บันทึก/ไปขั้นต่อไปไม่ได้ตาม validation และต้องไม่มีใบเสียหรือ line ขยะถูกสร้างค้าง

#### CRUD-03 — Update: แก้ไข draft

1. เปิด draft จาก CRUD-01
2. แก้เหตุผล วันที่ ศูนย์ต้นทุน จำนวน ราคา VAT และผู้ขาย
3. เพิ่มหนึ่งรายการ ลบหนึ่งรายการ เพิ่มไฟล์ใหม่ และลบไฟล์เดิม
4. บันทึกแล้ว refresh/เปิดใหม่

Expected:

- แก้ได้เฉพาะ draft
- ยอดคำนวณใหม่ถูกต้องทั้งหน้าจอและข้อมูลที่โหลดกลับมา
- line/ไฟล์ที่เพิ่มและลบตรงกับที่ผู้ใช้ทำ
- history เพิ่มรายการ update พร้อมผู้แก้และเวลา โดย history เดิมไม่หาย
- เลข PR ยังไม่มี

#### CRUD-04 — Update conflict: แก้พร้อมกันสองหน้าต่าง

1. เปิด draft เดียวกันในหน้าต่าง A และ B
2. A แก้เหตุผลและบันทึก
3. B แก้จำนวนแล้วบันทึกโดยไม่ refresh

Expected: B ต้องพบ version conflict หรือพฤติกรรมที่ BA ยืนยัน ห้ามบันทึกทับ A แบบเงียบ ๆ

#### CRUD-05 — Submit แล้วพยายาม Update

1. ส่ง draft เข้าสายอนุมัติจนได้เลข PR
2. เปิด edit route เดิมโดยตรงและลองแก้ผ่าน UI/API

Expected:

- สถานะเป็น `pending_approval` และเลข PR ถูกออกครั้งเดียว
- ไม่มีปุ่มแก้ไข
- direct route/API ต้องถูก block ด้วย `PR_NOT_EDITABLE`
- หากต้องการแก้ ผู้ขอต้อง recall ก่อน

#### CRUD-06 — Recall แล้ว Update และส่งใหม่

1. ให้ผู้อนุมัติขั้นแรกอนุมัติก่อน
2. U1 เรียกคืนเอกสาร
3. แก้ยอดให้ข้ามช่วงวงเงิน แล้วส่งใหม่

Expected:

- กลับเป็น draft และแก้ได้อีกครั้ง
- approval slot เดิมเป็น `void` แต่ยังอยู่ใน history
- ส่งใหม่แล้ว resolve สายตามยอดใหม่
- history และลายเซ็นรอบเก่าไม่ถูกลบ
- ตรวจเลข PR ว่ายังคงเดิมตาม BR-05; หากระบบออกเลขใหม่ให้เป็น `NEEDS-BA/FAIL` จนกว่าจะยืนยันข้อกำหนด

#### CRUD-07 — Delete attachment

1. ใน draft แนบไฟล์แล้วลบไฟล์
2. หลังส่งอนุมัติ ลองลบไฟล์เดิมผ่าน UI และ API โดยตรง

Expected:

- ตอน draft ลบได้ตามสิทธิ์
- หลังพ้น draft ต้องลบไม่ได้และได้ `PR_NOT_EDITABLE`
- การลบไฟล์ต้องไม่ทำให้ไฟล์อื่นหรือข้อมูลเอกสารหาย

#### CRUD-08 — Delete document: ต้องไม่มี hard delete

1. ค้นหาเมนูหรือปุ่มลบใบ PR ใน draft, pending, approved, rejected และ cancelled
2. ลอง direct URL/API ถ้าทราบ endpoint ที่สงสัยว่าใช้ลบ

Expected:

- ไม่มี hard-delete ใบ PR
- ไม่มีการลบ record และไม่มี history หาย
- การสิ้นสุดเอกสารต้องใช้ Cancel ตาม state ที่อนุญาต

#### CRUD-09 — Cancel draft

1. U1 ยกเลิก draft พร้อมเหตุผลอย่างน้อย 3 ตัวอักษร
2. ลองเปิด แก้ ส่งอนุมัติ และยกเลิกซ้ำ

Expected:

- สถานะเป็น `cancelled` และย้อนกลับไม่ได้
- เอกสารและ history ยังเปิดดูได้ตามสิทธิ์
- แก้หรือส่งต่อไม่ได้
- ไม่ยิง `doc.cancelled` ของ 7C เพราะใบยังไม่เคย approved

#### CRUD-10 — Cancel approved

1. อนุมัติใบจนครบทุกขั้น
2. ยกเลิกพร้อมเหตุผล
3. ทำซ้ำกับใบ approved ที่มี PO อ้างอิง ถ้าระบบ PO พร้อม

Expected:

- ใบที่ไม่มี PO อ้างอิงเปลี่ยนเป็น `cancelled`, เก็บเหตุผล และยิง `pr_cancelled` + `doc.cancelled` ครั้งเดียว
- ใบที่มี PO อ้างอิงต้องถูก block ด้วย `PR_HAS_PO_REFERENCE`
- ไม่มี record, PDF snapshot, ลายเซ็น หรือ history ถูกลบ

#### CRUD-11 — ใช้งานต่อจากเอกสารที่จบแล้ว

เปิดใบ rejected/cancelled แล้วใช้ `ทำสำเนาเป็นใบใหม่`

Expected: ได้ draft ใหม่ที่คัดลอกเฉพาะหัวและรายการ แต่ไม่คัดลอกเลข PR, approval slots, ลายเซ็น, history และ attachment

### Session A — Draft และ validation

1. สร้างใบใหม่และบันทึกร่างโดยยังไม่ส่ง
   - ร่างต้องยังไม่มีเลข PR จริง
   - กลับมาแก้ต่อได้ ข้อมูลไม่หาย
   - status ต้องเป็น `draft`
2. ตรวจช่องบังคับ: หน่วยงาน วันที่เอกสาร วันที่ต้องการใช้ ประเภท เหตุผล
3. ใส่วันที่ต้องการใช้ก่อนวันที่เอกสาร ต้องถูก block
4. รายการสินค้า:
   - ไม่มีรายการที่ครบ ต้อง block
   - มีแถวว่าง ต้อง blockและบอกจำนวนแถว
   - สินค้า+หน่วยซ้ำ ต้อง block
   - free-text นอกทะเบียนต้องบันทึกได้
   - จำนวน 0/ติดลบ และราคาประมาณ 0/ติดลบต้องไม่ผ่าน
5. เปิด draft เดียวกัน 2 หน้าต่าง แก้คนละค่าแล้วบันทึก
   - หน้าต่างหลังต้องเจอ version conflict หรือพฤติกรรมที่ BA ยืนยัน
   - ห้ามเงียบแล้วทับข้อมูลของหน้าต่างแรก

### Session B — การคำนวณเงิน (P0)

ทดสอบอย่างน้อยชุดต่อไปนี้และเทียบเลขทุกจุดใน edit, review, view, PDF:

1. `qty × unit price` ไม่มี VAT/ส่วนลด
2. ส่วนลดรายบรรทัดแบบ % และจำนวนเงิน
3. VAT แบบบวกเพิ่ม
4. VAT รวมในราคา: ราคา 107, VAT 7% ต้องได้ฐาน 100.00 และ VAT 7.00
5. หลายบรรทัดปน 3 VAT modes
6. ส่วนลดท้ายบิลต้องไม่ทำให้ยอดติดลบ
7. WHT เป็นค่าประมาณและ **ไม่หักออกจาก grand total**
8. เลขทศนิยมที่บังคับให้เกิดการปัดครึ่งขึ้น
9. ดัดแปลง request ให้ส่ง `subtotal/grand_total` ปลอม
   - server ต้องทิ้งยอดปลอมและคำนวณใหม่จากรายการ

ถ้ายอดในหน้าจอถูกแต่ PDF, DB, API response หรือหน้าผู้อนุมัติไม่ตรง ให้ถือเป็น bug ระดับ High

### Session C — ส่งอนุมัติและเลขเอกสาร

1. ก่อนส่ง ดูสายอนุมัติเป็น “คนจริง”: ชื่อ ตำแหน่ง avatar/อักษรย่อ ครบทุกขั้น
2. เลือกผู้อนุมัติไม่ครบ ต้องส่งไม่ได้
3. เลือก U1 เป็นผู้อนุมัติเอง ต้องถูกปฏิเสธทั้ง UI และ server
4. ส่งใบยอดตาม boundary ของ DOA จริงทุกช่วง
   - จำนวนขั้นต้องตรง config
   - เลขเอกสารออกเฉพาะตอนส่ง
   - เลขแก้ไม่ได้
5. หลังส่ง ให้ U7 เปลี่ยน config ใน test environment แล้วเปิดใบเดิม
   - สายของใบเดิมต้องไม่เปลี่ยน เพราะเป็น snapshot
   - ใบใหม่ต้องใช้ config ใหม่
6. กดส่งรัว/ส่ง request ซ้ำด้วย idempotency key เดิม
   - เกิด PR เพียงใบเดียว เลขเดียว สายเดียว และ notification ชุดเดียว

### Session D — Approval state machine และสิทธิ์

1. U3/U4 พยายามอนุมัติก่อนถึงขั้นตน ต้องทำไม่ได้
2. U6 เปิด URL ใบตรง ๆ ต้องได้ 403/not visible ไม่ใช่แค่ซ่อนเมนู
3. U5 เปิดดูได้ตามสิทธิ์ แต่ไม่มีปุ่ม approve/edit
4. U2 อนุมัติขั้น 1:
   - สถานะยัง pending
   - ขั้นถัดไปได้รับสิทธิ์/notification
   - history และลายเซ็นเพิ่มครั้งเดียว
5. อนุมัติจนครบ:
   - status เป็น approved
   - n/N ครบ
   - สร้าง PDF/สำเนา approved_final
   - ยิง `pr_approved` และ `doc.approved` ครั้งเดียว
6. Reject:
   - เหตุผลต่ำกว่า 3 ตัวอักษรต้องไม่ผ่าน
   - reject แล้วขั้นที่เหลือไม่อนุมัติต่อ
   - `pr_rejected` ต้องส่งและปิดไม่ได้ตาม declaration
7. ผู้อนุมัติสอง session กด approve ขั้นเดียวกันพร้อมกัน
   - คนแรกชนะ คนหลังได้ conflict; ต้องไม่มีลายเซ็น/event ซ้ำ

### Session E — Recall, resubmit, cancel, duplicate

1. หลัง U2 อนุมัติแล้ว ให้ U1 recall
   - เฉพาะผู้ขอทำได้
   - กลับ draft
   - slot เดิมเป็น void แต่ยังอยู่ใน history
   - ผู้อนุมัติค้างได้รับ `pr_recalled`
2. แก้ยอดให้ข้าม threshold แล้วส่งใหม่
   - ต้อง resolve สายใหม่จากยอดใหม่
   - snapshot เก่าไม่ถูกลบ
   - เลขเอกสารเดิมต้องไม่เปลี่ยนตาม BR-05; ถ้าระบบออกเลขใหม่ให้เปิดประเด็นกับ BA ทันที เพราะ FRD ไม่ได้รองรับ
3. ระหว่าง pending พยายามเข้า edit route ตรง ต้องแก้ไม่ได้
4. ยกเลิกจาก draft และ approved ด้วยเหตุผลอย่างน้อย 3 ตัวอักษร
   - ยกเลิกย้อนกลับไม่ได้
   - draft cancel ห้ามยิง `doc.cancelled`
   - approved cancel ต้องยิง `pr_cancelled` และ `doc.cancelled`
5. ยกเลิกใบ approved ที่มี PO อ้างอิง ต้องถูก block
6. ทำสำเนาจาก rejected/cancelled
   - คัดลอกเฉพาะหัวและรายการ
   - ไม่คัดลอกเลข PR, slot, ลายเซ็น, history, attachment

### Session F — Attachment

1. แนบชนิดและขนาดที่อนุญาตทุกแบบ
2. แนบไฟล์ผิดชนิด/เกินขนาดพร้อมไฟล์ดีหลายไฟล์
   - ปฏิเสธเฉพาะไฟล์เสีย ไฟล์ดีต้องไม่หาย
3. ตรวจ server-side validation โดยข้าม client validation
4. ลบไฟล์ตอน draft ต้องได้ตามสิทธิ์; หลังพ้น draft ต้องถูก block ตาม API-12
5. เพิ่มไฟล์หลังส่ง (ถ้าระบบเปิดให้ทำตาม declaration) ต้องแจ้งผู้อนุมัติขั้นปัจจุบันด้วย `pr_attachment_added`
6. ตรวจชื่อไฟล์ซ้ำ, ชื่อไทย, ชื่อยาว, download/open และ access control ของ URL ไฟล์

### Session G — Audit, integration และข้อมูลลับ

1. เดินครบ create, update, submit, approve, reject, recall, cancel แล้วตรวจ history
   - actor, เวลา, before/after, เหตุผลและสถานะต้องถูก
   - ไม่มี edit/delete history
2. ตรวจ notification ทั้ง 7 business events และ DOA events แยกกัน ไม่ยิงซ้ำ
3. ตรวจเลข PR มาจาก Document Configuration และไม่มีเลขซ้ำเมื่อ request ล้ม/ retry
4. ตรวจ approved PDF:
   - ยอด/สถานะ/ผู้ลงนามตรงใบจริง
   - ปี ค.ศ.
   - เปิดได้หลัง refresh และเป็น snapshot ไม่เปลี่ยนตามข้อมูล/config ภายหลัง
5. ตรวจ event 7C:
   - approved → `doc.approved`, EC/estimated
   - cancel หลัง approved → `doc.cancelled`, EC/avoided
   - cancel draft → ไม่ยิง
6. ตรวจ access log เมื่อผู้ที่ไม่ใช่เจ้าของอ่านเอกสาร และการปิดบังราคา งบ ผู้ขายตาม role

## 5. Business exploratory — ควรลองเพิ่ม

ส่วนนี้ใช้หา bug/ช่องโหว่ แต่ถ้า FRD ไม่กำหนด ห้ามสรุป FAIL ทันที ให้ลง `NEEDS-BA` ก่อน

- เปลี่ยนหน่วยงาน/ศูนย์ต้นทุนระหว่างทำ draft แล้วดูว่าสาย DOA และงบ refresh ถูกหรือยัง
- เปลี่ยนยอดตรง boundary ด้วยทศนิยม 0.01 และยอดใหญ่มาก
- เปิดหลาย tab, back/forward, refresh ระหว่าง submit/approve
- session หมดอายุระหว่างบันทึกหรืออัปโหลด แล้ว retry ต้องไม่สร้างข้อมูลซ้ำ
- approver ถูกปิดบัญชี/ย้ายตำแหน่งขณะใบ pending — FRD ระบุว่าเป็นเจ้าของ DOA ไม่ใช่ feature นี้
- ใบ pending นาน — reminder/escalation เป็นเจ้าของ DOA+Notify ไม่ใช่ PR
- vendor/item/cost center ที่ถูก inactive หลังสร้าง draft หรือหลัง submit
- timezone เที่ยงคืน/สิ้นปี เพื่อดูวันที่และเลข run รายปี
- export/print แล้วข้อมูล confidential หลุดให้ role ดูอย่างเดียวหรือไม่
- ค้นหา/กรอง/แบ่งหน้าแล้วข้อมูลต่างหน่วยงานหลุดหรือไม่

## 6. จุดที่ต้องถาม PM/BA ก่อนปิดผล

1. production ใช้วงเงิน DOA เท่าไรจริง และแยกตามหน่วยงานหรือไม่
2. `wire_status: pending` ในเอกสารเก่าถูก wire จริงแล้วหรือยัง ขอหลักฐาน config/log
3. Budget Control production ยังเป็น mock ตาม FRD หรือเชื่อมของจริงแล้ว
4. ยกเลิกใบ approved ต้องอนุมัติซ้ำหรือไม่
5. ข้อกำหนดไฟล์ 10 MB และชนิดไฟล์ได้รับการยืนยันแล้วหรือยัง
6. concurrency defaults ทั้ง 3 ข้อได้รับ BA sign-off หรือไม่: first-wins, version conflict, idempotent submit
7. recall หลังมีเลข PR แล้วส่งใหม่ ต้องใช้เลขเดิมตาม interpretation ของ BR-05 ใช่หรือไม่
8. W3/Compare Vendor เปิดใช้จริงแล้วหรือยัง เพราะ FRD เดิมคาดว่าเป็น future scope

## 7. หลักฐานที่ต้องเก็บต่อหนึ่งเคส

- Test ID / FRD ref เช่น `BR-03`, `AT-22`
- environment/build และวันเวลา
- actor/role และเลข PR
- precondition และ test data ที่ใช้
- steps แบบทำซ้ำได้
- expected จาก FRD
- actual ที่เห็นจริง
- screenshot/video และ request/response หรือ log ที่เกี่ยวข้อง
- ผล `PASS/FAIL/BLOCKED/NEEDS-BA`
- severity และผลกระทบทางธุรกิจ

Severity แนะนำ:

- Critical: ข้ามสิทธิ์/สายอนุมัติ, ข้อมูลหาย, อนุมัติเอง, confidentiality breach
- High: ยอด/ภาษี/สถานะ/เลขเอกสารผิด, duplicate transaction/event, ยกเลิกทั้งที่มี PO
- Medium: history/notification/integration ผิดแต่ core flow ยังเดินได้
- Low: ข้อความ/การแสดงผลที่ไม่ทำให้ตัดสินใจธุรกิจผิด

## 8. เกณฑ์ปิดรอบ review

ปิดได้เมื่อ:

- P0 ทุกข้อเป็น PASS หรือมี owner/กำหนดแก้ที่ยอมรับอย่างเป็นทางการ
- FRD AT-01..AT-40 ถูก map เป็น PASS/FAIL/BLOCKED/NEEDS-BA ครบ ไม่มีช่องว่าง
- BR 12 ข้อ, validation 9 ข้อ, confirmed edge case 7 ข้อ และ cross-module 6 ข้อมีหลักฐาน
- จุด mock/pending/assumed ถูก PM/BA ยืนยันสถานะจริง
- ไม่มี Critical/High ค้างโดยไม่มีแผนแก้และ retest
- รายงานระบุชัดว่าอะไร “ไม่ได้ตรวจ” เพื่อไม่รับรองเกินจริง
