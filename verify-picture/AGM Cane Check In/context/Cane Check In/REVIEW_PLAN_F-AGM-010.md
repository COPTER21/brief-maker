# แผน Review Logic — F-AGM-010 Cane Check-In

วันที่จัดทำ: 14 ตุลาคม 2026  
แหล่งอ้างอิงหลัก: `FRD/00_OVERVIEW.md` ถึง `FRD/06_TESTS.md`

## 1. เป้าหมายรอบนี้

ตรวจแบบเก็บตกหลังขึ้น Production โดยเน้นว่า flow หลักใช้งานได้และข้อมูลไม่ผิด ไม่ทดสอบ UI layout ซ้ำ และไม่พยายามรันทุก test case เดิมทั้งหมด

คำว่า CRUD สำหรับฟีเจอร์นี้ให้ตีความดังนี้:

- Create = เช็คอิน 3 วิธี: CBM, ไม่มีคิว-สมาชิก, ไม่มีคิว-โควต้ากลาง
- Read = รายการ 2 แท็บและหน้ารายละเอียด
- Update = การเปลี่ยนสถานะหลังเช็คอิน, Booking sync และ retry
- Delete = Void เท่านั้น ไม่ใช่ hard delete

## 2. ข้อควรระวังเมื่อทดสอบบน Production

- ใช้ CBM/โควต้า/ทะเบียนรถ/เลขเหรียญที่ทีมธุรกิจอนุญาตให้เป็นข้อมูลทดสอบเท่านั้น
- ตั้งชื่อคนขับหรือหมายเหตุให้ตามรอยได้ เช่น `TEST REVIEW 20261014`
- จดเลขเอกสารที่ระบบสร้างทุกครั้ง และ Void รายการทดสอบเมื่อจบตามขั้นตอนที่ BA อนุญาต
- ห้ามจงใจตัด network หรือทำให้ service จริงล่มเพื่อสร้าง sync failure บน Production; ใช้รายการที่ fail อยู่แล้ว หรือทดสอบกรณีนี้ใน UAT/SIT
- ถ้า Void ของ CBM กระทบงาน Booking/คิวรถจริง ให้ BA หรือ operation ยืนยันก่อนกด

## 4. วิธีตัดสินแบบเร็ว

ถือว่า “ผ่านรอบ review เบื้องต้น” เมื่อข้อ 1–7 ผ่าน และข้อ 8 ผ่านหรือมีหลักฐานชัดว่าไม่มีสถานการณ์ให้ทดสอบบน Production โดยข้อจำกัดนั้นถูกบันทึกไว้

ควรหยุดและแจ้ง PM/BA/Dev ทันทีเมื่อพบอย่างใดอย่างหนึ่ง:

- สร้างรายการแล้วข้อมูลคน รถ โควต้า หรือเลขเหรียญผิด
- CBM เช็คอินแล้ว Booking ไม่เป็น `รอผลการเท` โดยไม่มี badge/error ให้ผู้ใช้จัดการ
- กดซ้ำแล้วเกิด check-in หรือผล sync ซ้ำ
- Member/Central ได้เลข CBM หรือ CBM ได้เลข NBM
- validation ไม่ผ่านแต่มีเอกสารหรือข้อมูลถูกสร้างแล้ว
- Void แล้วรายการยังถูกใช้งานต่อเหมือน active หรือประวัติหาย
- ผู้ใช้ที่ไม่มีสิทธิ์สามารถ Void หรือแก้ผลธุรกิจได้

## 5. ประเด็นที่ FRD ยังไม่ชัด ห้ามฟันธงเป็น Bug เอง

1. **Void ของ CBM ต้องย้อน Booking หรือไม่** — `00_OVERVIEW` ระบุ void reversal event อยู่นอก scope, `02_API` ระบุเป็น OQ-04 แต่ `06_TESTS` มี XT-05 คาดหวัง reversal event. ให้ BA ยืนยัน expected ก่อนทดสอบ/แจ้ง defect
2. **แก้ไขรายการหลังเช็คอิน** — FRD ไม่มี edit flow จึงไม่ต้องหา Update form; Update ที่ต้องตรวจคือ state/sync/retry
3. **ลบถาวร** — FRD กำหนด Void และ audit append-only ไม่มี hard delete; การไม่มีปุ่มลบไม่ใช่ defect
4. **ห้าม CBM เดิมเช็คอินซ้ำหรือไม่** — FRD กำหนด idempotency ด้วย `checkin_id` แต่ไม่ได้ระบุ unique ต่อ `cbm_code`; ถ้าพบว่าสร้างซ้ำจาก CBM เดิมได้ ให้บันทึกเป็น business question ก่อน
5. **เลขเหรียญซ้ำได้หรือไม่** — FRD บังคับว่าต้องกรอก แต่ไม่ได้ระบุ uniqueness
6. **รายการ `เสร็จสิ้น` Void ได้หรือไม่** — state machine ระบุ void จาก `เช็คอินแล้ว`; boundary นี้ควรให้ BA ยืนยันหากหน้าจออนุญาต

## 6. หลักฐานที่ควรเก็บต่อหนึ่งเคส

- เลขเอกสาร CBM/NBM หรือ check-in ID
- วันเวลาและผู้ใช้ที่ทดสอบ
- ข้อมูลสำคัญก่อนทำและผลหลังทำ
- ภาพหน้าจอเฉพาะจุดที่ยืนยันผล หรือข้อความ error
- ถ้าไม่ผ่าน: ขั้นตอนสั้น ๆ, expected จาก FRD, actual ที่เห็นจริง, และผลกระทบธุรกิจ

เมื่อทดสอบเสร็จ ให้นำผลในตารางพร้อมหลักฐานมาสร้าง Feature Check Report รอบ 1; ข้อที่ไม่ได้ทดสอบต้องระบุ `ไม่ได้ตรวจ` ไม่ควรเติมว่า `ผ่าน`
