# Full Logic & Functional Review Plan

Feature: หัวข้อการประเมินความพึงพอใจ สำหรับ General Trade  
รหัสที่พบบนระบบจริง: `F-SAL-011` / รหัสแบบพิมพ์ `FM-SAL-11`  
รหัสชั่วคราวใน FRD: `F-TMP-002` / doc type `CSM`  
วันที่จัดทำแผน: 17 พฤศจิกายน 2026  
สถานะ: แผนตรวจ — **ยังไม่ใช่ผล Pass/Fail**

## 1. บทสรุปสำหรับผู้ตรวจ

รอบนี้ไม่ควรเสียเวลาตรวจ layout ซ้ำ แต่ควรพิสูจน์ 7 เรื่องนี้ให้ได้:

1. สูตรคะแนนและการแปลผลถูกต้องจริง โดยเฉพาะ `% โดยรวม` ที่ต้องถ่วงตามจำนวนคำตอบ ไม่ใช่เฉลี่ย 3 ด้าน
2. สถานะและ approval flow ไม่สามารถข้ามขั้น อนุมัติตัวเอง หรือตัดสินซ้ำ
3. สิทธิ์การเห็น/แก้/ยกเลิกแยกตาม owner, current approver, Sales admin, คนต่างเขต และ tenant
4. config, หัวข้อ, ระดับคะแนน, ช่วงแปลผล และสาย DOA ถูก snapshot ตามจังหวะที่ FRD กำหนด
5. การกดซ้ำ, สองแท็บแก้พร้อมกัน, network/API ล้ม ไม่ทำให้เลขซ้ำ อนุมัติซ้ำ หรือสถานะผิด
6. PDF/CSV/แจ้งเตือนใช้ข้อมูลชุดเดียวกับหน้าจอ และ approved PDF ไม่เปลี่ยนตาม config/master ภายหลัง
7. audit trail เก็บคน เวลา เหตุผล และลำดับเหตุการณ์ครบ

## 2. ผลจากการ review เอกสาร

### 2.1 จุดที่ยังต้องพิสูจน์ในระบบจริง

- DevPack ระบุว่ามี AI test case 64 เคส แต่ QA Audit ย่อ UAT สำหรับคนลง และระบุหลายเคสว่า “ตรวจโดย AI (testcases MD)” จึงห้ามสรุปว่าทุก logic ถูกรับรองโดยคนแล้ว
- README ระบุ `NO-BROWSER` และไม่มี `e2e_standard`/การ render PDF ในรอบสร้าง pack เอกสารจึงไม่ใช่หลักฐานว่า production PDF/E2E ผ่าน
- FRD เดิมใช้รหัสชั่วคราว `F-TMP-002`/บทบาท `role-mgr-bu` แต่ภาพจากระบบจริงแสดง `F-SAL-011 · FM-SAL-11` ต้องยืนยัน mapping ให้ตรงกันทั้ง menu, permission, DOA, document config และ notification
- FRD มี AI-DEFAULT 14 มติ ซึ่งเอกสารเดิมกำหนดว่าต้องได้รับการยืนยันก่อน UAT ควรขอ PM/BA ยืนยันว่า production behavior ยึด locked decisions ชุดนี้จริง

### 2.2 จุดเสี่ยงเชิงธุรกิจที่ FRD ยังไม่ล็อก

ข้อเหล่านี้ไม่ควรแจ้งเป็น bug ทันที แต่ควรเก็บผลจริงแล้วให้ BA/PM ตัดสิน:

1. **สร้างสรุปซ้ำเดือน/หน่วยงานได้** — EC-06 บอกชัดว่าไม่บล็อก เพราะ OQ-06 ยังค้าง ควรถามว่ารายงานปลายทางจะนับใบไหน
2. **จำนวนคำตอบไม่ผูกกับจำนวนลูกค้า** — FRD บังคับเพียงว่าคะแนนรวม > 0 และมีลูกค้า ≥ 1 ไม่ได้บังคับว่า total ของแต่ละหัวข้อต้องเท่ากับจำนวนลูกค้า จึงสามารถเกิด denominator ไม่เท่ากันระหว่างข้อได้
3. **เดือนอนาคต** — FRD กำหนดแค่ required `YYYY-MM` ไม่ได้ห้ามเดือนอนาคต ทั้งที่เป็นสรุปความพึงพอใจรายเดือน
4. **ขอบเขตสถานะ Sale Order** — FRD นับทุกใบที่ `status ≠ cancelled` ควรยืนยันว่า draft/rejected/void หรือใบที่ไม่เกิดการขายจริงควรถูกนับหรือไม่
5. **การลบ/ปิดใช้ลูกค้าภายหลัง** — DB เก็บ customer snapshot แล้ว แต่ควรพิสูจน์ว่าใบเก่า/PDF ยังเปิดได้และชื่อไม่เปลี่ยนตาม master

## 3. การเตรียมก่อนทดสอบ

### 3.1 บัญชีที่ต้องมี

| Maker A — Sales Manager เขต A | สร้าง/แก้/ส่ง/ยกเลิกใบของตน |

### 3.2 ข้อมูลที่ต้องเตรียม

- ลูกค้า GT เขต A ที่มี Sale Order ในเดือนทดสอบจำนวน 0, 2, 3, 4 ใบ
- ลูกค้า GT ต่างเขต 1 ราย และลูกค้าที่ไม่ใช่ GT 1 ราย
- Sale Order ที่ cancelled 1 ใบ, คนละเดือน 1 ใบ และสถานะอื่นที่ธุรกิจสนใจ
- เดือนทดสอบที่ไม่ชนกับข้อมูล production จริง
- สิทธิ์ดู notification inbox/log และ approved PDF ที่เก็บใน Document Center
- ช่องทางดู Network response หรือ API log สำหรับเคส permission/concurrency; ไม่ควรใช้เฉพาะปุ่มที่ซ่อนบน UI เป็นหลักฐานสิทธิ์

> ห้ามเปลี่ยน DOA/SalesConfig/Document Config ของ production โดยไม่มีอนุญาต เคสที่ต้องเปลี่ยน config หรือ simulate API failure ให้รันบน UAT/test tenant

## 6. ลำดับ flow ที่แนะนำให้เล่นจริง

ถ้าเวลามีจำกัด ให้เล่น 5 journey นี้ตามลำดับ:

1. **Happy-high:** สร้างใบ→คำนวณ 85.83→ดึงลูกค้า→ส่ง→อนุมัติครบ→ตรวจ approved PDF/audit
2. **Low-score:** สร้างผล <60→อนุมัติครบ→ตรวจ `csm_low_csat` และผู้รับจริง
3. **Reject/rework:** ส่ง→ไม่อนุมัติ→กลับร่างเลขเดิม→แก้→ส่งใหม่→อนุมัติ→ตรวจ audit สองรอบ
4. **Cancel:** ส่ง→Maker ยกเลิก→ตรวจเหตุผล/status/skipped step/notification→ลองแก้/อนุมัติหลังยกเลิก
5. **Attack/consistency:** คนต่างเขตเปิด direct URL/API→กดซ้ำ→สองแท็บ save ชนกัน→ตรวจ 404/403/409 และไม่มี side effect ซ้ำ

## 7. วิธีตัดสินผลและแยก Bug / OQ / Suggestion

- **Bug:** ผลจริงขัด FRD/locked decision ที่มี expected ชัด หรือเกิดผลผิดต่อข้อมูล/สิทธิ์/สถานะ
- **OQ / business decision:** FRD เว้นไว้หรือบอกว่ายังไม่ตัดสิน เช่น สร้างซ้ำเดือนเดียวกัน หรือเดือนอนาคต
- **Suggestion:** ทำงานตรง FRD แล้ว แต่ปรับแล้วจะลดความเสี่ยง/ใช้งานง่ายขึ้น

| Severity | ใช้เมื่อ |
|---|---|
| Critical | ข้าม tenant/ข้ามสิทธิ์อนุมัติ, ข้อมูลหาย/เสีย, สถานะไม่สามารถกู้ได้ |
| High | สูตรคะแนน/แปลผล/สถานะ/PDF approved ผิด, ออกเลขหรืออนุมัติซ้ำ |
| Medium | ผิด FRD แต่มี workaround, audit/notification/CSV ไม่ครบ |
| Low | ข้อความ, การจัดวาง, ความสม่ำเสมอของภาษา ที่ไม่กระทบงาน |

## 8. หลักฐานที่ต้องเก็บต่อหนึ่งเคส

ต่อหนึ่ง test case ให้เก็บอย่างน้อย:

1. Persona, env/build, วันเวลา, document no/id
2. Test data ที่ใช้ โดยปกปิด PII ที่ไม่จำเป็น
3. ภาพก่อนและหลัง action หรือคลิปสั้นสำหรับ race/double-click
4. Expected กับ Actual เป็นตัวเลข/ข้อความ/สถานะที่เห็นจริง
5. Network status/error code สำหรับ deny/stale/idempotency
6. ผลข้างเคียงที่ต้องไม่เกิด เช่น ไม่มีใบซ้ำ, audit ซ้ำ, notification ซ้ำ

## 9. Exit criteria

จะสรุปว่ารอบ review เพียงพอได้เมื่อ:

- P0 ทุกข้อมีผลและหลักฐาน; ไม่มี Critical/High ค้างที่กระทบผลธุรกิจ
- สูตร 85.83, สูตรถ่วงน้ำหนัก, boundary bands และ zero-side ตรง FRD
- approval/reject/resubmit/cancel และสิทธิ์ direct API ตรง matrix
- มี approved-final PDF จากระบบจริงที่ตรวจแล้ว ไม่ใช่เพียง template/seed ใน context
- PM/BA รับทราบและปิด/ยอมรับ OQ อย่างน้อย 5 ข้อใน §2.2
- ระบุชัดว่าอะไรไม่ได้ตรวจ ไม่ใช้คำว่า “ผ่านทั้งหมด” แทนสิ่งที่ไม่มีหลักฐาน
