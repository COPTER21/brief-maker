## §1 ⚖ DOA — **ไม่ต้อง** และนี่คือเหตุผล (ห้ามปล่อยว่าง)

**scope note ของผู้ใช้ตัดสินไว้ตรงตัว:** *"ขอสลับกะ (พนักงาน→หัวหน้ายืนยัน **ไม่ผ่าน DOA**)"* — และเมื่อไล่ lifecycle ทั้ง feature แล้ว **ไม่พบจุดใดเลยที่ต้องให้ทะเบียนกลาง resolve สายอนุมัติ**

**จุดตัดสินใจเดียวใน feature นี้คือ `§5.2 W-3` — หัวหน้าสายบังคับบัญชายืนยันคำขอสลับกะของลูกทีมตัวเอง** ซึ่ง **ไม่ใช่การอนุมัติเอกสาร** ด้วยเหตุผล 6 ข้อที่ตรวจได้:

| # | เกณฑ์ของสิ่งที่ต้องผ่าน DOA | การสลับกะเป็นอย่างไร |
|---|---|---|
| 1 | มี **เอกสารที่มีเลขที่** ให้เซ็น | **ไม่มี** — คำขอสลับกะมีแค่ `swap_request_id` ซึ่งเป็นรหัสภายใน ไม่ผ่าน Document Configuration (จึงไม่มี `doccfg` ด้วย · §2) |
| 2 | มี **ลายเซ็น** ที่ปรากฏบนเอกสารที่คนถือ | **ไม่มี** — ไม่มี PDF ไม่มีช่องเซ็น (จึงไม่มี `pdfdoc` ด้วย · §3) |
| 3 | มี **วงเงิน / threshold** ที่ทำให้สายยาวขึ้น | **ไม่มี** — การสลับเวรไม่มีมูลค่าเป็นเงิน (**BR-27** ห้ามมีตัวเลขเงินทั้ง feature) · ต่างจาก OT ที่มีเพดานชั่วโมงเป็นจุดตัดจริง |
| 4 | มี **หลายชั้น** ตามตำแหน่ง (หัวหน้า → HR → ผู้บริหาร) | **ไม่มี** — ชั้นเดียว และเป็น **หัวหน้าโดยตรงของผู้ขอเสมอ** (`BR-23`) · ถ้าจะต้องยืนยันสองฝ่าย (กรณีคนละหัวหน้า) จะกลายเป็นสายอนุมัติทันที ซึ่ง **OQ-R11 ตัดสินไว้ว่าไม่ทำ** |
| 5 | ต้องการ **การมอบฉันทะ / หมดอายุ / SoD** ของทะเบียนกลาง | **ไม่ต้องการ** — ถ้าหัวหน้าไม่ว่าง คำขอ **หมดอายุเมื่อถึงวันของกะ** (`W-6` · `BR-29`) แล้วตารางคงเดิม ซึ่งเป็นผลลัพธ์ที่ปลอดภัยอยู่แล้ว |
| 6 | ผู้อนุมัติถูก **resolve จากตำแหน่งในทะเบียน** | **ไม่ใช่** — ผู้ยืนยันมาจาก **ขอบเขตการเห็นตามสายบังคับบัญชาที่ Policy Center ให้** (`ENG-ROLESCOPE-01` · ตระกูลเดียวกับ Attendance `BR-22`) — เป็นการใช้สิทธิ์ที่มีอยู่แล้ว ไม่ใช่การเดินสายอนุมัติ |

**การเผยแพร่ตาราง (`T-3`) ก็ไม่ใช่การอนุมัติเช่นกัน** — เป็นการที่ผู้จัดตารางประกาศงานของตัวเองให้ทีมเห็น (สิทธิ์จาก Policy Center) ไม่ใช่การขออนุมัติจากใคร

**ผลพลอยได้ที่สำคัญ (ต้องบังคับที่ S2–S6):**
- **ไม่มี DOA → `CSQ_BRIEF.md` ห้ามประกาศท่อ DC ระดับเอกสารเด็ดขาด** — ไม่ใช่แค่ "ไม่ประกาศเพราะ DOA เจ้าของ" แต่ **ไม่มีอะไรให้ประกาศตั้งแต่ต้น** (register จะ reject **422**)
- **ไม่มี DOA → `NTF_BRIEF.md` ไม่มี `doa_pending` / `doa_result` / `doa_escalate` ให้ตัดออก** — ต่างจากพี่น้อง Leave/OT ในเวฟเดียวกันที่ต้องระวังการประกาศซ้ำ
- **HTML (S2) ห้ามมี slot picker เลือกผู้อนุมัติ ห้ามมีแถบสายอนุมัติ ห้ามมี tab ลายเซ็น** — ถ้าเผลอลอกมาจาก Leave/OT ที่เพิ่งเสร็จ = **governance invariant พัง** (สายอนุมัติที่ไม่ได้มาจาก `GET /doa/resolve`)
- ถ้าอนาคตธุรกิจต้องการให้การสลับกะต้องผ่านสายอนุมัติจริง → **ต้องกลับมาออก `DOA_BRIEF` ใหม่ ห้ามเขียนสายเองในตัว feature** (DOA iron rule)

## §2 📄 DOCCFG (เลขรัน + สำเนา) — **ไม่ต้อง** และนี่คือเหตุผล

**ตารางกะไม่ใช่เอกสารที่คนถือ** — ไม่มีใครยื่นตารางกะ ไม่มีใครอ้างเลขที่ตารางกะข้ามระบบ ไม่มีระเบียบให้เก็บสำเนา

| สิ่งที่ Document Configuration มีไว้ให้ | feature นี้ใช้หรือไม่ |
|---|---|
| **เลขรันแบบ `XX-YYYY-NNNN` ที่ `ENG-DOC-NUM.next()` ออกให้** (immutable · ไม่ reuse · reset ตามรอบ) | **ไม่ใช้** — `roster_version_id` และ `swap_request_id` เป็น **uuid ภายในของ feature** ที่ไม่มีความหมายกับคนนอก และไม่ต้องเรียงลำดับตามปี |
| **นโยบายสำเนา/snapshot ที่ `ENG-DOC-STORE.store()`** | **ไม่ใช้** — การเก็บย้อนหลังของ feature นี้คือ **ห่วงโซ่เวอร์ชัน `supersedes`/`superseded_by`** (`BR-15`) ซึ่งเป็นโครงสร้างข้อมูลของ feature เอง ไม่ใช่สำเนาเอกสารที่ต้องเก็บตามระเบียบ |

**เส้นแบ่งที่ชัด:** พี่น้องในเวฟเดียวกัน — **ใบลา (`LV-YYYY-NNNN`)** และ **ใบ OT (`OT-YYYY-NNNN`)** — เป็นเอกสารที่พนักงานยื่นและถือไว้เป็นหลักฐาน จึงต้องมี `doccfg` · **ตารางกะเป็นแผนงานของทีม ไม่ใช่หลักฐานของบุคคล**

*(ถ้าองค์กรของลูกค้ามีระเบียบว่า "ตารางเวรต้องมีเลขที่และเก็บสำเนา" → ต้องกลับมาออก `DOCCFG_BRIEF` ใหม่ · **ห้าม feature สร้างรูปแบบเลขเอง** ตามกติกาเหล็กของ Document Configuration)*

## §3 🖨 PDF DOC (thai-doc-pdf-generator) — **ไม่ต้อง** และนี่คือเหตุผล

**ไม่มีแบบฟอร์มทางการที่ต้องพิมพ์ · ลงนาม · หรือยื่นให้ใคร**

- ไม่มี **ช่องลายเซ็น** — ไม่มีผู้ขอ/ผู้อนุมัติ/ฝ่ายบุคคลต้องเซ็นอะไร (ต่อเนื่องจาก §1: ไม่มีการอนุมัติ)
- ไม่มี **เลขที่เอกสาร** ให้พิมพ์บนหัวกระดาษ (ต่อเนื่องจาก §2)
- ไม่ใช่ **เอกสารภาษี** — ไม่ต้องมีเลขผู้เสียภาษี/สาขา
- **การพิมพ์ตารางออกมาติดบอร์ดคือการพิมพ์หน้าจอ** (ความสามารถของเบราว์เซอร์) **ไม่ใช่การออกเอกสารของระบบ** — และ `S-46 · FN-56` ประกาศไว้แล้วว่า **"พิมพ์/ส่งออกตารางเป็นเอกสารทางการ" = ไม่รองรับ**
- `STANDARD_BASELINE §3` ตรวจแล้วว่า **ไม่มีค่ายไหนใน 3 ค่ายมาตรฐาน (Odoo · D365 · SAP) ที่ทำตารางกะเป็นเอกสารมีเลข+ลายเซ็น** — ทุกค่ายเผยแพร่เป็นหน้าจอ/แอปมือถือ + แจ้งเตือน

*(ถ้าพบภายหลังว่าลูกค้าต้องการ "ใบตารางเวรลงนาม" → **ยก OQ ให้ Strike เคาะ ห้ามเพิ่มท่อเอง** ตามที่ `LANE_BRIEF §Declarations` สั่งไว้)*

## §4 ท่อ 7C ที่ **ไม่ประกาศ** ภายใน `CSQ_BRIEF.md` (สรุปย่อ · รายละเอียดเต็มอยู่ `CSQ_BRIEF.md §3`)

| ท่อ | สถานะ | เหตุผลย่อ |
|---|---|---|
| **OC** | ❌ **ห้าม** | มาจาก Operation Process (`sow.*`) — feature นี้ไม่สร้างงาน OP · **422** |
| **DC ระดับเอกสาร** | ❌ **ห้าม** | มาจาก DOA — **และ feature นี้ไม่มี DOA เลย จึงไม่มีอะไรให้ประกาศตั้งแต่ต้น** · **422** |
| **SC** | ❌ **ห้าม** | สงวนไว้ (OQ-C3) · `trigger=false` เสมอ |
| **DC (terminal decision)** | ⬜ ไม่ประกาศ | ไม่มี Continue/Adjust/Hold/Stop/Complete — การยืนยันคำขอสลับกะคือการจัดการตารางของหัวหน้า |
| **FC** | ⬜ ไม่ประกาศ | **จุดที่ต่างจาก OT** — การจัดกะยังไม่ผูกพันเงินขององค์กร · ภาระผูกพันเกิดที่ **OT ตอนอนุมัติ** และ **Payroll ตอนปิดรอบ** · ประกาศที่นี่ = สร้างภาระผูกพันที่ไม่มีจริง + นับซ้ำกับ OT |
| **AC** | ⬜ ไม่ประกาศ | ไม่มีรายการทางบัญชี — เกิดที่ Payroll (W4) · scope ตัด "ไม่ทำต้นทุนแรงงาน" |
| **SecC** | ⬜ ไม่ประกาศ | นโยบายกะเป็นของ **HR Configuration** ซึ่งประกาศ SecC ไว้แล้ว (`CSQ-HRCFG` E1–E6) — ประกาศที่นี่ = **นับซ้ำ** · feature นี้ไม่เปลี่ยนสิทธิ์/นโยบายของใคร และไม่มีบัญชีสิทธิ์รายคนเป็นของตัวเอง (ต่างจาก Leave) |

**⭐ EC ที่ประกาศต้องไม่ทับพี่น้อง:** Attendance = **ชั่วโมงจริงในกรอบกะ (`actual`)** · OT = **ชั่วโมงล่วงเวลาที่ยืนยันแล้ว (`actual` + FC)** · **Roster = ชั่วโมง-กะที่วางแผน (`estimated`)** — คนละชั้นเวลาโดยนิยาม แยกด้วย `kind` ได้ตรง ๆ (รายละเอียดเต็ม `CSQ_BRIEF.md §2`)
