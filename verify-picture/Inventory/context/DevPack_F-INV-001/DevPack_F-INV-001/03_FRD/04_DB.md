## §4.3 Relationships

- `T_stock_balance` → `T_product` (soft ref, no cascade), `T_stock_balance` → `T_location` (soft
  ref, no cascade) — deleting a product/location master record must **not** cascade-delete

  pattern used across the CUBE ERP family)

- `T_bp_order` 1—N `T_bp_order_destination`

## §4.5 Field Dictionary Summary (cross-table, Classification column mandatory per R10)

All fields in this feature's owned tables are classified **Internal**, with **no default = Public**
anywhere (R10 compliance). No field in this feature's in-scope surface is **Confidential** or
**Restricted** — see §4.6 for the one conditional exception.

---

## §4.6 Data Classification (R10 — 4-level, mandatory)

**4-level definition (per Sync Read convention):** Public / Internal / Confidential / Restricted.

1. **Public** — none in this feature (internal ERP tool, no public-facing surface)
2. **Internal (default for this feature)** — all fields in §4.2: stock quantities, location codes,
   product references, ADJ log contents, Break/Pack order data. Visible to any authenticated user
   with module access; no additional gate beyond the RBAC roles in `00_OVERVIEW.md §0.4`
3. **Confidential — CONDITIONAL, currently N/A to this pack:** `T_product.cost` (external Item
   Master field, read but not surfaced here) and the derived `on_hand × cost` valuation
   (`.val-box` in the HTML) **would** be Confidential-level financial data if specified as in-scope.
   **This pack does not classify it because it does not specify it as a built surface** — see
   `00_OVERVIEW.md §0.1.4` G-01 and **OQ-INV-06**. If ratified later, this section must be revised
   to add `cost`-adjacent fields as Confidential with `finance`/`auditor`-only enforcement, backed
   by a Security Bible D5 review
4. **Restricted** — none identified in this feature

**Enforcement mapping (for the Internal-level fields that ARE in scope):**
| Layer | Enforcement |
|---|---|
| DB | RLS on `tenant_id`; warehouse row-scoping for `warehouse_staff` enforced at the query layer, not just app logic |
| API | `02_API.md §2.3` — every list/detail endpoint scopes to the caller's tenant + (if `warehouse_staff`) warehouse |
| UI | Conditional render (not just `disabled`) per `00_OVERVIEW.md §0.4` |
| Audit | `T_stock_adjustment_log`/`T_stock_movement` capture every mutation, append-only |

## §4.7 Append-Only Enforcement Detail (OB-11)

`T_stock_adjustment_log`, `T_stock_adjustment_log_line`, and the `adjustment`/`break`/`pack`
movement types in `T_stock_movement` must have **no UPDATE or DELETE grant** for any application
role, enforced at the database permission level (not merely "the endpoint doesn't exist"). This is
the direct DB-layer expression of OB-11 and should be verified in a migration/permissions review,
not left to application-code discipline alone.
