# Production Logic Review Playbook — F-TMP-005

## 1. เป้าหมายของรอบตรวจนี้

ตรวจระบบจริงหลังขึ้น Production โดยยึด FRD เป็นเกณฑ์หลัก และเน้นความเสี่ยงที่การทดสอบ UI/prototype มักไม่พบ ได้แก่ สิทธิ์ การเปลี่ยนสถานะ สายอนุมัติ เลขเอกสาร การบันทึกซ้ำ ข้อมูลชนกัน PDF/CSV/ไฟล์แนบ การแจ้งเตือน และ audit trail

รอบนี้ไม่ใช่การรับรอง layout ซ้ำ และยังไม่ควรออก Feature Check Report ว่า “ผ่าน” จนกว่าจะมีผลจริงพร้อมหลักฐาน

## 2. เอกสารอ้างอิงและข้อจำกัดที่ต้องรู้

- Source หลัก: FRD `00_OVERVIEW`, `02_API`, `03_LOGIC`, `04_DB`, `05_RULES`, `06_TESTS`, `07_LOCKED_DECISIONS`
- Source เสริม: DOA, DOCCFG, NTF, MDOC declarations และ print spec
- ชุด test เดิม 31 เคสเขียนสำหรับ prototype `feature.html`; ไม่ถือเป็นหลักฐานของ production backend โดยอัตโนมัติ
- มติ 11 ข้อเป็น `AI-DEFAULT` และเอกสารระบุว่ารอลูกค้ายืนยัน (OQ-02)
- จุดที่ต้องยืนยันกับ BA/PM ก่อนสรุป defect:
  - role จริงของ `role-line-manager` และ `role-gm`
  - สายและจำนวนขั้น DOA ที่เปิดใช้จริง
  - การรองรับเงื่อนไขเกิน 20 แถวใน PDF
  - การเชื่อม DOA/MDOC ใน production เพราะ declaration เดิมเคยระบุ `wire_status: pending` / `doa: pending`
- หากระบบใช้ชื่อสถานะ `pending_approval` ภายใน แต่ UI/FRD ใช้ `pending` ให้ตัดสินจากพฤติกรรม ไม่ตัดเป็น bug จากชื่อภายในเพียงอย่างเดียว

## 3. วิธีเตรียมทดสอบอย่างปลอดภัยบน Production

ใช้ข้อมูลทดสอบที่ระบุชัด เช่นชื่อโครงการขึ้นต้น `[REVIEW-YYYYMMDD]` และขออนุญาต PM/Owner ก่อนสร้างข้อมูลจริง ห้ามใช้ข้อมูลลูกค้าจริงหรือข้อมูลการลงทุนจริง

ต้องมีอย่างน้อย 5 บัญชี:

1. Maker A — ผู้จัดทำ
2. Maker B — ผู้จัดทำคนอื่น
3. Approver Step 1 — ผู้ตรวจสอบ
4. Approver Step 2 — ผู้อนุมัติ
5. BDM Admin

ถ้าจะตรวจ isolation ให้ครบ ต้องมีบัญชีคนละ tenant/company เพิ่มอีก 1 บัญชี หากไม่มี ให้ลงว่า “ไม่ได้ตรวจ cross-tenant” ห้ามสรุปว่าผ่าน

หลักฐานต่อเคสควรมี: เวลา, ผู้ใช้, เลขเอกสาร, input สำคัญ, screenshot ก่อน/หลัง, expected/actual, network/error code ถ้าดูได้ และผลกระทบ

## 4. ชุดข้อมูลหลัก

### DATA-A — Happy path

- วงเงิน `1,500,000.00`
- กรอกหัวข้อบังคับ 7 หัวข้อ และหัวข้อเสริมบางส่วน
- เงื่อนไข 3 แถว: ยังไม่เริ่ม, กำลังดำเนินการ, แล้วเสร็จ
- มีไฟล์แนบที่ไม่อ่อนไหว 1 ไฟล์

### DATA-B — Boundary

- วงเงิน: `0`, `0.01`, `9999999999999999.99`, `-0.01`, ตัวอักษร, ตัวเลขมี comma, ทศนิยมเกิน 2 ตำแหน่ง
- ข้อความยาว, emoji, อักขระพิเศษ, เว้นวรรคอย่างเดียว
- เงื่อนไข: 0, 1, 12, 20 และ 21 แถว

### DATA-C — Conflict

- เปิดเอกสารเดียวกัน 2 tab/2 browser
- เปิดหน้าตัดสินเอกสารเดียวกันด้วย session ของผู้อนุมัติซ้ำ

## 6. P1 — ควรตรวจเพื่อเก็บตก business logic

| ID | สิ่งที่ทำ | ผลที่ต้องได้ |
|---|---|---|
| P1-01 | ทดสอบวงเงิน 0, 0.01, comma และทศนิยมเกิน 2 ตำแหน่ง | 0 และค่าบวกใช้ได้; การ parse/round ต้องสม่ำเสมอระหว่างจอ, DOA, CSV, PDF |
| P1-02 | ทดสอบค่าสูงสุดของ numeric(18,2) และเกินขอบเขต | ค่าที่รองรับบันทึกได้; ค่าเกินถูกปฏิเสธอย่างควบคุมได้ ไม่เป็น 500 |
| P1-03 | ใช้ข้อความยาว/อักขระพิเศษ/สูตร CSV เช่น `=1+1` | ไม่พัง ไม่เกิด script injection และ CSV ไม่เปิดช่อง formula injection |
| P1-04 | เปลี่ยน config สถานะเงื่อนไข (ใน env ที่อนุญาต) | ตัวเลือกมาจาก config; การนับ done ใช้ key ถูกต้อง ไม่ผูก label ไทยแบบ hardcode |
| P1-05 | เปลี่ยน DOA ระหว่างเอกสาร pending | ใบเดิมใช้ snapshot เดิม; ใบส่งใหม่ใช้ config ใหม่ |
| P1-06 | DOA 1, 2, 6 ขั้น | flow และ PDF มีแถวผู้จัดทำ + N ขั้นจริง ไม่มี fix 2 ขั้น |
| P1-07 | เงื่อนไข 12, 20, 21 แถว + ข้อความยาว | PDF อ่านได้, header ตารางซ้ำ, แถวไม่ถูกตัด; 21 แถวให้บันทึก actual page count เพื่อปิด OQ-07 |
| P1-08 | ไม่มีเงื่อนไขเลย | ส่งได้; หน้า detail แสดง empty state; PDF มี 6 แถวว่าง |
| P1-09 | filter ค้าง/ครบ/ไม่มี + search ทุก field ที่ FRD ระบุ + pagination | count, rows และ CSV ตรงกับ filter เดียวกัน ไม่มีรายการนอกสิทธิ์ |
| P1-10 | แนบไฟล์ชนิดถูก/ผิด, ใหญ่เกิน, ชื่อซ้ำ, ลบ, download ด้วยคนไม่มีสิทธิ์ | validation และ ACL ถูก; ไม่เกิดไฟล์ orphan หรือรั่ว |
| P1-11 | ปิด doc_type IVM แล้วลองสร้าง | ปุ่มสร้างปิด/มีคำอธิบาย และ server ตอบ 409 `DOC_TYPE_INACTIVE` |
| P1-12 | API/เครือข่ายล้มระหว่าง save/submit/decide | แจ้ง error, สถานะบนจอไม่หลอกว่าสำเร็จ, retry ปลอดภัย |
| P1-13 | ตรวจว่า approved ไม่สร้างงบ/โครงการหรือส่งต่อระบบอื่น | ไม่มี downstream record/event นอกที่ FRD อนุญาต |
| P1-14 | ตรวจปี พ.ศ./ค.ศ. ใกล้สิ้นปีและ timezone | เลขเอกสาร, doc date, due date, audit time และ PDF ไม่เหลื่อมวัน/ปี |

## 7. จุดที่ไม่ควรตัดเป็น Bug ทันที

- UI/layout ที่ PM/BA ยืนยันปิดแล้ว เว้นแต่ทำให้ logic ผิดหรือใช้งานไม่ได้
- เลขเอกสารมี gap เพราะ DOCCFG ระบุ `no-gap = false`
- เงื่อนไขค้างแล้วส่งได้ เพราะ FRD ตั้งใจให้ “เตือน ไม่บล็อก”
- ไม่มีเลขโครงการหรือการเชื่อม FM-BDM-01/03/06 เพราะถูก defer ไว้
- ไม่มีฟังก์ชันทำซ้ำเอกสาร เพราะ DEC-11 ระบุไม่รองรับ
- approved ไม่แก้ไขและไม่ยกเลิก เป็นกฎธุรกิจ ไม่ใช่ข้อจำกัดที่ต้องแก้

## 8. จุดที่ควรยกระดับทันที

- Critical: ข้ามสิทธิ์/ข้าม tenant/ข้ามขั้นอนุมัติ, ผู้จัดทำอนุมัติใบตนเอง, ข้อมูลหาย/ถูกทับ, PDF หรือไฟล์แนบรั่ว
- High: เงิน/สถานะ/ผู้อนุมัติ/เลขเอกสาร/PDF final ผิด, เอกสารหรือ decision ซ้ำ, approved ยังแก้ได้
- Medium: audit/notification/filter/CSV ผิดแต่ core flow ยังทำงานและมีทางเลี่ยง
- Low: ข้อความ/ตำแหน่ง/ความเรียบร้อยที่ไม่กระทบ logic
