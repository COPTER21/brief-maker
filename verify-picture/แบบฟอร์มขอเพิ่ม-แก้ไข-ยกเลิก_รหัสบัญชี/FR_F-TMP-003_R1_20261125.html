ส่วนที่ไม่ได้ตรวจ อยู่นอกความรับผิดชอบของรายงานฉบับนี้

ตรวจแล้ว

  • ทดลองสร้างคำขอ บันทึกร่าง และส่งอนุมัติ
  • ตรวจ UX/UI ของ Create และ Edit drawer จากการเปิดหน้าที่ผู้ตรวจรายงาน
  • ผู้ตรวจระบุว่า UI/UX ส่วนอื่นที่ได้ลองใช้งานโอเค

ไม่ได้ตรวจ

  • Update และ Delete/ยกเลิกเอกสาร — ผู้ตรวจยังทำรายการไม่ได้ ควรยืนยันว่าคำว่า Delete หมายถึงยกเลิกเอกสารตาม FRD
  • View drawer ทั้ง 4 แท็บบนระบบจริง — ยังสร้างรายการเพื่อเปิดตรวจไม่ได้ ภาพ tk03 เป็น HTML ต้นแบบ
  • Validation ราย step และรายปุ่ม — ยังไม่มีข้อมูลว่าช่องใดถูกเว้นหรือปุ่มใดปล่อยข้อมูลผิดผ่าน
  • สิทธิ์, DOA, ประวัติ, PDF ที่จัดเก็บ, notification และ COA — ยังไม่มีผลตรวจรองรับในรอบนี้

1Logic — ทำงานถูกตามกฎธุรกิจ

เทียบผลจริงกับ FRD / Test Case — ข้อที่ไม่ผ่านต้องผูกกับ Bug ในข้อ 4

#กฎ / Scenarioผลที่คาดหวังผลจริงผลอ้างอิง
L-01สร้างคำขอและบันทึกร่างบันทึกได้เมื่อข้อมูลผ่านกฎ และได้เลข ACR ตอนบันทึกครั้งแรกAPI ตอบ INTERNAL «เกิดข้อผิดพลาดภายในระบบ» ผู้ตรวจสร้างรายการไม่สำเร็จไม่ผ่านBUG-01
L-02ส่งอนุมัติเมื่อข้อมูลและผู้พิจารณาครบ ใบเข้าสถานะรออนุมัติขั้นแรกผู้ตรวจรายงานว่ากดส่งอนุมัติแล้วพบ INTERNAL เช่นกัน จุดที่ล้มใน flow ยังต้องตรวจจาก logไม่ผ่านBUG-01
L-03ตรวจข้อมูลบังคับและชื่อบัญชีซ้ำก่อนเดินหน้าหรือบันทึกถัดไปตรวจขั้นที่กำลังจะออก บันทึกร่างและบันทึกพร้อมส่งตรวจข้อมูลบังคับทุกขั้นที่เกี่ยวข้อง ส่งอนุมัติตรวจผู้พิจารณาด้วยผู้ตรวจกำชับให้ตรวจครบ ยังไม่มีผลรายช่อง/ปุ่มสำหรับตัดสินไม่ได้ตรวจAC-02–05, AC-07 · VR-01–07
L-04เปลี่ยนประเภทคำขอแล้วบันทึกเฉพาะส่วนที่เลือกข้อมูลประเภทเดิมถูกล้าง และ PDF ติ๊กเฉพาะประเภทสุดท้าย—ไม่ได้ตรวจAC-06
L-05แก้ไขร่างเจ้าของแก้ร่างได้โดยใช้เลขเดิม—ไม่ได้ตรวจAPI-04 · BR-08 · TC-D05
L-06พิจารณาตามลำดับผ่านขั้นแรกแล้วไปขั้นถัดไป ผ่านครบแล้วเป็นอนุมัติแล้วรอบันทึก—ไม่ได้ตรวจAC-08
L-07ตีกลับเป็นร่างบังคับเหตุผล กลับร่างเลขเดิม แสดงเหตุผล และเก็บประวัติ—ไม่ได้ตรวจAC-09
L-08ฝ่ายบัญชีบันทึกเข้าระบบเฉพาะ admin บัญชีทำได้หลังอนุมัติ วันที่อยู่ในช่วงที่กำหนด PDF แสดงผู้บันทึกและวันที่—ไม่ได้ตรวจAC-10 · BR-11
L-09พิมพ์เอกสารและแสดงช่องลงนามตาม DOAPDF FM-ACC-01 ตรงกับข้อมูลใบ ลายเซ็นตามสายจริง—ไม่ได้ตรวจAC-11, AC-14 · EC-08
L-10ยกเลิกเอกสารเจ้าของหรือ admin ยกเลิกได้เฉพาะร่าง/รออนุมัติ และต้องมีเหตุผล—ไม่ได้ตรวจAC-12 · BR-09
L-11รายการและการเข้าถึงตามสิทธิ์รายการ รายละเอียด และตัวกรองแสดงข้อมูลตามบทบาท—ไม่ได้ตรวจAC-13 · TC-D01–08
L-12ปิดชนิดเอกสารและส่งออก CSVปิด ACR แล้วสร้างใหม่ไม่ได้ และ CSV ตรงกับตัวกรองและสิทธิ์—ไม่ได้ตรวจAC-15
L-13ผลข้ามโมดูลแจ้งผู้รับถูกคน เก็บ approved_final และไม่ส่ง event ไปแก้ COA—ไม่ได้ตรวจXT-01–03

U-03ตาราง 1 ช่อง = 1 บรรทัด ไม่ซ้อนข้อมูลผ่าน——

มองจากผู้ใช้จริง · "ผ่าน" = ผู้ตรวจลองใช้แล้วไม่ติดขัด

#หัวข้อตรวจผลหมายเหตุหลักฐาน
X-01ทำงานหลักจบได้เองโดยไม่ต้องเดาไม่ผ่านการสร้างคำขอจบไม่ได้ในรอบตรวจนี้ ทั้งบันทึกร่างและส่งอนุมัติพบ INTERNAL ดู BUG-01—
X-02กดแล้วระบบบอกผลทุกครั้ง (แจ้งเตือน / สถานะเปลี่ยน)ผ่าน——
X-03ข้อความ error บอกว่าผิดที่ไหน แก้ยังไงมีข้อสังเกตAPI ตอบข้อความทั่วไป ควรตรวจเพิ่มว่าหน้าจอแสดงผลอย่างไร และกรณีข้อมูลไม่ครบพากลับไปยังช่องที่ต้องแก้ได้หรือไม่—
X-04ถามยืนยันก่อนลบ / ยกเลิก / สิ่งที่ย้อนไม่ได้ไม่ได้ตรวจยังไม่ได้ทดลอง Delete/ยกเลิก—

X-06ความเร็วตอบสนองรับได้ผ่าน——
X-07View drawer ทั้ง 4 แท็บไม่ได้ตรวจหลังปลดตัวบล็อก ให้เปิดใบที่มีสิทธิ์ สลับแท็บ เลื่อนอ่าน และตรวจ preview/ดาวน์โหลดบนระบบจริง—

4Bug ที่พบ

เรียงจากรุนแรงมากไปน้อย · ทำซ้ำได้ตามขั้นตอน

BUG-01บันทึกร่างหรือส่งอนุมัติแล้ว API ตอบ INTERNALCriticalรอแก้
ขั้นตอนทำซ้ำ
  1. เปิด Create drawer และกรอกคำขอ
  2. ลองบันทึกแบบร่าง และลองเส้นทางส่งอนุมัติแยกกัน
  3. ตรวจ response ของแต่ละรายการ
ผลที่ควรเป็นข้อมูลถูกต้องบันทึกได้และดำเนินการต่อได้ตามปุ่ม ข้อมูลผิดได้รับ validation ที่ตรงกับสาเหตุ
ผลที่เกิดจริง{"code":"INTERNAL","message":"เกิดข้อผิดพลาดภายในระบบ"} ผู้ตรวจสร้างรายการไม่สำเร็จ ยังไม่มี payload, HTTP status, เวลา หรือ request ID สำหรับระบุจุดที่ล้ม
BUG-02Create/Edit drawer มี layout ต่างจากแบบอ้างอิงLowรอแก้
ขั้นตอนทำซ้ำ
  1. เปิด Create drawer และหน้า Edit drawer ที่เข้าถึงได้
  2. เทียบทีละขั้นกับ HTML ต้นแบบใน context
ผลที่ควรเป็นการจัดกลุ่มข้อมูล การจัดแนว และปุ่มของ wizard ใช้ได้ตรงตามแบบอ้างอิง
ผลที่เกิดจริงผู้ตรวจพบว่า UX/UI ต่างจากแบบและ layout บางส่วนไม่เรียบร้อย ยังไม่มีภาพจากระบบจริงหรือพิกัดส่วนที่ต่าง

5ข้อเสนอแนะ (ไม่ใช่ Bug)

ทำงานถูกตาม spec แล้ว แต่ควรปรับให้ดีขึ้น — ส่งต่อเป็น Enhancement ถ้าทีมเห็นด้วย

#ข้อเสนอเหตุผล
S-01ตรวจ BUG-01 จาก log และข้อมูลคำขอตอนเกิดเหตุเก็บเวลา, action, HTTP status และ request ID ของแต่ละปุ่ม พร้อมข้อมูลทดสอบที่ปิดข้อมูลส่วนบุคคล แล้วเช็กว่ามีใบหรือสถานะเปลี่ยนค้างหรือไม่ก่อนลองซ้ำ
S-02ทดสอบ validation ของ ถัดไป / บันทึกแบบร่าง / บันทึกและส่งอนุมัติ แยกทีละปุ่มลองเว้นช่องบังคับของเพิ่ม/แก้ไข/ยกเลิก ใส่ชื่อซ้ำ และเว้นผู้พิจารณาก่อนส่ง จดว่าระบบบล็อกและชี้ช่องแก้ไขได้ตรงหรือไม่
S-03ตรวจ Edit, ยกเลิก และ View ทั้งสี่แท็บบนใบที่มีสิทธิ์ใช้ใบที่เตรียมไว้ใน UAT เพื่อตรวจคู่ขนานได้ ถ่ายภาพจอจริงคู่กับภาพ tk03 และจดสถานะกับบทบาทก่อนเทียบ

6การรับรองผลตรวจ

ข้าพเจ้าได้ตรวจฟีเจอร์นี้ตามขอบเขตในข้อ 0 บน environment และ build ที่ระบุ ผลทั้งหมดมาจากการทดสอบจริง ข้อที่ระบุว่า "ผ่าน" คือได้ตรวจแล้วไม่พบปัญหา ส่วนที่ "ไม่ได้ตรวจ" อยู่นอกความรับผิดชอบของรายงานฉบับนี้
