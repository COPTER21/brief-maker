# Production Logic Review Plan — F-TMP-001 แบบประเมินความพึงพอใจลูกค้า

วันที่จัดทำ: 2026-11-03  
วัตถุประสงค์: ตรวจเก็บตกด้าน Logic, การทำงาน, สิทธิ์, ข้อมูล และ integration หลังฟีเจอร์ขึ้น Production แล้ว โดยไม่ตรวจ layout ซ้ำ

## 1. ข้อสรุปก่อนเริ่ม

ให้ใช้ FRD เป็น **เกณฑ์ตัดสินว่าถูกหรือผิด** ตามที่ PM/BA กำหนด แต่ไม่ควรอ่านเฉพาะหน้าจอหรือ Acceptance Criteria เท่านั้น เพราะกฎสำคัญกระจายอยู่ใน:

- `03_LOGIC.md` — จุดออกเลข, ส่ง, ยกเลิก, PDF, CSV, notification, attachment
- `05_RULES.md` — business rules, state, permission, validation, edge cases
- `06_TESTS.md` — expected behavior ที่ยืนยันได้ด้วยการทดสอบ
- `02_API.md` และ `04_DB.md` — idempotency, optimistic lock, audit, snapshot, RLS
- Governance declaration — การตั้งค่าเลขเอกสารและ event แจ้งเตือน

สิ่งที่ไม่ควรใช้เป็นหลักตัดสินรอบนี้คือ prototype HTML เพราะเป็นต้นทาง UI และ test case เดิมระบุชัดว่ารันกับ prototype ไม่ใช่หลักฐานว่า Production backend/integration ผ่านแล้ว

## 2. ข้อควรระวังจากเอกสาร

1. FRD เป็น v1.0 สถานะ “Ready for Dev” ไม่ใช่ As-built Production specification
2. เอกสารเดิมบอกว่า e2e บน browser ยังไม่รัน และไม่มี `e2e_standard report`
3. UAT ฉบับคนเก็บ 43 จาก 52 เคส โดยตัดเคสระบบ/API 9 เคสออก ได้แก่ service failure, direct-route permission, server PDF, doc type inactive, concurrent update, header snapshot, notification, CRM non-emission
4. OQ-02/03/04 ถูกระบุว่าต้องปิดก่อน UAT/register แต่ DevPack นี้ไม่มีหลักฐานคำตอบสุดท้าย
5. มติหลายข้อเป็น `AI-DEFAULT` จึงต้องขอ PM/BA ยืนยันว่า Production ใช้มติเหล่านี้จริงก่อนแจ้งเป็น bug:
   - ไม่มีสายอนุมัติ
   - ผู้จัดการฝ่ายขายเห็นทุกใบและยกเลิกได้
   - ผู้ประเมินคือผู้บันทึก
   - ส่งแล้วแก้ไม่ได้
   - ออกเลขตั้งแต่บันทึกครั้งแรก
   - แจ้งเตือนผู้จัดการฝ่ายขายเมื่อส่ง

## 3. วิธีจัดประเภทสิ่งที่พบ

| สิ่งที่พบ | จัดเป็น |
|---|---|
| ขัดกับ BR/VR/State/Permission ที่ PM/BA ยืนยันแล้ว | Bug |
| ขัดกับข้อที่ยังเป็น AI-DEFAULT หรือ OQ ยังไม่ปิด | Business clarification ก่อน ยังไม่ฟันธงเป็น bug |
| ทำงานตาม FRD แต่ production config ตั้งไม่ตรง | Configuration issue |
| ทำงานถูก แต่ใช้งานไม่สะดวก | Suggestion ไม่ใช่ bug |
| เอกสาร FRD สองส่วนขัดกัน | Spec conflict ส่งให้ BA ตัดสินก่อน |

## 4. ความสำคัญในการตรวจ

### P0 — ต้องตรวจแน่นอน

- สิทธิ์และการมองเห็นข้อมูลข้ามผู้ใช้/ข้าม tenant
- สถานะ `draft → submitted → cancelled`
- คะแนน 9 หัวข้อต้องครบและเป็น 1–5 ก่อนส่ง
- ส่งแล้วแก้ไม่ได้ และ action ต้องตรงตาม role
- เลขเอกสารไม่ซ้ำเมื่อกดซ้ำ/เน็ตช้า
- PDF/CSV ต้องเป็นข้อมูลของใบเดียวกันและไม่รั่วข้อมูลที่ไม่มีสิทธิ์
- ทุก write ต้องมี audit และไม่มี hard delete

### P1 — ควรตรวจ

- Customer master autofill และกรณีพิมพ์ร้านเอง
- ไฟล์แนบ ชนิด/ขนาด/สิทธิ์
- notification ถึงผู้จัดการฝ่ายขาย
- filter, sort, pagination และ CSV ตาม filter
- header snapshot เมื่อชื่อ Organization เปลี่ยน
- concurrent submit/cancel หรือเปิดแก้พร้อมกันสองหน้าต่าง

### P2 — ตรวจเมื่อมี environment รองรับ

- ปิด doc type CSE แล้วสร้างไม่ได้
- service/downstream ขัดข้องแล้วข้อมูลหลักไม่เสีย
- ยืนยันว่าไม่ยิงคะแนนไป CRM
- multi-tenant RLS ด้วย tenant อื่น

## 5. ข้อมูลและบัญชีที่ต้องเตรียม

| ชุด | ใช้ทำอะไร |
|---|---|
| Owner A — พนักงานขาย | สร้าง/แก้/ส่ง/ยกเลิกใบของตน |
| Owner B — พนักงานขายอีกคน | ตรวจว่าไม่เห็นและแก้ใบของ A ไม่ได้ |
| Manager — `role-mgr-sales` | เห็นทุกใบ, ยกเลิกได้, แต่แก้/ส่งแทน owner ไม่ได้ |
| Tenant B (ถ้ามี UAT) | ตรวจ RLS ไม่รั่วข้ามบริษัท |
| ร้านใน Customer master | ตรวจ autofill และ customer linkage |
| ชื่อร้านที่ไม่มีใน master | ตรวจ manual store และ `customer_id` ว่าง |
| ไฟล์ PDF/JPG/PNG ต่ำกว่า 10 MB | positive attachment |
| EXE และไฟล์มากกว่า 10 MB | negative attachment |

ถ้าจำเป็นต้องทดสอบบน Production ให้ใช้ชื่อร้านขึ้นต้น `TEST-REVIEW-YYYYMMDD`, ห้ามใช้ข้อมูลลูกค้าจริงโดยไม่จำเป็น และยกเลิกเอกสารทดสอบเมื่อจบ ห้ามปิด doc type, เปลี่ยนชื่อ Organization หรือทดสอบ tenant/config โดยตรงบน Production

## 6. ชุดทดสอบแนะนำตามลำดับ

บันทึกผลแต่ละข้อเป็น `PASS / FAIL / BLOCKED / NOT RUN` พร้อมเลขเอกสาร, ผู้ใช้, เวลา และหลักฐาน

### Flow A — สร้างร่างขั้นต่ำและเลขเอกสาร

- [ ] A01 Owner A สร้างโดยใส่เฉพาะชื่อร้าน แล้วกด “บันทึกแบบร่าง”
  - คาด: บันทึกได้, สถานะ `ร่าง`, ได้เลข CSE ทันที
  - ตรวจเพิ่ม: เลขรูปแบบตาม config เช่น `CSE-{YYYY}-{run:4}` และไม่เปลี่ยนเมื่อแก้ไข
- [ ] A02 กด Save ซ้ำ/ดับเบิลคลิก/จำลองเน็ตช้า
  - คาด: ได้เอกสารเดียวและเลขเดียว ไม่เกิด duplicate
- [ ] A03 สร้างร่างโดยไม่มีชื่อร้าน
  - คาด: บล็อกด้วย “กรุณาระบุชื่อห้าง/ร้านค้า”
- [ ] A04 ตรวจประวัติหลังสร้างและแก้ร่าง
  - คาด: มี actor และเวลา, ประวัติเพิ่มต่อท้าย ไม่ทับรายการเดิม

### Flow B — Customer master และค่าจาก Organization

- [ ] B01 เลือกร้านจากทะเบียนลูกค้า
  - คาด: ชื่อร้านเติมถูก และประเภทธุรกิจเติมเฉพาะเมื่อช่องยังว่าง
- [ ] B02 เลือกประเภทธุรกิจไว้ก่อน แล้วเลือกร้านที่มีค่าอีกแบบ
  - คาด: ค่าที่ผู้ใช้เลือกไว้ไม่ถูกเขียนทับโดยไม่แจ้ง
- [ ] B03 พิมพ์ชื่อร้านที่ไม่มีในทะเบียน
  - คาด: บันทึกได้โดยไม่ผูก customer และเปิดกลับมายังเห็นชื่อเดิม
- [ ] B04 ตรวจชื่อบริษัทในหน้ารายละเอียดกับ PDF ทั้งหัวเรื่องและข้อ 2
  - คาด: ตรงกันทั้งหมดและมาจาก `Organization.legal_name`

### Flow C — Validation คะแนนและค่าตัวเลือก

- [ ] C01 เลือกประเภทธุรกิจสลับไปมา
  - คาด: เลือกได้ครั้งละหนึ่งค่าเท่านั้น
- [ ] C02 เลือกระยะเวลา “3–5 ปี” สำหรับกรณี 3 ปีพอดี
  - คาด: ตรงกฎ FRD ที่ 3 ปีอยู่กลุ่ม 3–5 ปี
- [ ] C03 ให้คะแนนเพียง 8 จาก 9 แล้วกดส่ง
  - คาด: ไม่ส่ง, บอกจำนวนที่ขาด, แถวที่ขาดชัดเจน
- [ ] C04 พยายามส่งคะแนน 0, 6, ทศนิยม หรือค่าที่ดัดแปลงจาก request
  - คาด: backend ปฏิเสธ `422 INVALID_VALUE`; ห้ามเชื่อเฉพาะ validation หน้าเว็บ
- [ ] C05 กรอกข้อเสนอแนะยาว มีภาษาไทย/อังกฤษ/ตัวเลข/อักขระพิเศษ
  - คาด: บันทึกครบ, เปิดกลับไม่เพี้ยน, PDF ไม่ตัดข้อมูลสำคัญ
- [ ] C06 บันทึกร่างทั้งที่คะแนนยังไม่ครบ
  - คาด: ทำได้ เพราะคะแนนบังคับตอนส่ง ไม่ได้บังคับตอนร่าง

### Flow D — ส่งแบบประเมิน

- [ ] D01 เติมทุกช่องครบแล้วกดส่ง
  - คาด: มี confirm, สถานะเป็น `ส่งแล้ว` ทันที, ไม่มีขั้นอนุมัติ, มี `submitted_at`
- [ ] D02 หลังส่งตรวจ action ทั้งหมด
  - คาด: owner แก้ไม่ได้, ไม่มีปุ่มแก้, API แก้ต้องถูกปฏิเสธ, เลขเดิมไม่เปลี่ยน
- [ ] D03 เปิดแท็บลายเซ็น
  - คาด: มีผู้ประเมิน/ผู้บันทึกหนึ่งช่องและข้อความ “ส่งในระบบ” พร้อมวันเวลา ไม่มีภาพลายมือชื่อ
- [ ] D04 ตรวจ audit หลังส่ง
  - คาด: มี action “ส่งแบบประเมิน”, actor และเวลาถูกต้อง
- [ ] D05 refresh, logout/login และเปิดเอกสารเดิม
  - คาด: สถานะและข้อมูลยังเหมือนเดิม ไม่ใช่ state เฉพาะ browser

### Flow E — ยกเลิกและ state machine

- [ ] E01 ยกเลิกร่างโดยไม่ใส่เหตุผล
  - คาด: บล็อก “กรุณาระบุเหตุผล”
- [ ] E02 Owner ยกเลิกร่างโดยใส่เหตุผล
  - คาด: เป็น `ยกเลิก`, เก็บเหตุผลและ audit, ไม่มีปุ่มแก้/ส่ง/ยกเลิกซ้ำ
- [ ] E03 Owner ยกเลิกใบที่ส่งแล้ว
  - คาด: ทำได้ตาม FRD และคงข้อมูลเดิมไว้
- [ ] E04 Manager ยกเลิกใบของ Owner A
  - คาด: ทำได้ แต่ต้องมีเหตุผลและ audit เป็นชื่อ Manager
- [ ] E05 ยกเลิกใบที่ยกเลิกแล้วอีกครั้ง
  - คาด: UI ไม่มี action และ backend ตอบ `409 NOT_CANCELLABLE`
- [ ] E06 ตรวจว่าไม่มีเมนูลบถาวร
  - คาด: ยกเลิกเป็นการเปลี่ยนสถานะ ไม่มี hard delete

### Flow F — Permission และข้อมูลรั่ว

- [ ] F01 Owner A เปิดรายการ
  - คาด: เห็นเฉพาะ draft/submitted/cancelled ของตน ไม่เห็นของ Owner B
- [ ] F02 Owner B ใช้ URL ตรงของใบ Owner A
  - คาด: เปิดไม่ได้และควรได้ `404 NOT_FOUND` ไม่ใช่ข้อความที่เผยว่าเอกสารมีอยู่
- [ ] F03 Owner B พยายามแก้/ส่ง/ยกเลิกใบ Owner A ผ่าน request เดิม
  - คาด: ถูกปฏิเสธ; การซ่อนปุ่มอย่างเดียวไม่ถือว่าผ่าน
- [ ] F04 Manager เปิดรายการ
  - คาด: เห็นทุกใบใน tenant รวมร่างของ Owner A/B
- [ ] F05 Manager เปิดร่างของ Owner A
  - คาด: ดูและยกเลิกได้ แต่แก้หรือส่งแทนไม่ได้
- [ ] F06 ถ้ามี Tenant B ให้ใช้ URL/ID ของ Tenant A
  - คาด: ไม่พบข้อมูลทุกช่องทาง รวม detail, PDF, attachment และ CSV

### Flow G — Concurrent update และ retry

- [ ] G01 เปิดร่างเดียวกันสอง tab แล้วแก้จากทั้งสอง tab
  - คาด: tab ที่ใช้ version เก่าถูกปฏิเสธ `409 STALE`; ห้ามทับข้อมูลเงียบ ๆ
- [ ] G02 tab หนึ่งกดส่ง ขณะอีก tab กดยกเลิก
  - คาด: สำเร็จเพียงหนึ่ง transition อีกคำขอได้ `409 STALE`; สถานะสุดท้ายมีค่าเดียวและ audit ไม่ขัดกัน
- [ ] G03 ส่งคำขอ POST เดิมซ้ำด้วย idempotency key เดิม
  - คาด: ไม่สร้างเหตุการณ์/เลขเอกสาร/notification ซ้ำ

### Flow H — Attachment

- [ ] H01 Owner แนบ PDF/JPG/PNG ต่ำกว่า 10 MB ในร่าง
  - คาด: แนบ/เปิด/ดาวน์โหลดได้และผูกกับใบถูกต้อง
- [ ] H02 แนบ EXE หรือไฟล์มากกว่า 10 MB
  - คาด: ไม่รับและแจ้ง “ไฟล์ไม่ผ่านเงื่อนไข”
- [ ] H03 หลังส่งแล้วลองเพิ่ม/ลบไฟล์
  - คาด: ทำไม่ได้ เพราะ attachment แก้ได้เฉพาะร่างของ owner
- [ ] H04 Owner B และ Tenant B ลองเปิด URL ไฟล์ของ Owner A
  - คาด: ไม่มีสิทธิ์เข้าถึง

### Flow I — PDF

- [ ] I01 PDF ร่าง
  - คาด: มีป้าย “ร่าง”, เลขเอกสาร, ชื่อร้าน, ชื่อบริษัทถูกต้อง และไม่มี `{{...}}` หลง
- [ ] I02 PDF ส่งแล้ว
  - คาด: ไม่มีป้ายร่าง, คะแนนทั้ง 9 ตรงหน้ารายละเอียด, ข้อเสนอแนะครบ, วันเวลาส่งตรง audit
- [ ] I03 PDF ยกเลิก
  - คาด: สถานะ/ข้อมูลไม่ทำให้เข้าใจว่าเป็นใบใช้งานปกติ
- [ ] I04 ข้อเสนอแนะยาวและตัวอักษรไทย
  - คาด: layout dense ตาม FRD, ไม่ล้น/หาย/กลายเป็นสี่เหลี่ยม
- [ ] I05 ผู้ไม่มีสิทธิ์เรียก PDF ด้วย URL ตรง
  - คาด: `404 NOT_FOUND`

### Flow J — List, filter, sort, pagination และ CSV

- [ ] J01 ค้นหาด้วยเลขเอกสาร, ชื่อร้าน และชื่อผู้บันทึก
  - คาด: ผลตรงคำค้นและไม่หลุดสิทธิ์
- [ ] J02 filter สถานะและประเภทธุรกิจร่วมกัน แล้วเปลี่ยนหน้า/จำนวนต่อหน้า
  - คาด: filter คงอยู่, count/pagination ถูกต้อง, ไม่มีรายการซ้ำหรือหาย
- [ ] J03 sort ตามเลข, วันที่, คะแนนรวม
  - คาด: ลำดับถูกต้องรวมกรณี draft ที่คะแนนว่าง
- [ ] J04 export CSV หลังตั้ง filter
  - คาด: เฉพาะรายการตาม filter และสิทธิ์, มี 9 คอลัมน์คะแนน, เปิด Excel ภาษาไทยไม่เพี้ยน (UTF-8 BOM)
- [ ] J05 Owner export CSV
  - คาด: มีเฉพาะใบของตน
- [ ] J06 Manager export CSV
  - คาด: มีทุกใบใน tenant แต่ไม่ข้าม tenant
- [ ] J07 ตรวจ CSV formula injection ด้วยค่าชื่อร้าน/ข้อเสนอแนะขึ้นต้น `=`, `+`, `-`, `@`
  - คาดเชิงความปลอดภัย: เปิด spreadsheet แล้วไม่ execute formula อัตโนมัติ; ถ้า FRD ไม่กำหนด ให้รายงานเป็น security observation

### Flow K — Notification และ downstream

- [ ] K01 Owner ส่งใบสำเร็จ
  - คาด: ผู้รับ `role-mgr-sales` ได้ in-app notification หนึ่งครั้ง มีเลข CSE, ชื่อร้าน, คะแนน overall ถูกต้อง
- [ ] K02 กดส่งซ้ำ/retry
  - คาด: ไม่แจ้งซ้ำ
- [ ] K03 ผู้จัดการปิด preference ของ event นี้
  - คาด: ระบบเคารพ preference เพราะ event ระบุว่าปิดได้

## 7. Business-sense checks ที่ FRD เขียนไม่พอ

รายการนี้ควรตรวจหรืออย่างน้อยถาม PM/BA เพราะมีผลต่อการใช้จริง:

- ถ้าร้านเดียวถูกประเมินหลายครั้งในวันเดียวกัน ระบบยอมให้ซ้ำหรือควรเตือน? FRD ไม่กำหนด
- คะแนน “ความพึงพอใจโดยรวม” เป็นคะแนนที่ผู้ใช้เลือกเอง ไม่ใช่ค่าเฉลี่ย 8 ข้อแรก ใช่หรือไม่?
- ใบยกเลิกควรรวมในรายงาน/CSV และตัวชี้วัดหรือไม่?
- Manager ยกเลิกใบที่ส่งแล้วได้โดยไม่ต้องแจ้ง owner จริงหรือไม่?
- เมื่อ Customer master เปลี่ยนชื่อร้าน ใบเก่าควรตามชื่อใหม่หรือเก็บ snapshot? FRD snapshot เฉพาะ Organization ไม่ได้ระบุ snapshot ร้าน
- Retention ของเอกสารและไฟล์แนบกี่ปี? FRD ยังให้ยืนยันกับ Policy Center
- ข้อเสนอแนะอาจมีข้อมูลส่วนบุคคลหรือข้อมูลร้องเรียน แม้ FRD จัดทั้งหมดเป็น Internal ควรมีข้อจำกัดสิทธิ์/retention เพิ่มหรือไม่?
- การ export CSV จำนวนมากต้องมี limit, timeout หรือ audit การดาวน์โหลดหรือไม่?
- Notification ส่งเฉพาะ Manager ทุกคน หรือ Manager ตามทีม/สาขาของ owner?

คำถามเหล่านี้ไม่ควรถูกตีเป็น bug จนกว่า PM/BA จะตอบ แต่ควรอยู่ใน review report เพราะเป็น production risk

## 8. หลักฐานขั้นต่ำต่อเคส

- Positive flow: เลขเอกสาร + screenshot สถานะสุดท้าย
- Negative flow: ก่อนกด + error ที่เห็น + ยืนยันว่าข้อมูลไม่เปลี่ยน
- Permission: user/role ที่ใช้ + URL/เลขเอกสาร + ผลลัพธ์
- PDF/CSV: เก็บไฟล์จริงและเลขเอกสารที่อ้างอิง
- Concurrency: เวลา, tab A/tab B, request/response หรือ audit หลังจบ
- Integration: notification/event/log ที่มี correlation กับเลข CSE

ห้ามบันทึก `PASS` จากการเห็นปุ่มถูกซ่อนเพียงอย่างเดียวในเคส permission ต้องพิสูจน์ฝั่ง backend หรือ direct URL/request ด้วย

## 9. เกณฑ์ตัดสินก่อนปิด review

ถือว่ารอบ logic review ครบเมื่อ:

- P0 ทุกข้อมีผล ไม่ใช่ `NOT RUN`
- state และ permission ครบทั้ง Owner A, Owner B, Manager
- negative validation ถูก backend ปฏิเสธจริง
- PDF และ CSV เทียบกับข้อมูลต้นฉบับอย่างน้อยอย่างละหนึ่งใบ
- notification/audit/idempotency/concurrency มีหลักฐาน หรือระบุชัดว่า blocked เพราะ environment
- OQ/AI-DEFAULT ที่กระทบ Production ได้รับคำตอบจาก PM/BA
- ทุก FAIL มี steps, expected, actual, severity และ evidence ทำซ้ำได้

## 10. Severity แนะนำ

| ระดับ | ตัวอย่างในฟีเจอร์นี้ |
|---|---|
| Critical | เห็นข้อมูลข้าม tenant, ข้ามสิทธิ์แก้/ส่ง/ยกเลิก, ข้อมูลหาย |
| High | คะแนน/PDF/CSV ผิด, เลขซ้ำ, state ผิด, ส่ง/ยกเลิกซ้ำ, notification ทำ business action ซ้ำ |
| Medium | audit ไม่ครบ, filter/export ไม่ตรงแต่มีทางเลี่ยง, attachment ผิด spec |
| Low | ข้อความผิด, label/ตำแหน่ง/ความเรียบร้อยที่ไม่กระทบ logic |
