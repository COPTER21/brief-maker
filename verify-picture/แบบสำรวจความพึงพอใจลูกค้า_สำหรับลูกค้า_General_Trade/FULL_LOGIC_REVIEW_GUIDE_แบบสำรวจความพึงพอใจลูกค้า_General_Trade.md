# Full Logic Review Guide — แบบสำรวจความพึงพอใจลูกค้า General Trade

> Feature: F-TMP-001 / FM-SAL-10  
> วัตถุประสงค์: ตรวจเก็บตก logic และการทำงานบนระบบที่พัฒนาเสร็จแล้ว โดยยึด FRD v1.0 เป็นเกณฑ์หลัก  
> สถานะเอกสารนี้: แผนและ checklist สำหรับลงมือทดสอบ — ยังไม่ใช่ผลผ่าน/ไม่ผ่าน

## 1. หลักตัดสิน

- ถ้าผลจริงขัดกับ FRD `05_RULES`, `06_TESTS`, API contract หรือ permission matrix ให้บันทึกเป็น defect
- ถ้าระบบทำตรง FRD แต่ไม่เหมาะกับงานธุรกิจ ให้บันทึกเป็นข้อเสนอแนะ/OQ ไม่ใช่ bug
- UI layout ถือว่าผ่านการตรวจแล้ว รอบนี้ดูเฉพาะ UI ที่มีผลต่อ logic เช่น ปุ่มตามสิทธิ์ สถานะ ข้อความเตือน และค่าที่แสดง
- ห้ามสรุปว่า pass จากการเห็นปุ่มหรือ toast อย่างเดียว ต้องตรวจผลหลัง refresh, เปิดใหม่, สลับผู้ใช้ และตรวจข้อมูลปลายทางที่เกี่ยวข้อง
- Production ต้องใช้บัญชี/ข้อมูลทดสอบที่ได้รับอนุญาต ห้ามเปลี่ยน config กลางหรือ Customer master จริงโดยไม่มีผู้รับผิดชอบอนุมัติ

## 2. จุดที่หลักฐานรอบเดิมยังพิสูจน์ไม่ครบ

- Test case เดิม 30 เคสสร้างเพื่อรันกับ prototype ไม่ใช่หลักฐาน production โดยตรง
- Run log ระบุ `NO-BROWSER`; E2E 21/21 เป็นผลใน container/prototype
- UAT Lite ตัด notification, doc type inactive และ stale version ออก
- Snapshot ชื่อลูกค้าและการไม่ส่งต่อระบบอื่นถูกระบุว่าไม่ได้ตรวจบน UI
- FRD ยังแสดง OQ/AI-DEFAULT หลายข้อ จึงต้องขอ PM/BA ยืนยันว่า FRD v1.0 คือ baseline ที่อนุมัติจริงก่อน sign-off

## 3. สิ่งที่ต้องเตรียม

### บัญชี

1. `Owner A` — พนักงานขาย GT ผู้สร้างใบ
2. `Owner B` — พนักงานขาย GT คนอื่น
3. `Manager` — `role-mgr-sales`

### สิทธิ์/เครื่องมือประกอบ

- เปิด notification center หรือช่องทางที่รับ event ได้
- เปิดดู network/API response ได้ถ้านโยบายอนุญาต
- มีผู้ดูแล F-DOCCFG สำหรับทดสอบ CSG inactive ใน env ที่ปลอดภัย
- มีผู้ดูแล Customer master สำหรับทดสอบการเปลี่ยนชื่อ/เบอร์ลูกค้าใน env ที่ปลอดภัย
- มีไฟล์แนบชนิดที่อนุญาต, ไฟล์ชื่อไทย, ไฟล์ขนาดใกล้ limit และไฟล์ชนิดต้องห้าม

### ชุดข้อมูลหลัก

| ชุด | คะแนน | ใช้พิสูจน์ |
|---|---|---|
| A | ครบ 16 ข้อ ทุกข้อ 4–5 | happy path, ไม่มี low-score event |
| B | ตอบเพียง 5 ข้อ | draft ได้ แต่ record ไม่ได้ |
| C | ครบ 16 ข้อ มี 1 ข้อ = 2 | boundary คะแนนต่ำและ notification |
| D | ครบ 16 ข้อ ทุกข้อ = 3 | เหนือ threshold เริ่มต้น 2 ไม่ควรแจ้งคะแนนต่ำ |
| E | ข้อเสนอแนะ 2 ช่อง ช่องละประมาณ 400 ตัวอักษร | PDF 1 หน้า/dense |

## 4. ลำดับทดสอบแนะนำ

ทำ P0 ให้ครบก่อน ถ้าพบข้อมูลรั่ว, ข้ามสิทธิ์, สถานะผิด, บันทึกซ้ำ หรือข้อมูลสูญหาย ให้หยุดและแจ้งทีมทันที

## 5. P0 — ต้องผ่านก่อนรับรอง logic

### P0-01 Happy path ตั้งแต่ต้นจนจบ

ผู้ใช้: Owner A

1. เปิดรายการและกดสร้างแบบสำรวจ
2. เลือกลูกค้า GT, วันที่วันนี้ และตรวจประจำเดือน
3. ให้คะแนนชุด A ครบ 16 ข้อ ใส่ข้อเสนอแนะ และแนบไฟล์ปกติ
4. บันทึกแบบร่าง
5. จดเลขเอกสาร แล้ว refresh/ออกเข้าใหม่
6. เปิดร่างเดิม แก้ข้อมูลที่แก้ได้ แล้วบันทึก
7. กดบันทึกผลแบบสำรวจและยืนยัน
8. refresh และเปิดรายละเอียด/PDF/CSV

Expected ตาม FRD:

- เลือกลูกค้าแล้วชื่อ/เบอร์เติมจาก Customer master
- วันที่ต้องไม่เกินวันนี้; ประจำเดือนเริ่มจากเดือนของวันที่
- คะแนนแต่ละข้อรับได้หนึ่งค่าใน 1–5; สรุปตอบแล้วและค่าเฉลี่ยอัปเดตถูก
- บันทึกร่างแล้วได้เลข `CSG-YYYY-NNNN` ตั้งแต่การบันทึกครั้งแรก
- แก้ร่างเดิมแล้วเลขเอกสารต้องไม่เปลี่ยนและไม่สร้างใบซ้ำ
- บันทึกผลได้เมื่อครบ 16 ข้อเท่านั้น; สถานะเป็น `บันทึกผลแล้ว` ทันที ไม่มี approval
- หลังบันทึกผล ไม่มีปุ่มแก้ไข และ route แก้ไขต้องไม่แก้ข้อมูลได้
- ข้อมูลหลัง refresh ต้องเหมือนก่อน refresh
- ค่าเฉลี่ยเป็นค่าแสดงผล ไม่พิมพ์ลง PDF

### P0-02 ร่างไม่ครบ และการบล็อกบันทึกผล

ผู้ใช้: Owner A; ใช้ชุด B

1. กรอกข้อมูลหลักและคะแนนเพียง 5 ข้อ
2. บันทึกเป็นร่าง แล้ว refresh และเปิดใหม่
3. พยายามบันทึกผล

Expected:

- ร่างบันทึกได้และคะแนน 5 ข้อยังคงอยู่
- ระบบบล็อกการบันทึกผล, ระบุว่าขาด 11 ข้อ และพากลับไปยังจุดที่ต้องแก้
- สถานะยังเป็นร่าง ไม่มี `recorded_at` และไม่ส่ง low-score notification

### P0-03 Permission และการป้องกันข้อมูลรั่ว

สร้างใบของ Owner A อย่างน้อยหนึ่งใบต่อสถานะ: draft, recorded, cancelled

| การกระทำ | Owner A | Owner B | Manager |
|---|---:|---:|---:|
| เห็นใบของ Owner A ในรายการ | ได้ | ไม่ได้ | ได้ |
| เปิด URL/ID ของใบ Owner A โดยตรง | ได้ | ต้องได้ 404/ไม่เผยว่ามีใบ | ได้ |
| แก้ร่างของ Owner A | ได้ | ไม่ได้ | ไม่ได้ |
| บันทึกผลร่างของ Owner A | ได้ | ไม่ได้ | ไม่ได้ (`403 NOT_OWNER`) |
| ยกเลิกใบ Owner A | ได้ | ไม่ได้ | ได้ |
| CSV | เฉพาะใบที่ตนเห็น | เฉพาะใบที่ตนเห็น | ใบที่ manager เห็น |

ต้องทดสอบทั้งการซ่อนปุ่มและการยิง route/API โดยตรง เพราะการซ่อนปุ่มอย่างเดียวไม่ใช่ security control

### P0-04 State machine และ terminal state

ทดสอบ transition เหล่านี้แยกกัน:

- ใหม่ → draft
- ใหม่/draft → recorded เมื่อคะแนนครบ
- draft → cancelled โดย Owner A
- draft → cancelled โดย Manager
- recorded → cancelled โดย Owner A
- recorded → cancelled โดย Manager

Expected:

- cancelled ต้องมีเหตุผลเสมอ; ช่องว่าง/space-only ไม่ควรผ่าน
- recorded และ cancelled แก้ไขไม่ได้
- ยกเลิกซ้ำต้องไม่เปลี่ยนข้อมูลและควรตอบ `409 ALREADY_CANCELLED`
- ไม่มีทางย้อน cancelled กลับ draft/recorded และไม่มีทางย้อน recorded กลับ draft
- ประวัติต้องเพิ่มรายการตามลำดับและห้ามหายหลัง refresh

### P0-05 คะแนนต่ำและ notification

ใช้ threshold ปัจจุบันที่ทีมยืนยัน; FRD ระบุค่าเริ่มต้น `≤ 2`

1. บันทึกผลชุด D ซึ่งคะแนนต่ำสุด = 3
2. บันทึกผลชุด C ซึ่งมีหนึ่งข้อ = 2
3. เปิด notification ของ Manager
4. refresh ใบชุด C และเปิด PDF ซ้ำหลายครั้ง

Expected:

- ชุด D ไม่มีแบนเนอร์คะแนนต่ำและไม่มี `csg_low_score_recorded`
- ชุด C มี low_count ถูกต้องและแจ้ง Manager หนึ่งเหตุการณ์เมื่อ draft → recorded สำเร็จ
- notification มีเลขเอกสาร, ชื่อลูกค้า, low_count และประจำเดือนตรงกับใบ
- refresh/เปิดรายละเอียด/สร้าง PDF ซ้ำต้องไม่ยิง notification ซ้ำ
- ไม่มี notification ระหว่างเป็นร่าง แม้กรอกคะแนน 1 หรือ 2 แล้ว

### P0-06 การยกเลิกและ notification

1. Owner A ยกเลิกใบตนเอง
2. Manager ยกเลิกใบอื่นของ Owner A พร้อมเหตุผล

Expected:

- Owner ยกเลิกเอง: สถานะ/เหตุผลถูกต้อง แต่ไม่จำเป็นต้องส่ง `csg_cancelled` ให้ตนเอง
- Manager ยกเลิก: Owner A ได้ `csg_cancelled` หนึ่งครั้ง พร้อมเลขใบ ผู้กระทำ และเหตุผลตรงกัน
- การกดยืนยันซ้ำ/refresh ต้องไม่สร้าง event ซ้ำ

### P0-07 CSV และ PII

1. ตั้งตัวกรองสถานะ, เดือน, ผู้บันทึก และคำค้นทีละแบบ/ร่วมกัน
2. ส่งออก CSV ด้วย Owner A และ Manager
3. เปิดไฟล์และเทียบทุกแถวกับผลรายการที่ filter อยู่

Expected:

- CSV ส่งออกตาม filter ปัจจุบัน ไม่ใช่เฉพาะหน้าที่กำลังแสดง และไม่มีใบที่ผู้ใช้ไม่มีสิทธิ์เห็น
- ไม่มีคอลัมน์หรือค่าของ `contact_phone`
- เลขเอกสาร, ลูกค้า, เดือน, ผู้บันทึก, สถานะ และค่าเฉลี่ยตรงกับระบบ
- ภาษาไทย/อักขระพิเศษเปิดได้ไม่เพี้ยน

## 6. P1 — ความเสี่ยงสูงที่ tester UI มักไม่ครอบคลุม

### P1-01 วันที่และประจำเดือน

- วันที่อนาคต: ต้องบันทึกไม่ได้
- วันที่วันนี้: ต้องบันทึกได้
- เปลี่ยนวันที่ข้ามเดือน: ตรวจว่าประจำเดือนเปลี่ยนตามกติกาและผู้ใช้ยังเปลี่ยนเองได้
- วันที่ไม่อยู่ในประจำเดือนที่เลือก: ต้องเตือนแต่ไม่บล็อกทั้ง draft และ record
- ทดสอบวันสิ้นเดือน/ต้นเดือน และเปิดใหม่หลังบันทึกเพื่อจับ timezone shift

### P1-02 เลขเอกสาร, double-click และ idempotency

- double-click บันทึกร่าง/บันทึกผล/ยกเลิก
- กดบันทึกแล้ว network ช้า จากนั้นกดซ้ำหรือ refresh
- เปิดสองแท็บสร้างพร้อมกันและบันทึกใกล้กัน

Expected:

- หนึ่ง intent ต้องได้หนึ่งใบ/หนึ่ง transition/หนึ่ง event
- เลขเอกสารไม่ซ้ำและใบเดิมไม่เปลี่ยนเลขเมื่อแก้ไข
- ระบบไม่ต้อง no-gap ตาม FRD; เลขข้ามไม่ใช่ bug โดยตัวมันเอง

### P1-03 Optimistic lock / stale version

1. Owner A เปิดร่างเดียวกันสองแท็บ
2. แท็บแรกแก้และบันทึก
3. แท็บสองแก้ข้อมูลอีกค่าแล้วบันทึก

Expected:

- แท็บสองต้องไม่เขียนทับเงียบ ๆ; ได้ `409 STALE_VERSION` และข้อความให้ refresh
- หลัง refresh เห็นค่าจากแท็บแรกครบ ไม่มีข้อมูลผสมกัน

### P1-04 Snapshot จาก master data

ทำใน env/ข้อมูลที่อนุญาตเท่านั้น:

1. สร้างใบด้วยชื่อลูกค้า A และบันทึกร่าง
2. เปลี่ยนชื่อลูกค้าใน Customer master เป็น B
3. เปิดใบเดิม, PDF และ CSV; จากนั้นสร้างใบใหม่

Expected:

- ใบเดิมคง `customer_name_snapshot` เดิม
- ใบใหม่ใช้ชื่อใหม่
- header บริษัท/โลโก้และ form code/revision ของใบเดิมต้องเป็น snapshot ตามจังหวะออกเลข

### P1-05 PDF ทุกสถานะ

ตรวจ draft, recorded ปกติ, recorded คะแนนต่ำ, long comments และ cancelled

Expected:

- A4 หน้าเดียว; ตารางคะแนน 3 ด้านและคอลัมน์ 5 4 3 2 1 อยู่หน้าเดียวกับหัวข้อ
- เครื่องหมาย ✓ ตรงคะแนนทั้ง 16 ข้อ
- วัน/เดือนเป็นภาษาไทย พ.ศ. และข้อมูลตรงกับรายละเอียด
- ข้อความ “การส่งมอบตามเวลาที่ได้นัดหมายไว้” ถูกต้อง
- ข้อเสนอแนะยาวยังอ่านได้และไม่ล้น/หาย
- draft มีป้าย “ร่าง”; cancelled มีป้าย “ยกเลิก” และไม่ทำให้เข้าใจว่าเป็นใบใช้งานปกติ
- ไม่มีค่าเฉลี่ยและไม่มีช่องลายเซ็น/approval
- ดาวน์โหลดกับ preview ต้องให้ข้อมูลเดียวกัน

### P1-06 ไฟล์แนบ

- แนบไฟล์ปกติ, ชื่อไทย, ชื่อยาว, ขนาดใกล้ limit, ชนิดต้องห้าม และไฟล์ชื่อซ้ำ
- refresh แล้วดาวน์โหลดกลับมาเทียบไฟล์
- Owner B ทดลองเข้าถึง attachment URL/ID ของ Owner A โดยตรง

Expected:

- ไฟล์ปกติไม่เสียและผูกกับใบถูกต้อง
- ไฟล์ต้องห้าม/เกิน limit ถูกปฏิเสธด้วยข้อความที่เข้าใจได้
- ผู้ไม่มีสิทธิ์เห็นใบต้องดาวน์โหลดไฟล์ไม่ได้
- หมายเหตุ: FRD ไม่ล็อกชนิด/ขนาดและสิทธิ์แก้ไฟล์หลัง recorded ชัดเจน หากพฤติกรรมไม่เหมาะสมให้เปิด OQ/ข้อเสนอแนะก่อนตี bug

### P1-07 Filter, count และ pagination

- เทียบจำนวน badge ในแท็บกับจำนวนจริงของข้อมูลที่ผู้ใช้มีสิทธิ์เห็น
- ใช้ filter ร่วมกันและสลับ page size 10/25/50
- เปลี่ยน filter ขณะอยู่หน้าท้าย ๆ

Expected:

- count ต่อสถานะต้องสอดคล้องกับสิทธิ์ของผู้ใช้
- ไม่มีแถวหาย/ซ้ำระหว่างหน้า และการเปลี่ยน filter ไม่ค้างหน้าที่ไม่มีข้อมูล

### P1-08 F-DOCCFG inactive

ทำเฉพาะ env ที่ควบคุมได้:

- เมื่อ CSG inactive ปุ่มสร้างต้อง disabled และมีข้อความ “แบบเอกสารนี้ยังไม่เปิดใช้งาน”
- หากยิงสร้างตรง backend ต้องได้ `409 DOC_TYPE_INACTIVE`
- ใบเดิมควรยังเปิดดูได้ เว้นแต่มีข้อกำหนดอื่นที่อนุมัติแล้ว

## 7. P2 — Business exploration นอก FRD

รายการต่อไปนี้มี business sense แต่ถ้า FRD ไม่กำหนด ห้ามฟันธงเป็น bug ทันที:

1. ลูกค้ารายเดิมตอบซ้ำเดือนเดียวกัน — FRD EC-03 ระบุว่า “ไม่บล็อก”; ควรถาม BA ว่าต้องเตือนหรือรายงานซ้ำหรือไม่
2. ลูกค้าที่ถูก inactive หรือเปลี่ยน channel ออกจาก GT หลังสร้างร่าง — ใบเดิมควรทำอย่างไร
3. คะแนนต่ำหลายข้อหรือหลายใบติดกัน — Manager ได้ notification มากเกินไปหรือจำเป็นต้อง aggregate
4. Manager ยกเลิกใบที่บันทึกผลแล้ว — downstream report ต้องตัดใบนี้ออกหรือแสดงเป็น cancelled อย่างไร
5. การค้นหาชื่อไทยที่มีเว้นวรรค/สระ/เลขเอกสารบางส่วน และชื่อบริษัทซ้ำกัน
6. ปริมาณข้อมูลมาก: list, filter และ CSV หลายพันรายการยังตอบสนองได้และไม่ timeout
7. การเปลี่ยน threshold คะแนนต่ำภายหลัง — ใบเก่าควรคงผลเดิมหรือคำนวณใหม่เมื่อเปิดดู
8. Retention/สิทธิ์เข้าถึงเบอร์โทรและไฟล์แนบ — ต้องสอดคล้อง PDPA และ audit ขององค์กร

## 8. วิธีเก็บหลักฐานต่อหนึ่งเคส

บันทึกอย่างน้อย:

- Test ID / FRD reference
- วันเวลาและ environment/build
- ผู้ใช้/role และข้อมูลตั้งต้น
- ขั้นตอนทำซ้ำ
- Expected ตาม FRD
- Actual ที่เห็นจริง
- เลขเอกสาร/record ID
- screenshot ก่อนและหลัง, notification, CSV/PDF หรือ network response ที่เกี่ยวข้อง
- ผล `Pass / Fail / Blocked / Not Run`
- ถ้า Fail: severity และผลกระทบทางธุรกิจ

## 9. Severity ที่แนะนำ

- Critical: ข้ามสิทธิ์/ข้อมูลรั่ว, ข้อมูลเสียหรือหาย, ใช้งาน flow หลักไม่ได้
- High: สถานะผิด, record ทั้งที่คะแนนไม่ครบ, ใบซ้ำ, notification สำคัญไม่ส่ง/ส่งผิดคน, PDF/CSV ให้ข้อมูลธุรกิจผิด
- Medium: ผิด FRD แต่มีทางเลี่ยง, audit/history ไม่ครบ, stale update จัดการไม่ถูกแต่ยังไม่ทำข้อมูลเสีย
- Low: ข้อความ/การแสดงผลที่ไม่กระทบ logic
- Suggestion/OQ: ทำตรง FRD แต่ business rule ยังไม่เหมาะหรือ FRD ไม่ชัด

## 10. เกณฑ์จบรอบ review

- P0 ทุกข้อมีผลและหลักฐานครบ
- P1 ที่ทำไม่ได้ต้องระบุเหตุผล/เจ้าของ dependency ห้ามนับเป็น pass
- Critical/High ที่ยังเปิดอยู่ = ไม่ควรรับรอง
- Permission matrix ต้องพิสูจน์ด้วยอย่างน้อย Owner A, Owner B และ Manager
- Notification ต้องพิสูจน์ปลายทางจริง ไม่ใช่แค่เห็นแบนเนอร์
- PDF/CSV ต้องเปิดไฟล์จริงและเทียบข้อมูล ไม่ใช่แค่เห็น toast ดาวน์โหลด
- สรุปแยกชัดเจน: ผ่านตาม FRD, defect, blocked/not tested, และข้อเสนอแนะนอก FRD
