## 1. บทนำ
เอกสารฉบับนี้เป็น **หนังสือสัญญา 2 ฝ่าย** ไม่ใช่แบบฟอร์มกรอกช่องล้วน — บริษัทให้ลูกค้ายืมกล่องบรรจุกระดาษไปใช้ในกิจการโดยไม่คิดมูลค่า
ตัวเนื้อสัญญาเป็นถ้อยคำผูกพันทางกฎหมายที่คงที่ 2 ข้อ มีช่องเติมแทรกอยู่ในเนื้อความเพียงจุดเดียว
ปัจจุบันทำบน Word แล้วพิมพ์ 2 ชุด (ต้นฉบับ + สำเนา) ให้คู่สัญญาลงนามด้วยมือ ทำให้ไม่มีทะเบียนกลาง ตามไม่ได้ว่าใครยืมกล่องไปเท่าไร และเลขที่หนังสือซ้ำกันได้

## 2. วัตถุประสงค์ทางธุรกิจ
1. ให้มีทะเบียนกลางของหนังสือสัญญายืมกล่อง — รู้ว่าลูกค้ารายไหนยืมกล่องแบบใด จำนวนเท่าไร ตั้งอยู่ที่ใด
2. ออกเลขที่หนังสือจากระบบเพื่อไม่ให้ซ้ำ และสืบค้นย้อนหลังได้
3. บังคับให้ผู้ส่งมอบฝ่ายบริษัทลงนามในระบบก่อนพิมพ์ส่งลูกค้า (มีร่องรอยว่าใครอนุมัติ เมื่อไร)
4. พิมพ์แบบพิมพ์ให้เหมือนกระดาษเดิม ลูกค้าเปิดแล้วจำฟอร์มตัวเองได้
5. คุมถ้อยคำสัญญาให้เป็นชุดเดียวทั้งองค์กร — แก้เงื่อนไขรายฉบับไม่ได้ และเพดานเปลี่ยนกล่องฟรีอ่านจากนโยบายขายกลาง

## 3. ขอบเขต
### 3.1 อยู่ในขอบเขต
- หน้าทะเบียนหนังสือสัญญายืม (ค้นหา · กรองสถานะ · กรองลูกค้า · กรองฝ่าย · ส่งออก CSV)
- สร้าง/แก้ไขร่าง 3 ขั้น (ข้อมูลหนังสือสัญญา › เอกสารแนบ › ตรวจสอบและยืนยัน)
- ส่งให้ผู้ส่งมอบลงนามตามสาย DOA · ลงนาม · ส่งกลับแก้ไข · ยกเลิก
- แบบพิมพ์ Replica A4 แนวตั้ง ตาม FM-SAL-14 — **1 เลขที่ พิมพ์ 2 ชุด** (ต้นฉบับ · สำเนา) เนื้อความและเลขข้อเดียวกัน
- แนบไฟล์ประกอบผ่าน Document Center · ประวัติ append-only

### 3.2 ไม่อยู่ในขอบเขต (DEC-01 · DEC-02 · DEC-11)
- ไม่เปลี่ยนค่าตั้งต้นใด ๆ ในระบบเมื่อลงนามครบ
- ไม่ตัดสต๊อกกล่อง ไม่ออกใบส่งของ ไม่ลงบัญชี ไม่ส่งข้อมูลต่อระบบอื่นในรอบนี้ (กล่องยังเป็นทรัพย์สินบริษัท)
- ไม่มีการสร้างใบใหม่จากใบเดิม · ไม่มีประกาศเมื่อลงนามครบ
- ไม่ติดตามการคืนกล่อง ไม่คิดค่าเสียหาย ไม่มีวันครบกำหนดคืน (กระดาษไม่มีช่องเหล่านี้ · DEC-16)

## 8. สถานะและวงจรชีวิต
```
ร่าง ──ส่งให้ลงนาม──> รอลงนาม ──ลงนาม──> ลงนามแล้ว
 ^                       │
 └──ส่งกลับแก้ไข─────────┘        (DEC-08 · เลขเดิม)
ร่าง / รอลงนาม / ลงนามแล้ว ──ยกเลิก (มีเหตุผล)──> ยกเลิก
```
ไม่มีสถานะ "ไม่อนุมัติ" — การไม่ลงนามคือการส่งกลับแก้ไข (DEC-08)

## 10. Edge Cases
| # | กรณี | ระบบทำอย่างไร |
|---|---|---|
| E1 | ที่ตั้งกล่องต่างจากที่อยู่จดทะเบียนลูกค้า | ที่อยู่เติมอัตโนมัติแล้วแก้ได้ · เก็บค่าที่แก้ลงเอกสาร ไม่ย้อนแก้ทะเบียนลูกค้า |
| E2 | ช่องเติมในเงื่อนไขข้อ 1 เว้นว่าง | อนุญาต — แบบพิมพ์แสดงเส้นประว่างตามกระดาษ |

| E7 | สาย DOA ถูกตั้งเพิ่มเป็นหลายขั้นภายหลัง | ระบบรองรับ N ขั้น · ช่องลงชื่อบนแบบพิมพ์เพิ่มตาม (ทดสอบ 6 ขั้น → 7 ช่อง 2 แถว) |
| E8 | ส่งกลับแก้ไขซ้ำหลายรอบ | ประวัติเก็บทุกรอบแบบ append-only · เลขที่ไม่เปลี่ยน |
| E9 | เอกสารถูกแก้โดยผู้อื่นระหว่างกรอก | server ตอบ 409 → แจ้งให้รีเฟรชแล้วลองใหม่ |
| E10 | แบบเอกสารยังไม่เปิดใช้ที่ F-DOCCFG | ปุ่มสร้างถูกปิด + แจ้งเตือนบนหน้าทะเบียน |

## 16. Security
- ชื่อ ที่อยู่ลูกค้า และชื่อผู้ลงนามเป็นข้อมูลส่วนบุคคล — แสดงเฉพาะผู้มีสิทธิ์ตาม §4 · **ไม่ใช้ข้อมูลจริงจากไฟล์ลูกค้าเป็นข้อมูลตัวอย่าง** (prototype ใช้ชื่อสมมติและโลโก้ placeholder)
- ไม่เก็บรหัสผ่านหรือ credential ในเอกสารใด ๆ
- ตรวจสิทธิ์ที่ server ทุก endpoint — การซ่อนปุ่มใน UI เป็นเพียงชั้นแรก
- ประวัติ append-only · ไฟล์แนบผ่าน Document Center (ตรวจชนิดและขนาดที่ server)
