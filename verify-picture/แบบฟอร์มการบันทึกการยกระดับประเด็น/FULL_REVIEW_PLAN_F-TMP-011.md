วันที่จัดทำแผน: 27 พฤศจิกายน 2569  
เป้าหมาย: ตรวจเก็บตกด้าน Logic, Workflow, Permission, Data Integrity และ Integration หลังระบบขึ้น Production

> เอกสารนี้เป็นแผนตรวจ ไม่ใช่ผลรับรอง การใส่ Pass/Fail ต้องมาจากการทดสอบและหลักฐานของผู้ตรวจเท่านั้น

## 1. ข้อสรุปก่อนเริ่ม

- ใช้ FRD เป็นเกณฑ์ Expected Result ตามที่ PM/BA กำหนด
- ถ้าพฤติกรรมระบบต่างจาก FRD ให้ตรวจว่าเป็น Bug, Configuration Gap หรือ Spec Gap ก่อนสรุป
- ไม่ต้องย้อนตรวจ layout ทั้งหมด แต่ต้องตรวจ UI ที่มีผลต่อการทำงาน เช่น ปุ่มตามสิทธิ์, ข้อความ error, สถานะ, warning และข้อมูลใน PDF
- อย่าทดสอบอนุมัติ/ยกเลิกกับข้อมูลธุรกิจจริง ใช้เอกสารทดสอบที่ตั้งชื่อชัด เช่น `[REVIEW-F-TMP-011-YYYYMMDD]`
- การแก้ DOA, ปิด doc type หรือทดสอบหลาย tenant บน Production ต้องประสานผู้ดูแลก่อน หากทำไม่ได้ให้ระบุว่า `Not Tested` ห้ามเดาว่าผ่าน

## 10. สิ่งที่ไม่ควร Fail เพราะอยู่นอก Scope

- ไม่ดึงประเด็นจาก FM-IVM-03 อัตโนมัติ; อ้าง `OI-xxx` ได้เป็นข้อความเท่านั้น
- ไม่มีแจ้งเตือนกำหนดส่งรายวัน
- หลังอนุมัติไม่เปลี่ยนสถานะหรือค่าในระบบอื่น
- ไม่มีปุ่มทำซ้ำเอกสาร
- ชื่อโครงการ/ธุรกรรมกรอกเอง ไม่ผูกทะเบียนโครงการ FM-IVM-01

ถ้าพบว่าระบบมีความสามารถนอก scope ให้ตรวจว่าไม่ทำให้ข้อมูลหรือสิทธิ์เสีย แต่ไม่ถือว่าเป็น Pass ของ FRD และไม่ควรรับรองแทน BA

## 11. วิธีบันทึก Bug ให้ตัดสินใจได้

ทุก Bug ต้องมี:

1. เลขเอกสาร/ผู้ใช้/role/environment/build และเวลาที่พบ
2. Precondition และ state ก่อนเริ่ม
3. Steps ที่ทำซ้ำได้
4. Expected อ้าง FRD เป็นรหัส เช่น `BR-07`, `AC-09`, `TC-D03`
5. Actual ที่เห็นจริง รวมข้อความ/สถานะ/จำนวน/ผู้รับแจ้งเตือน
6. Screenshot หรือคลิป และ request/response ถ้าเข้าถึงได้
7. ตรวจว่าข้อมูลหรือ workflow เสียต่อเนื่องอย่างไร

ระดับแนะนำ:

- Critical: ข้ามสิทธิ์/ข้าม DOA, ข้อมูลข้าม tenant, ข้อมูลเสียหรือหาย, ใช้งาน flow หลักไม่ได้
- High: สถานะ/เลขเอกสาร/PDF/ผู้รับแจ้งเตือนผิด, เอกสารหรือ notification ซ้ำ
- Medium: ผิด FRD แต่มีทางเลี่ยง, audit/history ไม่ครบ
- Low: ข้อความ/ตำแหน่ง/หน้าตาที่ไม่กระทบการทำงาน
- Spec Gap: FRD ขัดกันเองหรือยังเป็น AI-DEFAULT/OQ และยังไม่มีมติธุรกิจ

## 12. ลำดับรันที่แนะนำ

1. ยืนยัน G-01..G-06 และบัญชีทดสอบ
2. รัน M-01..M-09 เป็น golden flow
3. รัน V และ S เพื่อพิสูจน์ validation/state machine
4. รัน P โดยเปลี่ยน persona และทดสอบ direct URL/API
5. รัน C เพราะเป็นกลุ่มเสี่ยงที่ test case เดิมครอบคลุมไม่ครบ
6. รัน I โดยประสานผู้ดูแล integration/configuration
7. สรุปผลแยก Pass, Fail, Not Tested และ Spec Gap ห้ามนับ Not Tested เป็น Pass

## 13. Exit Criteria สำหรับ Review รอบนี้

- Must-test M-01..M-09 ผ่านทั้งหมด
- ไม่มี Critical/High ค้างใน permission, state, numbering, PDF และ notification
- ทุก Validation/Permission case มีผลหรือมีเหตุผลชัดเจนว่า Not Tested
- Golden flow ใช้ผู้ใช้จริงตาม role อย่างน้อย 4 persona ไม่ใช่ admin คนเดียวสลับบทบาท
- PDF และ CSV ถูกเทียบกับข้อมูลต้นทางอย่างน้อย 1 ใบต่อสถานะสำคัญ
- Spec Gap G-01..G-06 มี owner และมติ ไม่ถูกปิดเป็น “ผ่าน” ด้วยการคาดเดา
