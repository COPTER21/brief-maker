# Logic & Business Review Guide — F-TMP-005 แบบฟอร์ม Change Request

วันที่จัดทำ: 11 พฤศจิกายน 2569  
ฐานอ้างอิงหลัก: FRD-F-TMP-005 v1.0 (`00_OVERVIEW` ถึง `07_LOCKED_DECISIONS`)  
วัตถุประสงค์: ตรวจรอบเก็บตกบนระบบที่ขึ้น Production แล้ว โดยเน้น logic, business flow, permission, data integrity และ integration ไม่ตรวจความสวยงามของ layout ซ้ำ

## 1. ข้อสรุปก่อนเริ่ม

ฟีเจอร์นี้ไม่ใช่ระบบ Change Management ครบวงจร หลังอนุมัติครบระบบเพียงสร้าง PDF ฉบับอนุมัติและแจ้งเจ้าหน้าที่ IT เท่านั้น ไม่ได้ดำเนินการเปลี่ยนแปลง, ปิดงาน, บันทึกผล, อัปเดต CMDB หรือส่งต่อระบบอื่น สิ่งเหล่านี้เป็น Out of Scope ตาม FRD หากผู้ใช้คาดหวังว่ากดอนุมัติแล้วงาน IT ถูกดำเนินการหรือปิดอัตโนมัติ ให้บันทึกเป็น scope gap / requirement question ไม่ใช่ bug ทันที

จุดเสี่ยงสูงสุดที่ควรใช้เวลาตรวจคือ:

1. สายอนุมัติ DOA แบบ dynamic และลำดับผู้อนุมัติ
2. การไม่อนุมัติแล้วกลับร่างด้วยเลขเดิม และ resolve สายใหม่เมื่อส่งซ้ำ
3. สิทธิ์มองเห็นข้อมูลระหว่าง owner, ผู้อนุมัติแต่ละขั้น, IT officer และคนอื่น
4. การออกเลข ITCR ตั้งแต่บันทึกครั้งแรก รวมถึงการกดซ้ำ/เปิดสองแท็บ
5. ความถูกต้องของ PDF, snapshot และลายเซ็นทุกสถานะ
6. Notification ที่ต้องส่งเฉพาะ event/ผู้รับตาม FRD
7. CSV/ไฟล์แนบ/ข้อมูลข้ามบริษัท ซึ่งมีความเสี่ยงด้านข้อมูลรั่วไหล

## 2.1 Finding ที่ยืนยันจากการตรวจ Production

### CR-LOGIC-001 — Flow แนบไฟล์ไม่ตรง Create/Edit wizard

**สถานะ:** Candidate defect — ต้องเก็บ screenshot/build และทำซ้ำก่อนออก Feature Check Report  
**ระดับเสนอ:** Medium; ปรับเป็น High หากทำให้ผู้ใช้ส่งคำขอโดยลืมแนบเอกสารสำคัญ หรือไม่สามารถกลับมาแนบได้ตามสิทธิ์  
**อ้างอิง:** FRD `01_UI §1.3`, `02_API API-11`, `06_TESTS AT-08`

**Expected**

- Step 2 ของหน้า Create/Edit คือ “เอกสารแนบ” ผู้ใช้ต้องจัดการไฟล์ภายใน wizard ได้
- View drawer ใช้ดูหรือดาวน์โหลดไฟล์เท่านั้น ไม่ใช่จุดเพิ่ม/แก้ไขไฟล์
- API อนุญาตแนบเมื่อเอกสารมีสถานะ draft ดังนั้นระบบอาจสร้าง/auto-save draft เพื่อให้มี document id ก่อน upload แต่ไม่ควรบังคับให้ผู้ใช้ออกจาก Create/Edit flow

**Actual ที่ผู้ตรวจแจ้ง**

- บน Production ต้องบันทึกร่างก่อน
- จากนั้นต้องเข้าหน้ารายละเอียดจึงจะแนบไฟล์ได้

**เหตุผลที่เป็นปัญหา**

- Create/Edit ไม่ทำงานครบตาม wizard 3 ขั้นที่ FRD กำหนด
- View drawer มีความสามารถแก้ข้อมูล attachment ทั้งที่ควรเป็น read/download only
- ผู้ใช้อาจเข้าใจว่าบันทึกร่างเสร็จแล้วและลืมกลับมาแนบไฟล์ก่อนส่งอนุมัติ
- เส้นทาง Create → Attach → Review → Submit ถูกตัดเป็นหลายบริบท ทำให้ validation และสิทธิ์ตามสถานะเสี่ยงไม่สอดคล้องกัน

**ขั้นตอนทำซ้ำที่ต้องเก็บหลักฐาน**

1. เข้า Create ด้วย U1 และกรอก Step 1 ครบ
2. ไป Step 2 แล้วบันทึกว่าเห็น upload control หรือไม่ และระบบแสดงข้อความอะไร
3. พยายามแนบไฟล์ที่อนุญาตก่อนบันทึกร่าง
4. บันทึกร่าง ตรวจ route/page ที่ระบบพาไป
5. เปิด View drawer แล้วบันทึกว่าเพิ่ม/ลบ/ดาวน์โหลดไฟล์อะไรได้บ้าง
6. เข้า Edit ของร่างเดิม ตรวจว่า Step 2 สามารถเพิ่ม/ลบไฟล์ได้หรือไม่
7. ส่งอนุมัติ แล้วตรวจว่า View เหลือเพียงดู/ดาวน์โหลดและไม่สามารถเพิ่ม/ลบไฟล์

**เกณฑ์ตัดสิน**

- Fail: Create/Edit Step 2 แนบไฟล์ไม่ได้ หรือ View drawer ของ draft เป็นจุดเดียวที่เพิ่ม/ลบไฟล์ได้
- Pass: Create/Edit จัดการ attachment ได้ครบ; การสร้าง draft id เกิดภายใน flow; View drawer เป็น read/download only
- ต้องแยก bug เพิ่ม: หาก pending/approved/cancelled ยังเพิ่มหรือลบ attachment ได้ ให้เปิดเป็น permission/state defect ระดับ High

## 3. การเตรียมข้อมูลทดสอบ

ใช้บัญชีแยกอย่างน้อย 6 ตัว และห้ามใช้ผู้อนุมัติจริงโดยไม่ประสานงาน

| บัญชี | บทบาท | ใช้พิสูจน์ |
|---|---|---|
| U1 | ผู้ขอ A | สร้าง/แก้ไข/ส่ง/ยกเลิก/เห็นของตน |
| U2 | หัวหน้า A / Approver ขั้น 1 | เห็นหลังส่งและพิจารณาเฉพาะขั้นตน |
| U3 | ผู้จัดการ IT / Approver ขั้น 2 | ห้ามอนุมัติก่อนขั้น 1 และอนุมัติขั้นสุดท้าย |
| U4 | IT officer | เห็นทุกใบ, ยกเลิกร่าง/รออนุมัติ, รับแจ้งอนุมัติครบ |
| U5 | ผู้ใช้ทั่วไปที่ไม่เกี่ยวข้อง | ทดสอบ deny และ data leakage |
| U6 | ผู้ใช้ต่างบริษัท/tenant | ทดสอบ tenant isolation ถ้าสภาพแวดล้อมรองรับ |

เตรียมข้อมูลอย่างน้อย 8 ใบ: ร่างปกติ, ร่างมีหลายประเภท, รอขั้น 1, รอขั้น 2, ใบตีกลับ, ใบอนุมัติแล้ว, ใบยกเลิก และใบข้อความยาว/DOA หลายขั้น

หลักฐานขั้นต่ำต่อเคส: เลขเอกสาร, ผู้ใช้/role, เวลากด, input สำคัญ, expected จาก FRD, actual ที่เห็น, screenshot ก่อน–หลัง และ request/response หรือ log เมื่อเข้าถึงได้

## 4. ลำดับทดสอบแนะนำ

อย่าทดสอบเป็นเคสแยกอย่างเดียว ให้ทำ “เส้นเรื่อง” ต่อเนื่องเพื่อจับข้อมูลค้างและ state ผิด

### Flow A — Happy path ครบวงจร

- [ ] U1 สร้างใบ กรอก required ครบ เลือกประเภท 2 ค่า แนบไฟล์ แล้วบันทึกร่าง
- [ ] ได้เลข `ITCR-ปีพ.ศ.-running` ตั้งแต่บันทึกครั้งแรก และเลขไม่เปลี่ยนหลังแก้/ส่ง/อนุมัติ
- [ ] สถานะเป็นร่าง U1 และ U4 เห็น แต่ U2/U3/U5 ไม่เห็น
- [ ] U1 แก้ข้อมูลแล้วส่งอนุมัติ ระบบ resolve DOA ตาม config ปัจจุบันและ freeze สายไว้
- [ ] U2 เห็นใบใน “รอฉันพิจารณา”; U3 เห็นใบหลังส่งแต่ยังไม่มีสิทธิ์กดอนุมัติ
- [ ] U2 อนุมัติ สถานะรวมยังเป็นรออนุมัติ และ current step เปลี่ยนเป็น U3
- [ ] U3 อนุมัติ สถานะเป็นอนุมัติแล้ว, PDF final ถูกเก็บ, U4 ได้ notification
- [ ] ใบอนุมัติแล้วไม่มีปุ่มแก้ไข/ยกเลิก และ API แก้/ยกเลิกต้องถูกปฏิเสธ

### Flow B — Reject, แก้ไข และส่งใหม่

- [ ] ส่งใบจนถึงขั้น 2 แล้วให้ U3 ไม่อนุมัติโดยไม่กรอกเหตุผล ระบบต้องบล็อก
- [ ] กรอกเหตุผลแล้วไม่อนุมัติ ใบกลับเป็นร่างด้วยเลขเดิมและแสดงเหตุผลแก่ U1
- [ ] ผู้อนุมัติเดิมต้องไม่เห็นร่างที่ถูกตีกลับ (เว้นแต่เป็น U4)
- [ ] ประวัติต้องเก็บสายอนุมัติเดิมและการตัดสินใจเดิม ไม่ถูกลบหรือเขียนทับ
- [ ] เปลี่ยน DOA ก่อน U1 ส่งใหม่ แล้วตรวจว่าส่งใหม่เริ่มขั้น 1 และใช้สายใหม่ตาม FRD
- [ ] เหตุผลตีกลับเก่าต้องไม่กลายเป็นเหตุผลของรอบใหม่ แต่ยังต้องอยู่ใน audit/history

### Flow C — Cancel

- [ ] U1 ยกเลิกร่างโดยไม่ใส่เหตุผล ระบบต้องบล็อก
- [ ] U1 ยกเลิกร่างพร้อมเหตุผล สถานะ cancelled และไม่มี notification ถึง approver เพราะยังไม่เคย pending
- [ ] U1 ยกเลิกใบ pending ผู้อนุมัติขั้นปัจจุบันต้องได้รับ `itcr_cancelled`
- [ ] ขั้นที่กำลัง pending เปลี่ยนเป็น skipped และไม่มีใครอนุมัติต่อได้
- [ ] U4 ยกเลิกใบ draft/pending ได้ แต่ U2/U3/U5 ทำไม่ได้
- [ ] ใบ approved ยกเลิกไม่ได้ทั้งจาก UI และ direct API

### Flow D — Permission matrix และข้อมูลรั่วไหล

- [ ] U5 ค้นหาเลขเอกสาร, เปิด URL ตรง, ดาวน์โหลด PDF, attachment และ export CSV แล้วต้องไม่เห็นข้อมูล
- [ ] U2/U3 เห็นใบหลัง submit เฉพาะใบที่ตนอยู่ใน approval chain
- [ ] ผู้อนุมัติขั้นถัดไปเห็นรายละเอียดได้ แต่ action approve/reject ต้องยังใช้ไม่ได้
- [ ] U1 ไม่สามารถอนุมัติใบตัวเองผ่าน UI หรือ API
- [ ] U4 เห็นทุกใบในบริษัท แต่ไม่มีสิทธิ์อนุมัติแทน current approver เว้นแต่ได้รับมอบหมายใน DOA จริง
- [ ] U6 ต้องไม่เห็นเลข, รายการ, PDF, attachment หรือ CSV ของอีกบริษัท แม้เดา id/URL ได้
- [ ] จำนวน badge, tab count, pagination และ export ต้องนับเฉพาะข้อมูลที่ role นั้นมีสิทธิ์เห็น

### Flow E — Concurrency / double action

- [ ] เปิดร่างเดียวกันสองแท็บ แก้และบันทึกแท็บ A แล้วบันทึกแท็บ B ระบบต้องตอบ 409 STALE/ให้รีเฟรช ไม่ทับข้อมูลล่าสุด
- [ ] ดับเบิลคลิก “บันทึกและส่งอนุมัติ” ต้องได้ transition ครั้งเดียว ไม่มี approval chain ซ้ำ
- [ ] U2 เปิด approve สองหน้าต่าง กดพร้อมกัน ต้องบันทึก decision ครั้งเดียวและไม่ข้ามขั้น
- [ ] U1 ยกเลิกพร้อมกับ U2 อนุมัติ ต้องมีผลลัพธ์สุดท้ายเพียงสถานะเดียวและ audit สอดคล้อง
- [ ] API submit ล้มเหลว 500 ใบต้องคง draft, ไม่มี partial approval chain และไม่ส่ง notification
- [ ] refresh/back/retry หลัง network timeout ต้องไม่ออกเลขใหม่หรือสร้างเอกสารซ้ำ

## 5. Checklist ตาม FRD

### 5.1 Validation และค่าขอบเขต

- [ ] Subject ว่าง → `ระบุเรื่องที่ต้องการ`
- [ ] ไม่เลือก change type → บล็อกด้วยข้อความตาม VR-02
- [ ] เลือกหลาย change type ได้ และค่าถูกเก็บครบ
- [ ] เลือก Other แต่เว้นข้อความ → บล็อก; เอาติ๊ก Other ออกแล้วค่าข้อความเก่าต้องไม่รั่วเข้า PDF/CSV
- [ ] due date ว่าง → บล็อก
- [ ] due date ก่อน request date → เตือนแต่ยังส่งได้ นี่เป็น spec ไม่ใช่ bug
- [ ] ทดสอบวันสิ้นเดือน/สิ้นปี/ปีอธิกสุรทิน และการแสดง พ.ศ. เทียบกับค่าที่เก็บจริง
- [ ] Delivery location, change detail, objective, impact และ action plan ว่างทีละช่อง → บล็อกและชี้ช่องถูก
- [ ] ทดสอบช่องว่างล้วน, ขึ้นบรรทัด, ภาษาไทย/อังกฤษ, emoji, quote, `<script>` และข้อความยาว เพื่อดู trim, encoding และ XSS
- [ ] ข้อมูลที่กรอกถูกแสดงตรงกันใน detail, PDF, CSV และหลัง reopen
- [ ] ผู้พิจารณาทุกขั้นต้องมีครบ และห้ามเป็นผู้ขอเอง

### 5.2 เลขเอกสารและ snapshot

- [ ] ออกเลขครั้งแรกตอนบันทึกร่าง ไม่ใช่ตอนเปิดฟอร์มหรือตอน submit
- [ ] กดยกเลิกหน้าสร้างก่อนบันทึกต้องไม่ใช้เลข
- [ ] FRD ระบุ `no-gap ✗` ดังนั้นเลขขาดจากร่างที่ยกเลิกอาจเป็น behavior ที่ยอมรับได้
- [ ] สร้างพร้อมกันสองคน เลขต้อง unique ภายในบริษัทและไม่ชนกัน
- [ ] ปิด doc type ITCR → ปุ่มสร้าง disabled และ API ตอบ `DOC_TYPE_INACTIVE`
- [ ] เปลี่ยนชื่อ/ตำแหน่งผู้ขอหลังออกเลข เอกสารเดิมต้องใช้ snapshot เดิม
- [ ] เปลี่ยนชื่อบริษัท/โลโก้หลังออกเลข เอกสารเดิมต้องใช้ header snapshot เดิม
- [ ] format/ปี พ.ศ./running ต้องมาจาก Document Config ไม่ hardcode

### 5.3 DOA และการอนุมัติ

- [ ] จำนวน slot ตอน submit เท่ากับจำนวน step ที่ DOA resolve จริง
- [ ] ค่าเริ่ม 2 ขั้นควรเป็น line manager → IT manager เฉพาะเมื่อ config ปัจจุบันยืนยันเช่นนั้น
- [ ] หาก resolve คนไม่ได้ slot ต้องว่างและให้เลือกเอง ไม่เดาคนให้อัตโนมัติ
- [ ] เปลี่ยน DOA หลัง submit ใบที่ pending ต้องใช้ snapshot เดิม
- [ ] ขั้น 2 กดก่อนขั้น 1 → `NOT_CURRENT_APPROVER`
- [ ] Reject ได้ทุกขั้นแต่ต้องใส่เหตุผล และกลับ draft ทั้งใบ
- [ ] Submit ใหม่หลัง reject ต้อง resolve DOA ใหม่ ไม่ reuse chain เก่า
- [ ] approver ที่ซ้ำหลายขั้น, approver ถูก disable/ลาออก, owner เป็น IT manager และ owner ไม่มีหัวหน้า ต้องไม่เปิดช่องให้ self-approve
- [ ] audit ต้องเรียงเวลาและระบุ actor/step/decision/note ถูกต้อง

- [ ] Pagination 10/25/50, first/last page และ count ถูกหลังข้อมูลเปลี่ยนสถานะ
- [ ] CSV เคารพ filter และ permission ตามรายการที่ผู้ใช้เห็น
- [ ] CSV เป็น UTF-8 BOM ภาษาไทยไม่เพี้ยน, คอลัมน์/ค่า multi-type ถูกต้อง
- [ ] ทดสอบค่าที่ขึ้นต้น `=`, `+`, `-`, `@` เพื่อป้องกัน CSV formula injection

## 6. Business probes ที่ FRD ไม่ได้เขียนเป็น acceptance ตรง ๆ

รายการนี้ควรลองเพราะมีผลธุรกิจสูง แต่ถ้าพฤติกรรมไม่ตรงความคาดหมายให้ถาม BA ก่อนเปิด bug

- Approver คนเดียวถูกตั้งไว้ 2 ขั้น ระบบอนุญาตหรือควรบล็อก
- Approver ลาออก/ถูกปิดบัญชีขณะที่เอกสาร pending จะ reassign อย่างไร
- IT officer ยกเลิกใบของผู้อื่นแล้ว owner/approver ได้รับแจ้งหรือไม่
- การแก้ร่างหลังถูก reject สามารถเปลี่ยน attachment และข้อมูลทุกช่องได้หรือมี field ที่ควร lock
- ใบ approved ต้องมี workflow ต่อให้ IT รับงาน/บันทึกผล/ปิดงานหรือไม่ ซึ่ง FRD รอบนี้ระบุว่า Out of Scope
- retention ของ PDF/attachment/audit และสิทธิ์ดาวน์โหลดหลังพนักงานพ้นสภาพ
- CSV ควรมี PII/เหตุผล reject/cancel หรือไม่ และใครได้รับอนุญาต
- หาก Document Config เปลี่ยน Rev. หรือ template หลังเอกสาร approved เอกสารเก่าควรคงแบบเดิมหรือ render ตามแบบใหม่

## 7. เกณฑ์จัดระดับสิ่งที่พบ

| ระดับ | ตัวอย่างในฟีเจอร์นี้ |
|---|---|
| Critical | ข้ามลำดับอนุมัติ, self-approve, ข้าม tenant, คนไม่มีสิทธิ์เห็น/ดาวน์โหลดข้อมูล, audit สูญหาย, สถานะเสียหาย |
| High | อนุมัติ/ยกเลิกผิดสถานะ, เลขซ้ำ, reject แล้วเลขเปลี่ยน, PDF final ผิดข้อมูล, notification ไปผิดคน, double action |
| Medium | validation ไม่ตรง FRD แต่มีทางเลี่ยง, filter/count/CSV ผิดบางกรณี, history ขาดรายการที่ไม่กระทบ decision |
| Low | ข้อความ, label, format หรือรายละเอียดการแสดงที่ไม่กระทบการทำงาน (รอบนี้ไม่ใช่จุดเน้น) |

Bug ทุกใบต้องมี: role/บัญชี, เลขเอกสาร, precondition, steps สั้นที่ทำซ้ำได้, expected อ้าง FRD section/BR/VR/EC, actual ที่เห็นจริง, เวลา, environment/build และหลักฐาน ห้ามเขียนเพียงว่า “ทำงานผิด”

## 8. ชุดทดสอบขั้นต่ำเมื่อเวลาจำกัด

ถ้ามีเวลาเพียงครึ่งวัน ให้ทำตามลำดับนี้:

1. Flow A ครบวงจร 2 ขั้น
2. Reject ที่ขั้น 2 → กลับร่าง → เปลี่ยน DOA → ส่งใหม่
3. Permission deny ด้วย U5 และ direct URL/PDF/attachment/CSV
4. เปิดสองแท็บทดสอบ stale + ดับเบิล submit/approve
5. Cancel pending และ notification
6. PDF approved + ข้อความยาว + multi-type
7. Document type inactive และเลขเอกสาร concurrent
8. Tenant isolation หากมีบัญชี U6
