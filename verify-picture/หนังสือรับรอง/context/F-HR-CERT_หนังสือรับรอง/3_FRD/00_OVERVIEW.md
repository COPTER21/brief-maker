## §0.3 Scope

### In Scope

1. **คำขอหนังสือรับรอง** — พนักงานยื่นเอง / HR ยื่นแทน (รวม **อดีตพนักงาน**) · ประเภท × ภาษา × จุดประสงค์ × ผู้รับปลายทาง × จำนวนชุด × ช่องทางรับ
2. **บันทึกร่างโดยยังไม่กินเลขที่และยังไม่อ่านต้นทาง**
3. **สายอนุมัติ 2 รูป (1 ขั้น / 2 ขั้น)** จาก DOA engine — เลือก `action_id` ด้วย `pickAction(cert_type)` ⭐ **ไม่มี argument ที่เป็นจำนวนเงิน**
4. **เลขรัน `CERT-YYYY-NNNN` ออกตอนกดส่ง** · immutable · ไม่ reuse
5. ⭐ **จุดตรึงข้อเท็จจริงตอนกดออกหนังสือ (T-06)** — `buildSnap()` อ่าน 4 ต้นทางด้วย `as_of = issue_date` แล้วแช่แข็ง snapshot + `version_id` ทั้ง 4 ก้อน + `template_version_id`
6. **PDF 4 rendition** (ไทย/อังกฤษ × มี/ไม่มีตัวเลขค่าจ้าง) จากแม่แบบ 2 ไฟล์ + สำเนา 4 จุดเหตุการณ์
7. ⭐ **ปฏิเสธการออกเมื่อ `masked = true`** — ไม่มี rendition ที่เว้นช่องตัวเลข
8. **ส่งมอบ/ดาวน์โหลด 3 ช่องทาง** + ร่องรอย ใคร-เมื่อไร-ครั้งที่
9. **lifecycle 9 สถานะ · 12 transition** รวม **เพิกถอน** กับ **ถูกแทนที่** ที่เป็นการ *แทนที่ ไม่ใช่ลบ*
10. **ทะเบียนที่ออกแล้ว append-only** + ค้น 6 ทาง + `verification_code` + คู่ฉบับ + **ธง `upstream_changed_flag`**
11. **read model 1 ตัว** ที่ feature อื่นอ่านได้ (§0.13)
12. **7 NTF business event + 5 CSQ event (SecC ท่อเดียว)**
13. ⭐ **ทางเข้าสำหรับอดีตพนักงาน** (สิทธิตามกฎหมาย · BR-27)
14. **ลงทะเบียน where-used กับต้นทางทั้ง 4**

## §0.7 Multi-Tenant & Security Context

- **`company_id` บังคับส่งไปกับทุก `resolve`** และเป็นคอลัมน์บนทุกตารางของ feature (BR-30 ของ HR Configuration ตระกูลเดียวกัน) · ⭐ **ไม่ทำ UI สลับบริษัทรอบนี้** (`OQ-HR-05`)
- **สิทธิ์มาจาก Policy Center 100 %** — ไม่มีตารางสิทธิ์ในฟีเจอร์นี้ · ไม่มี persona switch บนหน้าจอ (#105)
- **การปิดบังเกิดที่ต้นทาง** — `salary-structure/resolve` คืน `base_amount = null` + `masked = true` เมื่อผู้เรียกไม่มีสิทธิ์ · ⭐ **feature นี้ไม่ปิดบังเอง ไม่ถอดการปิดบังเอง**

### §0.7.1 Data Classification สูงสุด = **Restricted**

### §0.13.4 event ที่ consumer ฟังได้

| event | ท่อ | เมื่อไร | consumer ควรทำอะไร |
|---|---|---|---|
| `cert_issued` | NTF | หนังสือออกสำเร็จ (หลัง render + store) | ESS แสดงใบใหม่ในรายการของพนักงาน |
| `cert_ready_for_pickup` | NTF | ออกแล้วโดยช่องทางรับ = รับที่ HR | แจ้งพนักงานให้มารับ |
| `cert_revoked` | NTF | เพิกถอน | ⭐ **อ่านมุมมองใหม่แล้วเปลี่ยนสถานะที่แสดง — ห้ามลบรายการ** |
| `cert_approved` · `cert_rejected` · `cert_requested` · `cert_pending_issue_overdue` | NTF | ตามสถานะคำขอ | ใช้ในกล่องงาน/แจ้งเตือนเท่านั้น (ยังไม่มีหนังสือ) |
| `cert.issued` · `cert.delivered_external` · `cert.restricted_viewed` · `cert.issue_blocked_masked` · `cert.revoked` | **SecC** | ตาม `CSQ_BRIEF §2` | ⭐ **เป็นของฝ่ายกำกับดูแล ไม่ใช่ของ consumer ทางธุรกิจ** |

> ⭐ **ทั้ง 7 NTF event ยิงหลังการทำงานฝั่งนี้สำเร็จเท่านั้น** — โดยเฉพาะ `cert_issued` ที่ต้องยิงหลัง `store()` สำเร็จ · ยิงก่อนแล้วล้ม = พนักงานได้ข่าวที่ไม่จริง

### §0.13.5 ⭐⭐ ไม่มีทางเข้าสำหรับการเขียนกลับ — **และฟีเจอร์นี้เองก็ไม่เขียนกลับไปที่ใด**

**สองทิศทาง ทั้งคู่ปิด:**

**(ก) consumer เขียนเข้ามาไม่ได้** — feature นี้ไม่เปิด endpoint เขียนให้ consumer เลย (ตระกูลเดียวกับ `F-HR-ONBOARD §0.13.5` · `F-HR-MOVE §0.13.5`)
เหตุผล: **หนังสือที่ออกไปแล้วคือเอกสารที่มีคนเซ็นและอยู่ในมือบุคคลภายนอก** — ถ้าให้ระบบอื่นเขียนเข้ามาได้ ทะเบียน append-only จะไม่เป็นหลักฐานอีกต่อไป
> ข้อยกเว้นเดียวคือ `POST /api/v1/certificate/usage` (CT-4) ซึ่งเป็นการ **ลงทะเบียนว่าใครอ่านอยู่** ไม่ใช่การเขียนข้อมูลของหนังสือ

**(ข) ⭐ feature นี้ไม่เขียนกลับไปที่ต้นทางใดเลย** — ต่างจาก `F-HR-MOVE` ที่มีทางเขียนเดียวไปยัง Salary Structure

| ต้นทาง | ฟีเจอร์นี้เขียนอะไรกลับไหม | ทำไม |
|---|---|---|
| **Employee Master** | ❌ **ไม่มีเลย** | `LD-4C-02` — การขอหนังสือรับรองไม่เปลี่ยนข้อมูลพนักงานแม้แต่ field เดียว |
| **Salary Structure** | ❌ **ไม่มีเลย** | `SS-4` ห้าม CRUD · ⭐ **ฟีเจอร์นี้ไม่ใช่ caller ของ `/rates/from-movement`** (นั่นเป็นของ F-HR-MOVE เท่านั้น) |
| **Employee Movement** | ❌ **ไม่มีเลย** | MOVE §0.13.5 ไม่เปิดทางเขียนให้ consumer |
| **On/Offboard** | ❌ **ไม่มีเลย** | `OB-5` ไม่มี endpoint เขียนสำหรับ consumer |
| **HR Configuration** | ❌ **ไม่มีเลย** | `C-4` ห้าม CRUD · ลิงก์ `#/hr-config/<tab>` เท่านั้น |
| **Document Configuration** | ⚠️ **เรียกใช้บริการ ไม่ใช่เขียนข้อมูล** | `ENG-DOC-NUM.next()` (ขอเลข) · `ENG-DOC-STORE.store()` (ฝากไฟล์) — เป็นการเรียก engine ตามสัญญา ไม่ใช่การ CRUD ตาราง config |

⭐ **ผลของข้อ (ข):** ฟีเจอร์นี้ **ไม่มีทางทำให้ข้อมูลของ feature อื่นผิดได้เลย** — ความเสี่ยงทั้งหมดของมันอยู่ที่ **เอกสารที่มันผลิตออกไป** ไม่ใช่ที่ข้อมูลในระบบ · นี่คือเหตุผลที่ invariant ของฟีเจอร์นี้ (§0.14) เน้นเรื่อง *ความถูกต้องของสิ่งที่พิมพ์* ไม่ใช่ *ความถูกต้องของสิ่งที่บันทึก*

### §0.14.1 ⭐ ทำไม CI-6 ถึงเป็น invariant ไม่ใช่แค่แนวปฏิบัติ

ถ้าเอา **จำนวนเงินเดือนของพนักงาน** ไปเป็นขอบของ matrix ใน DOA (เช่น "เกิน 100,000 ต้องเพิ่มขั้น") จะเกิดผลเสียสองชั้น

1. **ตัวเลขที่มี `effective_date` ถูกคัดลอกไปฝังในทะเบียน DOA** — วันที่ Salary Structure ประกาศกระบอกใหม่ matrix จะเงียบ ๆ ผิดทันที (ผิด `P-8` · `P-8′`)
2. ⭐⭐ **"เงินเดือนของคนคนหนึ่ง" รั่วออกมาเป็นความยาวของสายอนุมัติ** — ใครที่เห็นว่าใบนี้ผ่านกี่ขั้นจะอนุมานช่วงเงินเดือนได้ทันที **โดยไม่ต้องเห็นตัวเลขเลย** · สิ่งที่รั่วไม่ใช่ข้อมูล แต่เป็น **รูปร่างของกระบวนการ** ซึ่ง **ผ่านชั้น masking ทุกชั้นไปได้** — นี่คือ "ทางอ้อม" ที่ `SS-5` ห้ามไว้ตรง ๆ

**สิ่งที่ประกาศไว้แทน:** `has_salary_figure = (cert_type == "salary")` → `action_id` → `GET /doa/resolve` · ทั้งสอง set ใช้ `amount_from = 0` · `amount_to = null` · **ไม่มีค่าจริงเดินทางเข้าไป**
เป็นหลักการเดียวกับพี่น้องสามใบ — ลา (ประเภทการลา) · โอที (ธง `over_cap`) · โยกย้าย (คู่ `sub_type`, `has_pay_change`)

## §0.15 ⭐ Soft-Reference Read Model (LD-4C-02)

- ทุกเส้นข้าม feature เป็น **soft reference** — เก็บ `employee_id` + snapshot ชื่อ · **ไม่มี FK cascade**
- **พนักงานลาออก → หนังสือเก่ายังอ่านได้** พร้อมป้าย "(พ้นสภาพ)" (FN-79)
- **แม่แบบถูกปิดใช้ → หนังสือเก่ายังเปิดได้** เพราะ `template_version_id` ถูกแช่แข็งไว้ (`C-5` soft archive · FN-84)
- **ค่าที่ต้นทางเปลี่ยนภายหลัง → หนังสือเก่าไม่เปลี่ยน** เพราะอ่านจาก snapshot ไม่อ่านสด (BR-23)
- ⭐ **ก่อน "ออกแล้ว" = อ่านสดทุกครั้งที่เปิดดู · ตั้งแต่ "ออกแล้ว" = แสดง snapshot เท่านั้น ไม่อ่านสดอีก** — นี่คือเส้นแบ่งที่ชัดที่สุดของฟีเจอร์นี้
