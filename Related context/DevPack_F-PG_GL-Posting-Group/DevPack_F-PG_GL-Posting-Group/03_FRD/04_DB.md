### T_gl_posting_setup

**Purpose:** One row per General Posting Setup combination (tab 2). Corresponds to BRD §6.3.

| Column | Type | Null | Default | Classification | PII | Description |
|---|---|---|---|---|---|---|
| `id` | uuid | NO | gen_random_uuid() | Internal | — | PK (`setup_id` in BRD §6.3 #1) |
| `tenant_id` | uuid | NO | — | Internal | — | FK → T_tenant; RLS |
| `bus_group` | varchar(20) | NO | — | Internal | — | As-built value set: `DOMESTIC`\|`FOREIGN` (see §0.9/OQ-PG-04 in Overview for gap note). **🔒 locked, together with `prod_group`, only when `used>0`** (IR-PG-01) |
| `prod_group` | varchar(20) | NO | — | Internal | — | As-built value set: `GOODS`\|`SERVICE`. Same combined lock as `bus_group` |
| `sales_account` | varchar(30) | NO | — | Internal | — | Soft-ref to COA `code`, type=income. Always editable |
| `purchase_account` | varchar(30) | NO | — | Internal | — | Soft-ref to COA `code`, type=expense∨asset (see `02_API.md` §2.5 note). Always editable |
| `cogs_account` | varchar(30) | NO | — | Internal | — | Soft-ref to COA `code`, type=expense. Always editable |
| `status` | varchar(10) | NO | `'draft'`\* | Internal | — | enum: `draft`\|`active`\|`inactive` |
| `used` | integer | NO | 0 | Internal | — | Mock today — OQ-PG-03 |
| `doa_field_1..4` | varchar(50) | YES | NULL | Internal | — | Placeholders — always NULL (OB-5) |
| `created_by`/`created_date`/`modified_by`/`modified_date` | — | — | — | Internal | — | Audit fields, same as above table |
| `deleted_at` | timestamp | YES | NULL | Internal | — | Soft-delete marker (R06) |
| `version` | integer | NO | 1 | Internal | — | `[AI-DEFAULT]` optimistic locking — same rationale as above |

**Constraints:**
- PRIMARY KEY (id)
- UNIQUE (tenant_id, bus_group, prod_group) WHERE deleted_at IS NULL — R04
- CHECK (bus_group IN ('DOMESTIC','FOREIGN')) — **`[AI-DEFAULT]` note:** hardcoding this enum at the DB layer matches the as-built HTML, but BRD §14.1/R09 explicitly flags this value set as **DYNAMIC** (pending Admin Panel, OQ-PG-04). Per BRD §14.2 dev instruction: *"schema ของ bus_group/prod_group ให้เป็น lookup table แยก (ไม่ hardcode enum ตรง column)"* — **recommendation: use a lookup table `T_gl_business_group`/`T_gl_product_group` + FK, not a DB CHECK enum**, so Phase 2 (Admin Panel) can add values without a migration. The CHECK constraint shown here documents current as-built values for clarity but should **not** ship as a hard CHECK in the real implementation — see §4.4 Migration Strategy.
- CHECK (status IN ('draft','active','inactive'))
- CHECK (used >= 0)

**Indexes:**
- IDX_gl_posting_setup_tenant_status ON (tenant_id, status)
- IDX_gl_posting_setup_combo ON (tenant_id, bus_group, prod_group)

## §4.3 Relationships (ER Diagram)

```
T_coa_account (F-COA-001, external)
      │  soft-ref (code, no DB FK — see §4.4 note)
      ├──────────────────────────────► T_gl_posting_group.account_1 / account_2
      └──────────────────────────────► T_gl_posting_setup.sales_account / purchase_account / cogs_account

T_gl_posting_group ──(soft-ref by code, future — Vendor/Customer/Bank master not built)──► (not built)
T_gl_posting_setup ──(soft-ref by bus_group×prod_group, future)──► (not built)

T_gl_posting_group + T_gl_posting_setup ──(resolved at post-time, no FK, BR-08)──► GL / Journal Engine (out of scope)

T_user (1) ──< (N) T_gl_posting_group (created_by, modified_by)
T_user (1) ──< (N) T_gl_posting_setup (created_by, modified_by)
T_tenant (1) ──< (N) both tables (RLS isolation)
```

> **No DB-level FK to `T_coa_account`** — intentional soft-reference (per BRD §6.4 note) so that account codes can be validated at write-time (via ENG-PG-01) without creating a hard dependency that would break if COA restructures. Consistency is enforced at the **application layer** (ENG-PG-01), not the DB layer.

### Initial migration
- [ ] Create `T_gl_posting_group`, `T_gl_posting_setup`

- [ ] Add indexes (§4.2)

## §4.6 Data Classification & Sensitive Data

### §4.6.1-4.6.4 — Summary
All fields in both tables are **Internal** classification. No field carries `pii_flag=true`. This is consistent with BRD §16.2 (ISO/IEC 27701 / NIST Privacy Framework marked ❌ Not Applicable — "ไม่มี PII ในฟีเจอร์นี้"). Account codes, group codes, and status are organizational configuration data, not personal data, and not the kind of "salary/board-minutes" data that would warrant Restricted classification per the CUBE 4.0 standard's own examples.

### §4.6.5 Security Bible Domain Mapping
| Domain | Applies because |
|---|---|
| D5 (Financial) | Every field here controls where money posts — audit mandatory on all mutations regardless of classification level being "only" Internal (BRD's Security Preset P4 override — financial risk, not data-sensitivity risk, is why the bar is high) |
| D9 (Audit) | All create/edit/status/delete/import → `T_audit_log` with before/after diff |
| D17 (Multi-Tenant) | RLS on both tables |

### §4.6.6 Linkage with Policy Center
- No Restricted fields → no Restricted Resources registry wiring needed for this feature.
- No PII fields → no PDPA consent scope wiring needed.
- Both tables' `status`/`code`/`combination` mutation events should still flow into whatever "Financial Config Change" audit stream the org's Policy Center expects, per BRD §16.3 S01-07/S06-03 — this is an audit-routing detail, not a classification-level one.
