| `created_at` / `created_by` / `updated_at` / `modified_by` | — | NO | — | Internal / Confidential | —/Yes | audit fields |
| `modified_by_name_snapshot` | varchar(120) | NO | — | **Confidential** | **Yes** | snapshot ชื่อผู้แก้ไข — ใช้ในไทม์ไลน์ประวัติ (EA-13) |
| `version` | integer | NO | 1 | Internal | — | optimistic locking |

**Constraints:**
- PRIMARY KEY (`id`) · FOREIGN KEY (`config_item_id`) REFERENCES `T_hr_config_item`(`id`) **ON DELETE RESTRICT** (ไม่มีการลบอยู่แล้ว — กันพลาด)
- **CHECK (`status` = 'draft' OR `effective_date` IS NOT NULL)** ← **P-1 / BR-01 บังคับที่ระดับ DB**
- CHECK (`version_no` < 2 OR `status` = 'draft' OR char_length(`change_reason`) >= 10) ← BR-02/VR-04
- CHECK (`status` <> 'cancelled' OR char_length(`cancel_reason`) >= 10) ← BR-20/VR-05
- CHECK (`effective_to` IS NULL OR `effective_to` >= `effective_date`)
- CHECK (`status` IN ('draft','scheduled','active','superseded','inactive','cancelled','discarded'))
- **UNIQUE (`tenant_id`,`config_item_id`,`effective_date`) WHERE `status` IN ('scheduled','active','superseded')** ← **BR-03 / VR-02 · ป้องกัน race (PR-1)**
- **EXCLUDE USING gist** ป้องกันช่วง `[effective_date, effective_to]` ทับกันต่อ (`config_item_id`) เมื่อ `status IN ('scheduled','active','superseded')` ← BR-03 ระดับช่วง
- UNIQUE (`tenant_id`,`config_item_id`,`version_no`)

**Indexes:** `IDX_cfgver_item_eff` (`tenant_id`,`config_item_id`,`effective_date` DESC) · **`IDX_cfgver_resolve` (`tenant_id`,`status`,`effective_date`) WHERE `status`='active'** (hot path ของ `resolve()` — SLA-02 P95 ≤300ms) · `IDX_cfgver_status` (`tenant_id`,`status`)

## §4.4 Migration Strategy

### Initial migration (Phase 1)
- [ ] สร้าง 16 ตาราง (`T_hr_config_item` … `T_hr_legal_minimum` รวม join table)
- [ ] เพิ่ม RLS policy ทุกตาราง (`tenant_id`)
- [ ] เพิ่ม index ตาม §4.2 (โดยเฉพาะ `IDX_cfgver_resolve` และ `IDX_payperiod_lookup`)
- [ ] เพิ่ม **EXCLUDE constraint (gist)** ป้องกันช่วง effective ทับกัน (BR-03)
- [ ] Seed `T_hr_config_param` 5 แถว + `T_hr_legal_minimum` 4 แถว
- [ ] **ยืนยันว่าไม่มี DELETE grant** ให้ role ของแอปบนตารางของ feature นี้ (บังคับ BR-07 ที่ระดับสิทธิ์ DB)

### Data migration (go-live — จาก Excel/อีเมล)
- **Source:** ไฟล์ Excel นโยบาย HR + อีเมลประกาศ (ปัจจุบัน)
- **Transformation:** 1 นโยบาย = 1 `T_hr_config_item` + 1 `T_hr_config_version` สถานะ `active` พร้อม `effective_date` **ย้อนหลังตามวันประกาศจริง** · `change_reason` = `"นำเข้าจากระบบเดิม (migration) — <อ้างอิงเอกสาร>"`
- **กติกา:** migration ต้องเขียน audit ด้วย `actor = 'system:migration'` — **ห้าม insert เงียบ** · ถ้าไม่ทราบวันประกาศจริง → ใช้วันเริ่มใช้ระบบ + note ไว้ใน `note`
- **Rollback:** migration ทำใน transaction เดียวต่อ tenant · rollback = drop rows ที่ `created_by='system:migration'` **ก่อน go-live เท่านั้น** (หลัง go-live ห้าม rollback — ใช้เวอร์ชันใหม่แทน)

## §4.6 Data Classification & Sensitive Data (R10)

### §4.6.1 Classification Levels (CUBE 4.0 Standard)

| Level | นิยาม | ใน feature นี้ | UI Behavior | Export Behavior |
|---|---|---|---|---|
| **Public** | เผยแพร่นอกองค์กรได้ | **ไม่มี field ใดเป็น Public** | — | — |
| **Internal** | เห็นได้เฉพาะคนในบริษัท (**default**) | **ค่านโยบายทั้งหมด** (โควตา · อัตรา · ปฏิทิน · รอบ · สถานะ · audit timestamp) | แสดงปกติสำหรับ authenticated user | export ได้ทุก internal role |
| **Confidential** | จำกัด role | **4 field ที่อ้างถึงพนักงาน** — `owner_employee_id`, `created_by`, `modified_by`, `closed_by` (+ snapshot ชื่อ) | mask `***` ถ้า role ไม่ผ่าน Data Masking ของ Policy Center | excluded column ถ้า role ไม่ผ่าน |
| **Restricted** | จำกัดถึงระดับ person (ACL) | **ไม่มี** — feature นี้ไม่มีเงินเดือน/ข้อมูลอ่อนไหวรายบุคคล | — | — |

### §4.6.2 Default Rule
- **Default classification = Internal** — ทุก field ที่ไม่ระบุใน §4.2 ถือเป็น Internal
- **ห้าม default เป็น Public** — และใน feature นี้ **ไม่มี field ใดถูกตั้งเป็น Public เลย** (ตรวจแล้ว)
- Field ที่ ≠ Internal ระบุชัดใน §4.2 (มี 8 คอลัมน์ — 4 employee ref + 4 name snapshot)

### §4.6.3 Enforcement Mapping

| Classification | DB Layer | API Layer | UI Layer | Audit |
|---|---|---|---|---|
| Internal | RLS (`tenant_id`) | JWT auth | — | mutation only |
| Confidential | RLS + column ACL | role check (Policy Center) | mask ถ้าไม่มีสิทธิ์ | view + mutation |
| Restricted | — (ไม่มีใน feature นี้) | — | — | — |

### §4.6.4 PII Overlay
- `owner_employee_id`, `created_by`, `modified_by`, `closed_by` → **Confidential + `pii_flag=true`**
- `*_name_snapshot` → **Confidential + `pii_flag=true`** (ชื่อบุคคล)
- ค่านโยบายทั้งหมด (โควตา/อัตรา/วันหยุด/รอบ) → **Internal + `pii_flag=false`** — เป็นกติกาขององค์กร ไม่ใช่ข้อมูลของบุคคลใด

### §4.6.5 Security Bible Domain Mapping

| Domain | เกี่ยวข้องกับ |
|---|---|
| **D7 (PII)** | 8 คอลัมน์ที่อ้างถึงคน → อยู่ใน PDPA scope · **ห้ามส่งชื่อดิบใน event payload** (ส่ง `employee_id` เท่านั้น — BR-CSQ-03) |
| **D9 (Audit)** | ทุก mutation → `T_audit_log` พร้อม diff (before/after) — **append-only** |
| **D15 (Admin Actions)** | ทุก transition ของ `T_hr_config_version` + การปิด/เปิดงวด บันทึกผู้ทำ + เหตุผล |
| **D17 (Multi-Tenant)** | RLS ทุกตาราง |
| **D5 (Financial)** | **ไม่ trigger** — ไม่มี amount field ใน feature นี้ (มีแต่ multiplier/quota ที่เป็นพารามิเตอร์) — บันทึกไว้ไม่ให้เข้าใจว่าลืม |

### §4.6.6 Linkage with Policy Center
- Field Confidential + PII → register ที่ **Policy Center → Data Classification** + **PDPA consent scope**

## §4.8 Performance Considerations

| Query pattern | Optimization |
|---|---|
| **`resolve(date, company)` — hot path** (50,000–200,000 req/วัน · P95 ≤300ms) | `IDX_cfgver_resolve` partial index (`status='active'`) + join item_company · **read replica** เมื่อเกิน 500 req/s |
| ตรวจ "วันมีผลอยู่ในงวดที่ปิดหรือไม่" (BR-04 · ทุกครั้งที่ publish) | `IDX_payperiod_lookup` (range scan บน `date_from`/`date_to`) |
| list ต่อ tab + as-of | `IDX_cfgver_item_eff` + filter ที่ `effective_date <= as_of` |
| ประวัติเวอร์ชันของ 1 item | `IDX_cfgver_item_eff` (เรียงตาม `effective_date` DESC) |
| where-used ของ 1 item | index บน `T_hr_config_usage(config_item_id)` |
| **จุดกระจุกตัวที่ต้องเฝ้า** | ต้นปีปฏิทิน (ปฏิทินวันหยุด + รอบประเมินปีใหม่มีผลพร้อมกัน) และวันตัดเวลา/วันจ่ายของทุกเดือน |

**Caching:** อนุญาต cache ผลของ `resolve()` **ภายในวันเดียวเท่านั้น** · ต้อง invalidate เมื่อได้รับ `hrconfig.effective` · **ห้าม cache ข้ามวัน** (EA-17 · §0.13.3 C-3)
