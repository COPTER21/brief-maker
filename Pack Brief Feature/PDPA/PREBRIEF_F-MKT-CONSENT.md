# PREBRIEF — F-MKT-CONSENT · ความยินยอม PDPA
> S1 · สถานการณ์การใช้งานจริง + กฎธุรกิจ ก่อนลงมือทำต้นแบบหน้าจอ

## ส่วน A · สถานการณ์การใช้งาน (S-01 … S-20)

### กลุ่ม 1 — วัตถุประสงค์และนโยบาย (lifecycle ขั้น 1)

**S-01 · ผู้ดูแลข้อมูลส่วนบุคคลตั้งวัตถุประสงค์ใหม่**
สร้างวัตถุประสงค์ "ส่งโปรโมชันสินค้า" · ระบุว่าใช้ช่องทางใดได้บ้าง · ตั้งอายุความยินยอม 24 เดือน · แนบข้อความนโยบายเป็นเวอร์ชัน v1

**S-02 · แก้ข้อความนโยบายแล้วออกเวอร์ชันใหม่**
แก้ข้อความในนโยบายของวัตถุประสงค์เดิม → ระบบสร้างเวอร์ชัน v2 · ระบบเตือนว่าความยินยอมที่ให้ไว้กับ v1 จำนวน N รายการ **จะไม่ครอบคลุมเวอร์ชันใหม่** ต้องขอใหม่

**S-03 · ดูว่าวัตถุประสงค์ไหนมีคนยินยอมเท่าไร**
ตารางวัตถุประสงค์แสดงจำนวนคนที่ยินยอมอยู่ · ที่ถอนแล้ว · ที่หมดอายุ · และ % ความครอบคลุม

**S-04 · ปิดวัตถุประสงค์ที่เลิกใช้**
ปิดวัตถุประสงค์ที่ไม่ใช้แล้ว — ความยินยอมเดิมยังอยู่ในทะเบียนเพื่อเป็นหลักฐาน แต่ห้ามสร้างคำขอใหม่

### กลุ่ม 2 — สร้างและส่งคำขอ (lifecycle ขั้น 2–3)

**S-05 · สร้างคำขอความยินยอมให้ลูกค้ารายเดียว**
เลือกเจ้าของข้อมูล + วัตถุประสงค์ (หลายข้อได้) + ช่องทางที่ขอ → ระบบสร้างคำขอ พร้อมลิงก์และคิวอาร์โค้ด

**S-06 · ส่งคำขอทางอีเมล**
กดส่งทางอีเมล → ระบบบันทึกว่าส่งเมื่อไร ไปที่อยู่ไหน · สถานะเปลี่ยนเป็น "รอตอบ"

**S-07 · ส่งซ้ำเพราะลูกค้าไม่ได้รับ**
ส่งคำขอเดิมซ้ำทาง LINE → ระบบบันทึกเป็นการส่งครั้งที่ 2 ในคำขอเดียวกัน ไม่สร้างคำขอใหม่

**S-08 · คัดลอกลิงก์ไปส่งเอง**
คัดลอกลิงก์หรือดาวน์โหลดคิวอาร์โค้ดไปใช้ในช่องทางอื่น → ระบบบันทึกว่ามีการนำลิงก์ออกไปเมื่อไร

**S-09 · ดาวน์โหลดแบบฟอร์ม PDF**
สำหรับลูกค้าที่ต้องเซ็นกระดาษ — ดาวน์โหลด PDF ที่มีข้อความนโยบายเวอร์ชันปัจจุบันฝังอยู่

### กลุ่ม 3 — ยืนยันและหลักฐาน (lifecycle ขั้น 4)

**S-10 · ลูกค้าเซ็นยินยอมผ่านลิงก์**
สถานะคำขอเปลี่ยนเป็น "ตอบแล้ว" · สร้างรายการในทะเบียนความยินยอม · เก็บหลักฐานครบ 5 อย่าง

**S-11 · ลูกค้าเลือกยินยอมบางวัตถุประสงค์**
คำขอมี 3 วัตถุประสงค์ ลูกค้ายินยอม 2 ปฏิเสธ 1 → ทะเบียนบันทึกแยกรายวัตถุประสงค์ ไม่ใช่ทั้งก้อน

**S-12 · ดูหลักฐานของความยินยอมหนึ่งรายการ**
เปิดดูแล้วเห็นครบ: เวลาที่เซ็น · ช่องทางที่ส่งคำขอ · วิธียืนยันตัวตน · เวอร์ชันนโยบายที่เห็นตอนนั้น · ไอพีและอุปกรณ์

### กลุ่ม 4 — ทะเบียนและการจัดการ (lifecycle ขั้น 5–7)

**S-13 · ดูทะเบียนความยินยอมทั้งหมด**
ตาราง เจ้าของข้อมูล × วัตถุประสงค์ × ช่องทาง พร้อมสถานะและวันหมดอายุ · กรองได้ทุกมิติ

**S-14 · ค้นหาว่าลูกค้ารายหนึ่งยินยอมอะไรไว้บ้าง**
พิมพ์ชื่อหรือรหัสลูกค้า → เห็นทุกรายการของคนนั้นในที่เดียว

**S-15 · ถอนความยินยอมแทนลูกค้า**
ลูกค้าโทรมาขอถอน → เจ้าหน้าที่ถอนให้ พร้อมกรอกเหตุผทและระบุว่าลูกค้าแจ้งมาทางไหน · มีผลทันที

**S-16 · ดูรายการที่ใกล้หมดอายุ**
เห็นรายการที่จะหมดอายุใน 30 วัน เรียงตามวันหมดอายุ · กดสร้างคำขอต่ออายุได้จากตรงนั้น

**S-17 · ต่ออายุความยินยอม**
สร้างคำขอต่ออายุจากรายการที่ใกล้หมด → เป็นคำขอใหม่ที่อ้างรายการเดิม

**S-18 · ดูประวัติของความยินยอมหนึ่งรายการ**
เห็นทุกการเปลี่ยนสถานะเรียงเวลา: ขอ → ยินยอม → ถอน → ขอใหม่ → ยินยอม พร้อมเหตุผลทุกครั้ง

### กลุ่ม 5 — ตรวจสิทธิ์ (lifecycle ขั้น 8)

**S-19 · นักพัฒนาแคมเปญทดลองตรวจสิทธิ์**
ใส่เจ้าของข้อมูล + วัตถุประสงค์ + ช่องทาง → เห็นคำตอบเหมือนที่ API จะให้ พร้อมเหตุผลว่าทำไมส่งได้/ไม่ได้ และตัวอย่าง JSON

**S-20 · ตรวจคนที่ไม่เคยถูกขอความยินยอมเลย**
ได้คำตอบว่า `ส่งไม่ได้` สถานะ `ยังไม่เคยขอ` — ไม่ใช่ข้อความผิดพลาด และไม่ใช่ `ปฏิเสธ`

## ส่วน B · กฎธุรกิจ (BR-01 … BR-22)

### กลุ่มโครงสร้าง
| ID | กฎ |
|---|---|
| BR-01 | ความยินยอมเป็นคู่ **เจ้าของข้อมูล × วัตถุประสงค์ × ช่องทาง** — คู่นี้ต้องไม่ซ้ำในทะเบียน (มีได้รายการเดียวที่ยังมีผล) |
| BR-02 | ช่องทางที่รองรับ: อีเมล · ข้อความสั้น (SMS) · LINE · โทรศัพท์ · ไปรษณีย์ |
| BR-03 | วัตถุประสงค์แต่ละข้อกำหนดเองว่าใช้ช่องทางใดได้บ้าง — ขอความยินยอมช่องทางที่วัตถุประสงค์ไม่รองรับไม่ได้ |
| BR-04 | **ค่าเริ่มต้นคือไม่อนุญาต** — ไม่มีรายการในทะเบียน = ส่งไม่ได้ |
| BR-05 | นโยบายของวัตถุประสงค์เป็น **เวอร์ชัน** · แก้ข้อความ = ออกเวอร์ชันใหม่ · เวอร์ชันเดิมแก้ไม่ได้ |
| BR-06 | ความยินยอมผูกกับ**เวอร์ชันนโยบายที่เจ้าของข้อมูลเห็นตอนเซ็น** — เวอร์ชันใหม่ไม่ครอบคลุมโดยอัตโนมัติ |

### กลุ่มวงจรชีวิต
| ID | กฎ |
|---|---|
| BR-07 | สถานะความยินยอม 5 ค่า: **ยังไม่เคยขอ · รอตอบ · ยินยอม · ไม่ยินยอม · ถอนแล้ว** และสถานะที่คำนวณเพิ่ม: **หมดอายุ** |
| BR-08 | **การไม่ตอบไม่ใช่การปฏิเสธ** — คำขอที่เกินกำหนดตอบกลับกลายเป็น "คำขอหมดอายุ" ไม่ใช่ "ไม่ยินยอม" |
| BR-09 | ถอนความยินยอมได้ทุกเมื่อ **ไม่ต้องผ่านการอนุมัติใด ๆ** และมีผลทันทีในคำขอถัดไป |
| BR-10 | การถอนต้องระบุ **เหตุผล** และ **ช่องทางที่ลูกค้าแจ้งมา** |
| BR-11 | ความยินยอมมีวันหมดอายุตามอายุที่วัตถุประสงค์กำหนด (ค่าเริ่มต้น 24 เดือน) |
| BR-12 | รายการที่ใกล้หมดอายุภายใน 30 วัน แสดงสัญลักษณ์เตือน **ไม่บล็อก** การใช้งาน |
| BR-13 | ต่ออายุ = สร้างคำขอใหม่ที่อ้างรายการเดิม — **ไม่ใช่**การแก้วันหมดอายุของรายการเดิม |
| BR-14 | ปิดวัตถุประสงค์แล้ว ห้ามสร้างคำขอใหม่ · ความยินยอมเดิมยังอยู่ในทะเบียนเป็นหลักฐาน |

### กลุ่มหลักฐานและร่องรอย
| ID | กฎ |
|---|---|
| BR-15 | ทุกความยินยอมที่ได้รับต้องมีหลักฐานครบ 5 อย่าง: เวลาที่ตอบ · ช่องทางที่ส่งคำขอ · วิธียืนยันตัวตน · เวอร์ชันนโยบาย · ไอพีและอุปกรณ์ |
| BR-16 | ประวัติเป็นแบบ **เพิ่มอย่างเดียว** — เขียนในทรานแซกชันเดียวกับการเปลี่ยนสถานะ · แก้และลบไม่ได้ |
| BR-17 | ไม่มีการลบถาวรทั้งความยินยอม คำขอ และวัตถุประสงค์ |
| BR-18 | คำขอหนึ่งใบส่งซ้ำได้หลายครั้งหลายช่องทาง — บันทึกทุกครั้งเป็นรายการส่ง ไม่สร้างคำขอใหม่ |

### กลุ่ม API และการเชื่อมต่อ
| ID | กฎ |
|---|---|
| BR-19 | `/consent/resolve` **ตอบ 200 เสมอ** — คนที่ไม่เคยถูกขอได้ `allowed:false` + `status:"never_asked"` ไม่ใช่ 404 |
| BR-20 | สัญญาผลลัพธ์ของ `/consent/resolve` **ล็อกแล้ว** — เพิ่มฟิลด์ได้ ห้ามเปลี่ยนชื่อหรือความหมายของฟิลด์เดิม |
| BR-21 | ผู้เรียกแคชคำตอบได้ **ไม่เกิน 5 นาที** และ **การถอนต้องล้างแคชทันที** — สั้นกว่าฟีเจอร์อื่นเพราะการส่งผิดมีผลทางกฎหมาย |
| BR-22 | ปลายทาง `/consent/*` ต้องขึ้นทะเบียนในด่านบังคับใช้สิทธิ์และผ่านการตรวจ 4 ขั้น |

### กลุ่ม CSQ (ผลกระทบ 7 ด้าน)
| ID | กฎ |
|---|---|
| BR-CSQ-01 | ทุก event ที่ประกาศไว้ยิงเข้า 7C Engine ผ่าน `POST /csq/events` ตาม Event Envelope — **ห้ามเขียนผลรายท่อลงตารางของฟีเจอร์นี้** |
| BR-CSQ-02 | envelope ต้องมี `idempotency_key` ที่ไม่ซ้ำต่อ (ฟีเจอร์, รายการอ้างอิง, การกระทำ) — กันยิงซ้ำตอนลองใหม่ |
| BR-CSQ-03 | payload **ห้ามพกข้อมูลชั้นจำกัดแบบดิบ** — ปิดบังที่ผู้ส่งก่อน |
| BR-CSQ-04 | การกลับรายการต้องส่ง event ที่มี `reversal_of` ชี้ event เดิม — ห้ามลบหรือแก้ผลเดิม |
| BR-CSQ-05 | ฟีเจอร์นี้ **ไม่ประกาศและไม่คำนวณ** ท่อ OC และท่อ DC ระดับเอกสาร (มาจาก Operation Process และ DOA engine) |

## ส่วน C · สิ่งที่ต้องไม่เกิด (กันหลงทาง)

1. ❌ ทำความยินยอมคุกกี้บนเว็บไซต์ (LOCK-05)
2. ❌ ใส่สายอนุมัติภายในก่อนส่งคำขอ (LOCK-04)
3. ❌ ส่งอีเมล/LINE จริงจากฟีเจอร์นี้
4. ❌ **คำนวณมูลค่าใด ๆ** หรือสร้างคอลัมน์เก็บผลรายท่อ (LOCK-CSQ-04/05)
5. ❌ **วาดการ์ดผล 7 ท่อบนหน้าจอ** (LOCK-CSQ-06)
6. ❌ ประกาศท่อ OC หรือ DC-จากการอนุมัติ หรือ SC (LOCK-CSQ-01/02/03)
7. ❌ ใช้ธง opt-out เดียวต่อคน (แบบ Odoo) แทนคู่สามมิติ
8. ❌ ให้ "ไม่ตอบ" นับเป็น "ไม่ยินยอม"
9. ❌ บล็อกการส่งด้วยตัวเอง — ที่นี่ตอบอย่างเดียว
10. ❌ ใช้ wizard Pattern Q (LOCK-07)
