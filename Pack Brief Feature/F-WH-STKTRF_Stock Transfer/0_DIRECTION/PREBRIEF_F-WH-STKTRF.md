## 1. สรุป + ผู้ใช้ + สิทธิ์

### 1.1 ทำอะไร [แผน]

**Stock Transfer = ใบย้ายสินค้า** — เอกสารที่บอกว่า *ของชิ้นไหน จำนวนเท่าไหร่ ย้ายจากที่เก็บไหน ไปที่เก็บไหน* แล้วทำให้ **ยอดคงเหลือราย bin ขยับตามจริง** โดยไม่แตะมูลค่ารวมของกิจการ

สิ่งที่ feature นี้ **ทำ**:
1. เปิดใบย้าย ระบุ **คลัง/bin ต้นทาง → คลัง/bin ปลายทาง** หลายบรรทัดในใบเดียว
2. **ส่งอนุมัติตามมูลค่า** (DOA slot picker คนจริง) ก่อนของจะขยับ
3. **ส่งของออกจากต้นทาง** — ยอดออกจาก bin ต้นทางทันที
4. **ปลายทางยืนยันรับ** — ยอดเข้า bin ปลายทาง แล้ว **ปิดใบ**
5. จัดการกรณี **รับไม่ครบ / ของหายระหว่างทาง** ให้ยอดระหว่างทางไม่ค้างลอย
6. **กลับรายการ (reversal)** เมื่อย้ายผิด — ไม่มีการลบ movement

สิ่งที่ feature นี้ **ไม่ทำ** (ดู §3.6): ไม่ปรับยอด · ไม่นับสต๊อก · ไม่แก้ผัง location · ไม่ post JE จริง

### 1.2 ★★ 2 โหมด — ต่างกันตรงไหน (OB-5 · BASELINE G-02 · ข้อที่พลาดบ่อยที่สุด)

| | **โหมด A · ย้ายภายในคลังเดียวกัน** | **โหมด B · ย้ายข้ามคลัง/สาขา** |
|---|---|---|
| **เงื่อนไขที่ทำให้เป็นโหมดนี้** | คลังต้นทาง **=** คลังปลายทาง (ข้าม bin / ข้ามโซนภายในคลังเดียว) | คลังต้นทาง **≠** คลังปลายทาง |
| **ระบบตัดสินโหมดเมื่อไหร่** | **อัตโนมัติ** ตอนเลือกคลังต้นทาง+ปลายทางที่ wizard step 1 — **ผู้ใช้ไม่ได้เลือกโหมดเอง** | เหมือนกัน |
| **ผ่าน in-transit ไหม** | ❌ **ไม่ผ่าน** | ✅ **ผ่านเสมอ** (`WH-TRN` · `OQ-TRF-01`) |
| **จำนวนจังหวะ** | **1 จังหวะ** — กด "ย้าย" ครั้งเดียวจบ | **2 จังหวะ** — (1) ส่งออกจากต้นทาง (2) ปลายทางยืนยันรับ |
| **movement ที่เกิด (ต่อบรรทัด)** | **1 เส้น**: `bin ต้นทาง → bin ปลายทาง` | **2 เส้น**: `bin ต้นทาง → in-transit` แล้ว `in-transit → bin ปลายทาง` |
| **ใครกดปิดใบ** | ผู้ปฏิบัติงานคลังต้นทาง (คลังเดียว) | ★ **คลังปลายทาง** เป็นคนกดรับ ใบจึงปิด (OB-4) |
| **สถานะระหว่างกลาง** | ไม่มี — `อนุมัติแล้ว` → `ย้ายสำเร็จ` | ★ **`ส่งออกแล้ว — อยู่ระหว่างทาง`** และอาจมี `รับบางส่วน` |
| **รับไม่ครบเป็นไปได้ไหม** | ❌ ไม่มีช่วงกลาง จึงไม่มีเคสนี้ | ✅ **เป็นได้** — ส่วนต่างค้าง in-transit ต้องสะสาง (§2 S-06..S-09) |
| **เอกสารพิมพ์** | ใบย้ายภายใน (1 หน้า) | ใบย้าย + **ช่องลงชื่อผู้รับปลายทาง** (คนขับถือไป) |
| **scenario ที่เป็นตัวแทน** | **S-02** | **S-01 (ครบ)** · S-06 (ไม่ครบ) · S-07 (ของหาย) · S-08 (ตีกลับ) |

> ★ **กติกาเหล็ก**: โหมดถูกตัดสินจาก *คลัง* ไม่ใช่จาก *ระยะทาง* — ย้ายข้ามโซนคนละมุมคลังเดียวกันก็ยังเป็นโหมด A · ย้ายข้ามคลัง 2 แห่งที่อยู่ติดกันก็ยังเป็นโหมด B (BR-03)

## 3. Data — full data dict

### ★ 3.0 LOCATION MODEL — อ้างจาก PREBRIEF_F-WH-PUTAWAY §3.0 (สัญญากลาง · **ห้ามนิยามใหม่ ห้ามแตะ**)

> feature นี้ **ไม่มีสิทธิ์เพิ่ม/แก้/ตีความใหม่** — ด้านล่างคือการยกมาอ้างเพื่อความสะดวก ของจริงอยู่ที่ Putaway §3.0 (OB-12)

#### 3.0.1 โครงสร้าง 3 ระดับ (ยกมาอ้าง)
```
Warehouse (คลัง/สาขา)   WH-BKK-01 · WH-CNX-01 · WH-TRN (in-transit เสมือน — ★ feature นี้เป็นคนใช้)
   └── Zone (โซน)        A · B · C · ST (staging) · QA (quarantine) · DM (ของเสีย) · TR (ระหว่างทาง)

```

#### 3.0.2 `location_type` — สิทธิ์ของ **StockTransfer** ต่อประเภท (ยกมาอ้าง + ระบุสิทธิ์ตัวนี้)

**กติกาข้ามประเภทที่ยกมาบังคับใช้ (Putaway §3.0.2 — ห้ามแก้):**
1. `quarantine` ไปไหนไม่ได้นอกจาก quarantine ด้วยกัน หรือออกด้วย RTV
2. ★ `in-transit` ห้ามมีใครเขียนตรง ๆ **นอกจาก StockTransfer** — **ข้อนี้คือใบอนุญาตของ feature นี้**
3. `damage` เขียนได้เฉพาะ StockAdj
4. `staging + storage + in-transit` = ทรัพย์สินใช้ได้ · `quarantine + damage` = กันออกจากยอดขายได้
   → ★ **ผลคือ: ของที่อยู่ `in-transit` ยังเป็นทรัพย์สินของกิจการ** แค่ยังเบิกที่ปลายทางไม่ได้ (BR-15)

#### 3.0.3 ฐานยอดที่ feature นี้อ่าน (Putaway §3.4)
**ยอดคงเหลือราย bin** = `Σ movement เข้า − Σ movement ออก` ต่อคู่ **(bin, สินค้า)** — ตัวเลขนี้คือ "ยอดคงเหลือ (snapshot)" ที่ §3.2 ดึงมาใช้ · **ยอดที่ `TR-*` = ของที่ยังอยู่ระหว่างทาง** (§3.3 KPI)

#### 3.0.4 ชุด location ตั้งต้น + ★ in-transit bin ที่ feature นี้ใช้
ใช้ **ชุดเดียวกับ Putaway §3.0.5 เป๊ะ** — ห้ามสร้างชุดใหม่:
`WH-BKK-01`: `ST-DOCK-01/02` · `A-01-01-A`…`A-02-04-C` · `B-01-01-A`…`B-03-02-B` · `C-01/C-02` · `QA-01` · `DM-01`

### 5.2 Movement lifecycle (append-only · สืบทอด StockAdj §5.2)
```
[โหมด A · กด "ย้าย"]     ──▶ movement "ย้ายภายในคลัง"  bin→bin           (แถวถาวร ห้ามแก้ ห้ามลบ)
[โหมด B · กด "ส่งออก"]   ──▶ movement "ย้ายออก"        bin→TR-*
[โหมด B · ยืนยันรับ]      ──▶ movement "ย้ายเข้า"        TR-*→bin          (ผูกกลับ movement ขาส่งเสมอ)
[ตัดส่วนต่าง (DOA จุด 2)] ──▶ movement "ตัดส่วนต่างระหว่างทาง"  TR-*→—
[ตีกลับคืนต้นทาง]         ──▶ movement "ย้ายกลับต้นทาง"  TR-*→bin ต้นทางเดิม
[กลับรายการ]              ──▶ movement "กลับรายการ<ชนิดเดิม>" ทิศตรงข้าม ครบทุกเส้นของใบ
                                └── ผูก soft link 2 ทางกับแถวเดิมเสมอ
```

**สมการที่ต้องเป็นจริงเสมอ (invariant · โหมด B):**
`จำนวนที่ย้าย = รับแล้วสะสม + ส่วนต่างที่ตัดแล้ว + ตีกลับคืนต้นทาง + คงค้างระหว่างทาง`
→ ★ **ยอดที่ `TR-*` ไม่มีวันค้างลอยโดยไม่มีใบอ้างอิง** (gap G-03 ปิด)

## 7. Data behaviour

- **เลขรัน**: `TRF-YYYY-NNNN` จาก **ENG-DOC-NUM** ตาม config ที่ประกาศใน `DOCCFG_BRIEF` — ปี **ค.ศ.** · ออกเลขตอน**ส่งอนุมัติ** (BR-09) · ห้าม hardcode ในหน้า feature (OB-8)
- **สำเนาเอกสาร**: ผ่าน **ENG-DOC-STORE** ตาม snapshot policy ใน doccfg — feature ไม่เก็บเอง
- **Soft reference (LD-4C-02)**: Item · UOM · Warehouse/Zone/Bin · Cost Center · ผู้อนุมัติ · ผู้รับปลายทาง = **picker ไม่ FK validate nullable** · เก็บข้อความ ณ เวลาที่เลือกไว้ด้วย (BR-28)
- **Soft archive**: ไม่มี hard delete ทุกระดับ — ใบยกเลิก/ตีกลับยังอยู่ · movement append-only (BR-25)
- ★ **ยอดคงเหลือทุกที่เป็นค่า derive จาก movement** — ไม่มีตารางยอดที่แก้มือได้ (สืบทอด Putaway §3.4 · StockAdj §3.0.3) · **ทางเดียวที่แก้ยอดได้คือ StockAdj** (BR-31)
- ★ **ยอด `in-transit` เป็นยอดจริงในระบบ ไม่ใช่ตัวเลขชั่วคราวในหน้าจอ** — อ่านได้จากมุมมอง "ของที่อยู่ระหว่างทาง" และตรวจสอบได้ด้วย invariant §5.2
