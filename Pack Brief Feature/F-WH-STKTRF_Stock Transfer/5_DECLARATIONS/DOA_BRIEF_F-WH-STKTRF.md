# DOA_BRIEF — F-WH-STKTRF · Stock Transfer (ใบย้ายสินค้า)

> ใบประกาศ — feature **ประกาศ** ว่ามีการอนุมัติแบบไหน · **ห้าม hardcode สายอนุมัติใน feature**
> คนเอาใบนี้ไปตั้งค่า entry จริงที่หน้า **DOA กลาง (F-DLG-001)** → `wire_status: pending → wired`
> ⚠️ **LOCK ที่เหนือกว่า template เดิมของ skill**: `DOA-UI-LOCK 2026-08-17` (GOLDEN_RULES §3) —
> ตอน submit **UI ต้องให้เลือกคนจริงต่อ slot** (avatar + ตำแหน่ง + ชื่อ) · **ห้ามแสดง role ID บนหน้าจอ**
> role/ตำแหน่งใน matrix ข้างล่างเป็น **นิยามฝั่งทะเบียน DOA** (ใช้กำหนดว่า slot นั้นดึงคนจากกลุ่มไหน) — ไม่ใช่สิ่งที่ผู้ใช้เห็น
> ★ **feature นี้มี 2 จุดตัดสินใจ + 3 สาย** (Q1 = หลายสาย → ใช้ `actions[]`)

## 1. Identity

| ช่อง | ค่า |
|---|---|
| feature_id | `F-WH-STKTRF` (fid F083) |
| ชื่อ | Stock Transfer — ใบย้ายสินค้า (ย้ายคลัง/สาขา) |
| module | Warehouse (WH) |
| platform | CUBE NATIVE — Web |
| approval_scope | `document_sign` |
| **มีวงเงิน** | ✅ **มี** — ชั้นอนุมัติเปลี่ยนตาม **มูลค่าของที่ย้าย** |
| ★ **ฐานวงเงิน สาย A1/A2** | **`Σ (จำนวนที่ย้าย × ต้นทุนอ้างอิง)` = "มูลค่ารวมที่ย้าย" — เป็นค่าบวกเสมอ** (PREBRIEF §3.3 · `OQ-TRF-02`) |
| ★ **ฐานวงเงิน สาย B1** | **`Σ (จำนวนส่วนต่างที่ตัด × ต้นทุนอ้างอิง)` = "มูลค่าส่วนต่างที่ตัดทิ้ง"** (PREBRIEF §3.3 · BR-18) |
| ★ **มิติเพิ่ม** | **โหมดการย้าย** (`ภายในคลัง` / `ข้ามคลัง`) — แยกเป็นคนละสาย (A1 / A2) |

| wire_status | `pending` |

**เหตุผลที่ Stock Transfer ต้องมี DOA:** การย้ายสินค้าไม่ทำให้มูลค่ารวมของกิจการเปลี่ยน **แต่เปลี่ยน "ผู้ครอบครอง"** — ของออกจากความรับผิดชอบของคลังหนึ่งไปอีกคลังหนึ่ง และในโหมดข้ามคลัง **มีช่วงที่ของไม่อยู่ในมือใครเลย (in-transit)** ซึ่งเป็นจุดที่ของหายได้จริง (PREBRIEF S-07) · ERP มาตรฐาน (SAP release strategy · D365 workflow) จึงบังคับอนุมัติก่อนของขยับ (BASELINE M-11)

★ **ทำไมต้องแยกสาย A1 (ภายในคลัง) ออกจาก A2 (ข้ามคลัง):** ความเสี่ยงต่างกันคนละระดับ — ย้ายข้ามชั้นวางในคลังเดียวกันของยังอยู่ในสายตาคนเดิม แต่ย้ายข้ามสาขาของขึ้นรถออกไปจากพื้นที่ **มีช่วง in-transit ที่ตรวจสอบไม่ได้** · การใช้จุดตัดชุดเดียวกันจะทำให้ **การย้ายในคลังถูกคุมเข้มเกินจำเป็น หรือการย้ายข้ามสาขาหลวมเกินไป** อย่างใดอย่างหนึ่งเสมอ

★ **ทำไมการตัดส่วนต่าง (B1) ต้องแยกเป็นสายที่ 3:** เพราะมันคือ **การยอมรับความสูญเสียจริง** — ต่างจาก A1/A2 ที่แค่ย้ายที่เก็บ · ถ้าไม่มีชั้นอนุมัติแยก คนที่รับของปลายทางจะสามารถ "ปิดใบให้จบ ๆ" ด้วยการกดว่าของหาย โดยไม่มีใครถ่วงดุล — นี่คือช่องทุจริตที่ตรงที่สุดของ feature นี้

## 2. Approval Actions

| # | Action | Trigger | สถานะก่อน | ผลเมื่ออนุมัติครบ | ผลเมื่อตีกลับ | ผลเมื่อยกเลิก |
|---|---|---|---|---|---|---|
| **A1** | **ส่งอนุมัติใบย้าย — โหมดภายในคลัง** | ผู้ใช้กด "ส่งอนุมัติ" ที่ wizard step 5 · หัวใบ `โหมด = ภายในคลัง` | `ร่าง` | `อนุมัติแล้ว` — **ปุ่ม "ย้าย" เปิด (ของยังไม่ขยับ)** | กลับ `ร่าง` แก้ต่อได้ · เลขที่ TRF เดิมคงอยู่ | `ยกเลิก` (ปลายทาง · ไม่มี movement) |
| **A2** | **ส่งอนุมัติใบย้าย — โหมดข้ามคลัง/สาขา** | เหมือน A1 แต่หัวใบ `โหมด = ข้ามคลัง` | `ร่าง` | `อนุมัติแล้ว` — **ปุ่ม "ส่งออก" เปิด (ของยังไม่ขยับ)** | กลับ `ร่าง` · เลขที่เดิมคงอยู่ | `ยกเลิก` |
| **B1** | ★ **อนุมัติการตัดส่วนต่างระหว่างทาง (ของหาย/เสียหาย)** | ผู้ใช้**คลังปลายทาง**เลือกการจัดการส่วนต่าง = `ของหาย/เสียหายระหว่างทาง` แล้วกดขออนุมัติตัด (PREBRIEF §6.4 · BR-18) | `ส่งออกแล้ว` / `รับบางส่วน` | เกิด movement `ตัดส่วนต่างระหว่างทาง` → ใบ = **`ปิดใบพร้อมส่วนต่าง`** | ส่วนต่างยังค้างที่ in-transit · ใบยังเปิด — กลับไปเลือกทางจัดการใหม่ได้ (รอรับเพิ่ม / ตีกลับคืนต้นทาง) | — (ยกเลิกใบไม่ได้แล้วหลังส่งออก · BR-22) |
| — | **ส่งอนุมัติซ้ำหลังถูกตีกลับ** | แก้แล้วกดส่งอนุมัติอีกครั้ง | `ร่าง` | `อนุมัติแล้ว` (สายใหม่ตาม **มูลค่าใหม่และโหมดใหม่** — BR-DOA-05) | กลับ `ร่าง` | `ยกเลิก` |

> ตีกลับ / ยกเลิก / ตัดส่วนต่าง / ตีกลับคืนต้นทาง / กลับรายการ = **บังคับกรอกเหตุผล** (PREBRIEF BR-13/BR-18/BR-19/BR-21/BR-26)
> **ไม่มี** DOA ที่ transition `อนุมัติแล้ว → ส่งออกแล้ว` และ `ส่งออกแล้ว → ปิดใบ (รับครบ)` — การส่งของและการรับของเป็น **งานปฏิบัติการ** ไม่ใช่การอนุมัติซ้ำ `[AI-DRAFT]` (เหมือนที่ StockAdj ไม่มี DOA ที่ `อนุมัติแล้ว → ผ่านรายการ`)
> **ไม่มี** DOA แยกสำหรับ `ตีกลับคืนต้นทาง` — **ของไม่ได้หาย มันกลับเข้า bin ต้นทางครบ** จึงคุมด้วยสิทธิ์ (คนคลังปลายทาง) + เหตุผลบังคับแทน → ดู DOA-Q2
> **ไม่มี** DOA แยกสำหรับ `กลับรายการ` — คุมด้วยสิทธิ์ (หัวหน้าคลังต้นทาง) + เหตุผลบังคับ (สอดคล้อง StockAdj) → ดู DOA-Q3

**Business Rule ที่ต้องมีเสมอ (DOA มาตรฐาน + ของ feature นี้)**

| BR-DOA-01 | ส่งอนุมัติได้เฉพาะสถานะ `ร่าง` |
| BR-DOA-02 | สายอนุมัติ resolve ตอนส่ง แล้ว **freeze** — แก้ DOA ทีหลังไม่กระทบใบที่ส่งไปแล้ว |

| BR-DOA-05 | แก้ยอด/แก้คลัง (โหมดเปลี่ยน) หลังถูกตีกลับ → **ต้อง re-resolve สายใหม่** ทั้งจำนวนเงินและสาย A1/A2 |
| ★ BR-DOA-06 | ★ **ผู้ที่กด "ส่งออก" (ต้นทาง) เซ็นอนุมัติสาย B1 (ตัดส่วนต่าง) ไม่ได้** — สาย B1 ต้องมาจากฝั่งปลายทาง + ชั้นเหนือขึ้นไป (ขยาย segregation of duty ให้ครอบคลุมช่วง in-transit · PREBRIEF BR-14) |
