# Feature Check Report

รายงานนี้คือ "ใบรับรองผลตรวจ" ที่ผู้ตรวจลงชื่อรับผิดชอบ — เป้าหมายคือ **ผู้ตรวจพิมพ์น้อยที่สุด แต่รายงานครบและอ่านจบใน 1 นาที**. การคำนวณผล การเรียงลำดับ การเติม checklist มาตรฐาน และหน้าตา ทั้งหมดอยู่ใน `scripts/build_report.py` — งานของ Claude คือแปลงสิ่งที่ผู้ตรวจเล่าให้เป็น `report.json` ให้ถูกต้องตามจริง

## Input ที่ต้องมี (ขั้นต่ำ)

| ต้องมี | ไม่มีก็ได้ (แสดง "—") |
|---|---|
| feature (รหัสหรือชื่อ) · ผู้ตรวจ · สิ่งที่ตรวจ + สิ่งที่เจอ | module · env/build · Dev · ผู้ทบทวน · FRD/TC อ้างอิง · สิ่งที่ไม่ได้ตรวจ · ข้อเสนอแนะ |

ขาดเฉพาะ "ต้องมี" → ถามคำถามเดียวรวบทุกข้อที่ขาด. ขาดแค่ช่อง optional → ออกรายงานเลย ไม่ถาม. วันที่ไม่บอก = วันนี้ · รอบไม่บอก = 1

ถ้า user แนบ FRD / Test Case มาด้วย → ดึงรายการ Logic จาก TC/กฎใน FRD มาเป็นแถว แล้วใส่ผลตามที่ผู้ตรวจเล่า (ข้อที่ผู้ตรวจไม่ได้พูดถึง = `na` ไม่ได้ตรวจ)

## ขั้นตอน

1. อ่านสิ่งที่ผู้ตรวจส่งมา (ข้อความ / ภาพ / ไฟล์) แล้วแยกเป็น 4 ถัง: Logic · UI · UX · Bug (+ ข้อเสนอแนะ)
2. เขียน `report.json` ตาม `references/json-schema.md` (ดูตัวอย่างเต็มที่ `assets/sample_report.json`) ไว้ใน working dir เดียวกับรูปหลักฐาน
3. รัน `python3 scripts/build_report.py report.json --out /mnt/user-data/outputs` — script พิมพ์ผลตัดสินกลับมาเป็น JSON
4. เปิดไฟล์ด้วย Playwright ตรวจ `pageerror = 0` และไม่มี scroll แนวนอน
5. `present_files` แล้วตอบในแชทสั้น ๆ 3 บรรทัด: ผลตัดสิน · เหตุผล · สิ่งที่ต้องทำต่อ

## กฎการแปลงให้ถูกต้องตามจริง (สำคัญที่สุด)

รายงานนี้มีคนลงชื่อรับผิดชอบ ถ้า Claude เติม "ผ่าน" เองในสิ่งที่ไม่ได้ตรวจ = ทำให้ผู้ตรวจรับรองสิ่งที่ไม่ได้ทำ

- **ห้ามแต่งผลตรวจ** — ทุก pass/fail ต้องมาจากคำพูดหรือหลักฐานของผู้ตรวจ
- **UI / UX ใช้ exception-based** — script มี checklist มาตรฐาน 6 ข้อต่อมิติ (ดูใน schema). ผู้ตรวจบอกว่าดู UI/UX แล้ว (เช่น "UI ที่เหลือโอเค", "ลองใช้แล้วลื่น") → `ui_checked: true` ข้อที่ไม่ได้พูดถึง = ผ่าน. ถ้าไม่ได้พูดถึงมิตินั้นเลย → `false` ทั้งมิติเป็น "ไม่ได้ตรวจ" แล้วบอกในแชทว่ามิตินั้นยังว่าง
- **Logic 1 แถว = 1 กฎ/scenario** — "สร้าง แก้ไข อนุมัติ ผ่านหมด" แตกเป็น 3 แถว (ผลรวมตัดสินจากจำนวนข้อ ถ้ารวบเป็นแถวเดียว ผลจะเพี้ยน)
- **Logic ที่ไม่ผ่าน/มีข้อสังเกต ต้องผูก Bug** — ใส่ `bug: "BUG-xx"` และสร้างการ์ด Bug คู่กันเสมอ
- **Bug ต้องทำซ้ำได้** — steps เป็นขั้นสั้น ๆ, expected/actual เป็นค่าที่เห็นจริง (ตัวเลข/ข้อความบนจอ). ถ้าผู้ตรวจเล่าไม่พอให้ทำซ้ำ → เขียนเท่าที่รู้ แล้วบอกในแชทว่า BUG ไหนควรเติม step
- **ข้อเสนอแนะ ≠ Bug** — ทำงานถูกตาม spec แต่อยากให้ดีขึ้น → `suggestions` ไม่ใช่ `bugs`
- **หลักฐาน** — รูปที่ user แนบ copy มาไว้ข้าง report.json แล้วอ้าง path → script ฝังรูปในไฟล์ (คลิกขยายได้). คลิป/ไฟล์อื่นใส่เป็นชื่อไฟล์

## ระดับ Bug (Claude เสนอตามนี้ ถ้าผู้ตรวจไม่ระบุ)

| ระดับ | ใช้เมื่อ |
|---|---|
| critical | ใช้งานไม่ได้ · ข้อมูลเสีย/หาย · ข้ามสิทธิ์หรือข้ามสายอนุมัติ (DOA) |
| high | ผลลัพธ์ผิด — เงิน ภาษี สต๊อก สถานะเอกสาร · สร้างเอกสารซ้ำ |
| medium | ผิด spec แต่มีทางเลี่ยง · ประวัติ/log ไม่บันทึก |
| low | หน้าตา · ข้อความ · ตำแหน่ง |

## ผลตัดสิน (script คำนวณ ห้ามเลือกเอง)

- **ไม่ผ่าน** — มี Bug Critical ค้าง หรือ Logic ไม่ผ่าน ≥ 3 ข้อ
- **ผ่านแบบมีเงื่อนไข** — มี Bug High ค้าง หรือ Logic ไม่ผ่าน 1–2 ข้อ → แก้แล้วตรวจซ้ำเฉพาะจุด
- **ผ่าน** — นอกจากนั้น (Medium/Low ตามแก้รอบถัดไป)

Bug ที่ `status: "fixed"` ไม่นับ — ใช้กับรายงานตรวจซ้ำรอบ 2+ (ตั้ง `round` ตามรอบ และใส่ bug เดิมพร้อม status)

## ตอบในแชทหลังส่งไฟล์

```
ผลตรวจ F-PO-001: ผ่านแบบมีเงื่อนไข
เหตุผล: Bug High 1 รายการ (VAT คิดก่อนหักส่วนลด)
ต้องทำต่อ: แก้ BUG-01 แล้วตรวจซ้ำเฉพาะจุด
```
+ ถ้ามี: มิติที่ยังไม่ได้ตรวจ / Bug ที่ step ไม่พอ — บรรทัดละเรื่อง ไม่ต้องอธิบายรายงานซ้ำ
