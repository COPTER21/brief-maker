# cases.json — schema

ไฟล์นี้คือ "เนื้อหาแบบทดสอบ" ที่ Claude เขียนเองจาก BRD + FRD + HTML (ไม่ใช่ engine).
เขียนเป็นภาษาผู้ใช้ทั่วไป ตาม **iron-rules.md** อย่างเคร่งครัด.

```jsonc
{
  "meta": {
    "feature_id": "F-91",                         // ใช้ตั้งชื่อ localStorage key + ชื่อไฟล์ PDF
    "title":      "แบบทดสอบ SOW Template",        // ขึ้นหัว sidebar + <title> + หัวรายงาน
    "crumb":      "กระบวนการทำงาน",                // บรรทัดเล็กเหนือ title
    "code":       "F-91 · เวอร์ชัน 1.0",          // บรรทัดเล็กใต้ title
    "footer":     "F-91 · ... · 2BSimple · ผลบันทึกในเครื่องนี้อัตโนมัติ",
    "report_sub": "งานย่อย (SOW Template) · รหัสฟีเจอร์ F-91"   // ใต้หัวรายงานผลทดสอบ
  },

  "groups": [                                     // แต่ละ group = 1 หน้า (hash #g1..#gN)
    { "id": "g1", "name": "ดูรายการ & ค้นหา" },
    { "id": "g2", "name": "สร้างงานใหม่" }
  ],

  "data": {                                       // ชุดข้อมูลตัวอย่าง (แสดงใน modal "data sample")
    "A": { "rows": [                              // rows = [ [ฟิลด์, ค่า], ... ]  (2 คอลัมน์เท่านั้น)
      ["ชื่องาน", "จัดทำใบเสนอราคา"],
      ["กลุ่มงาน", "จัดทำเอกสาร"]
    ]}
  },

  "cases": [
    {
      "id":   "TC-01",
      "grp":  "g1",                               // ต้องตรงกับ groups[].id
      "pri":  "high",                             // high | med | low  (สำคัญมาก/ปานกลาง/ทั่วไป)
      "title":"ดูรายการงาน พร้อมการกรองและตัวเลขสรุป",
      "why":  "ตรวจว่าหน้ารายการแสดงงานครบ กรองได้ และตัวเลขสรุปด้านบนถูกต้อง",
      "who":  "ผู้ดูแลกระบวนการ",                  // ใครเป็นคนทดสอบ (role ภาษาคน)
      "pre":  "มีงาน (SOW) อยู่ในระบบหลายรายการ",  // เตรียมก่อนเริ่ม
      "data": "A",                                // คีย์ใน data{} หรือ null ถ้าเคสนี้ไม่มีชุดข้อมูล

      "steps": [
```

## กติกาของ steps
- step = อาเรย์ 4 ช่อง: `[do, dataText, expect, regionKey]`
- `do` — สั่งทำทีละขั้น ภาษาคนไม่รู้ระบบ (ดู iron-rules R2)
- `dataText` — ข้อความข้อมูลที่ใช้ในขั้นนั้น เช่น `ชื่อ “จัดทำใบเสนอราคา”` หรือ `"—"` ถ้าไม่มี
  - ถ้าเคสมี `data` set → ช่องนี้จะกลายเป็นปุ่ม **data sample** (เปิด modal). ถ้า `"—"` จะไม่มีปุ่ม
- `expect` — สิ่งที่ผู้ทดสอบควรเห็นบนจอ (เขียนจากสิ่งที่ตาเห็นจริง อ่านจาก HTML) — **ต้องผ่าน R16/R17**:
  - **R16 Mock ≠ Real:** ห้ามผูกกับค่าปลอมใน prototype (จำนวนแถว/ยอดสรุป/ชื่อรายการที่ seed ไว้).
    เขียนเชิงโครงสร้าง/ความสามารถ: "แสดงรายการได้ถูกต้อง (เท่ากับข้อมูลจริง; ว่างถ้ายังไม่มี)".
    ยกเว้นค่าที่ผู้ทดสอบเพิ่งกรอก/สร้างเองในเคสนี้ → assert ได้.
  - **R17 Dynamic/derived:** ค่าที่ระบบดึงจากที่อื่น เขียน "ตรงกับที่ตั้งไว้ที่ [แหล่ง]" + ระบุแหล่ง —
    ห้าม hardcode literal จาก prototype.
- `regionKey` — คีย์ภาพหน้าจอ (ต้องตรงกับ key ใน shot-spec.json / shots_b64.json) หรือ `""` ถ้าขั้นนั้นไม่มีภาพ → ปุ่ม 👁 จะเป็นจุดจาง
  - **R18:** regionKey ต้องเป็นภาพของ **สถานะหลังทำ step นี้เสร็จ**. ถ้าถ่ายจุดลึกไม่ได้ ตั้ง `""` — อย่าใช้ key ของสถานะอื่นแทน

## priority → ป้าย
`high → สำคัญมาก` · `med → ปานกลาง` · `low → ทั่วไป`

## ฟิลด์เสริม (v2 Pipeline Mode)
- `"sys": true` (optional, ระดับเคส) — เคสที่ "ทดสอบโดยระบบ/AI แล้ว — ข้ามในรอบผู้ใช้"
  (simulate/หลังบ้าน/ข้าม tenant จาก testcases-*.md). template จะแสดงแบบจาง + ป้าย,
  ไม่นับใน progress/รายงานสรุป แต่โชว์ในรายงานรายเคสว่า "ทดสอบโดยระบบ/AI".
  - **Lite Mode (default):** เคสพวกนี้ **ตัดออกเข้า drop ledger** (คนทำไม่ได้) — ไม่ต้องใส่ในไฟล์
  - **Mirror Mode (opt-in):** ใส่ `sys:true` คงไว้แบบจาง ตาม iron-rules R14
  - ทั้ง 2 โหมด: ห้ามลบทิ้งเงียบ — ที่ตัดต้อง list ใน drop ledger เสมอ (R14/R15)

## โหมด (v3 — ตัดสินก่อนเขียน cases.json)
- **Lite (default):** คัดเคสที่ "คนกดจริงบน UI ตรวจได้" ตาม R19; ยุบ step ที่ atomic เกิน (R13);
  เอกสารสั้น อ่านไหว. เคสที่ตัด → drop ledger.
- **Mirror (opt-in):** สะท้อน MD 1:1 ทุกเคสทุก step (R12/R13/R15 เข้ม) — ใช้เมื่อ user ต้อง cross-check เป๊ะ.
- id ของเคสที่เก็บ = id เดิมจาก MD เสมอ (ทั้ง 2 โหมด, R12).
