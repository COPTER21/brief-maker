# Iron Rules — qa-friendly-html-generator

กฎที่ห้ามฝ่าฝืน เวลาเขียน `cases.json` และตอน build.

## R1 — ห้ามมีโค้ด/ศัพท์เทคนิคในเอกสาร (ผู้ทดสอบเป็นคนทั่วไป)
ทุก error code, API path, ชื่อฟังก์ชัน, ชื่อตาราง, แนวคิดภายใน ต้องเขียนใหม่เป็น
"สิ่งที่ผู้ทดสอบเห็นจริง". เช่น
- `409 / optimistic lock / race condition` → "ระบบแจ้งว่ามีคนแก้ไขรายการนี้ไปแล้ว ให้โหลดใหม่"
- `idempotency / junction diff / bfs` → อธิบายเป็นพฤติกรรมที่เห็นบนจอ
- ถ้าเผลอเขียนศัพท์เทคนิค = ผิดกฎ ต้องแปลงทันที

## R2 — step เขียนเป็นคำสั่งทีละขั้น ละเอียด ภาษาคนไม่รู้ระบบ
ชี้ตำแหน่งบนจอแบบจับมือทำ: "มองที่มุมขวาบน จะมีปุ่มสีน้ำเงินเขียนว่า ‘สร้าง SOW’ ให้คลิกหนึ่งครั้ง",
"เลื่อนลงไปที่ส่วน ‘ตำแหน่งที่รับงานได้’". หลีกเลี่ยงคำสั่งห้วน ๆ แบบ dev.

## R3 — แต่ละ group เป็นคนละหน้า
nav ซ้ายสลับหน้า (ไม่ scroll ยาว). 1 group = 1 ชุดเคสที่เกี่ยวข้องกัน.

## R4 — ภาพหน้าจอถ่ายจากของจริง + ไฮไลต์จุดที่ทดสอบ
ภาพมาจากการ render HTML จริงด้วย Playwright (capture.py) แล้วทำ spotlight (กรอบฟ้า #0B5CFF +
หรี่รอบนอก). **ห้ามวาด/เดาภาพเอง**. ปุ่ม 👁 เปิดดูเต็มจอ.

## R5 — "ผลที่ควรเห็น" เขียนจากสิ่งที่ตาเห็นจริง
อ่าน UI/HTML เพื่อบรรยายผลลัพธ์ที่ปรากฏ (ข้อความ ป้าย สถานะ ตำแหน่ง) ไม่ใช่ผลเชิงระบบ.

## R6 — โทเคน/รูปภาพ (สำคัญมากเรื่อง context)
- ภาพถูก "ถ่ายโดย Chromium + ฉีดโดยสคริปต์" — **ไม่ใช่** ให้ Claude พิมพ์ base64
- **ห้ามอ่านไฟล์ `shots_b64.json` หรือไฟล์ HTML ผลลัพธ์กลับเข้า context** (มันใหญ่มากและไม่มีประโยชน์)
  ใช้แบบ write→present เท่านั้น. capture.py/build.py พิมพ์แค่ path/ขนาด/จำนวน ไม่พิมพ์ base64

## R7 — dedup ตอน build เสมอ
build.py จะ (1) ยุบภาพ byte ซ้ำ → เหลือใบเดียว remap regionKey, (2) ตัดภาพที่ไม่มี step ใช้ทิ้ง.

## R8 — modal "data sample" = ฟิลด์ + ค่า + ปุ่มคัดลอก เท่านั้น
ไม่มีคอลัมน์ "วิธีกรอก". `data.rows` เป็น `[ฟิลด์, ค่า]` 2 คอลัมน์.

## R9 — ไม่มีช่อง "สิ่งที่พบ/โน้ต" ในเอกสาร
ผู้ทดสอบไปแขวนปัญหาใน ticket system ของตัวเอง. เอกสารเหลือแค่กล่อง "ถือว่าผ่านเมื่อ".

## R10 — lean + ตรง CI (Warm Light — อ้าง html-generator-v6)
CI = Warm Light ตาม `html-generator-v6/knowledge/ci-tokens.md` — **ห้าม hardcode hex ในกฎนี้**
(ค่าจริงอยู่ใน `assets/template.html` :root ซึ่ง sync กับ v6; v6 เปลี่ยน → sync template ตาม)
Sidebar charcoal flat (ไม่ใช่ gradient). ฟอนต์เอกสาร: Noto Sans Thai + Inter (Inter ฝัง b64
เพื่อ offline — deviation ที่ยอมรับได้จาก Satoshi ของ v6 เพราะเอกสารเทสต้อง self-contained), ไม่มี emoji,
ไอคอนเส้นแบบ Lucide, priority เป็นข้อความสีล้วน (ไม่เป็น pill), การ์ดบาง เส้นอ่อน.
ข้อความปุ่ม/toast ที่อ้างในเอกสาร ยึดตาม testcases-*.md เป็นหลัก (MD anchor จาก HTML จริงมาแล้ว) — fallback: microcopy กลางของ html-generator-v6 อ่านสดจาก `knowledge/microcopy.md`.

## R11 — รายงานผลทดสอบ = พิมพ์/PDF จริง
ปุ่ม "พิมพ์ผลทดสอบ" เปิด **หน้า preview เอกสาร A4** ก่อน, กรอกชื่อผู้ตรวจ/ตำแหน่ง/วันที่ได้
(จำค่าไว้), แล้ว **ดาวน์โหลด PDF จริง** (html2pdf ฝังในไฟล์) หรือสั่งพิมพ์.

## R12 — คง TC id เดิมสำหรับ "เคสที่เก็บไว้" (ทั้ง 2 โหมด)
ทุกเคสจาก MD ที่ **เลือกเก็บ** ต้องคง id เดิมเป๊ะ (TC-BP03 ใน MD = "TC-BP03" ใน HTML) —
ห้ามรีนัมเบอร์เคสที่เก็บ. id เดียวกันทำให้ผลของ AI agent (ฝั่ง MD) กับคน (ฝั่ง HTML) เทียบกันได้ตรง ๆ.
เคสที่ **ตัดออก** (Lite) ไม่หายเงียบ — ไปอยู่ใน drop ledger ตาม R14.

## R13 — ระดับความละเอียดของ step ขึ้นกับโหมด
- **Lite Mode (default สำหรับ UAT ของคน):** เขียน step เพื่อ "คนอ่านแล้วทำได้จริง" —
  **ยุบ step ที่ atomic เกินไปให้เป็นขั้นที่อ่านลื่น** (เช่น การคลิกนำทางต่อเนื่องหลายทีที่เป็นการ
  ไปหน้าเดียวกัน รวมเป็นขั้นเดียวได้). **แต่ห้ามยุบ step ที่เปลี่ยน "สิ่งที่ต้องกรอก" หรือ "สิ่งที่ต้อง
  สังเกต/ตรวจผล"** — ถ้ายุบแล้วผู้ทดสอบพลาดจุดตรวจสำคัญ = ผิด. จุดตรวจ (Expected) สำคัญทุกจุด
  ต้องยังอยู่.
- **Mirror Mode (opt-in — เมื่อ user ต้องการ cross-check เป๊ะกับ MD):** 1 MD step = 1 step ห้ามยุบ
  (พฤติกรรมเดิม; ยุบ `OPEN` ที่ซ้ำกับ Start ได้ 1 กรณี ต้องนับใน R15).
- ทั้ง 2 โหมด: verb tag → ประโยคจับมือทำ, route → การนำทางที่คนทำได้ (R1/R2), ตัด error code (R1).
  เช่น "CLICK ปุ่ม **บันทึก**" → "มองหาปุ่มสีน้ำเงินเขียนว่า 'บันทึก' ที่มุมล่างของแบบฟอร์ม แล้วคลิกหนึ่งครั้ง".

## R14 — ไม่มีการตัดเงียบ: ทุกเคส/step ที่ตัดหรือยุบต้องอยู่ใน "drop ledger"
Lite Mode ตัดเคสได้ (ดู R19 ว่าตัดอะไรได้บ้าง) แต่ต้อง **list ออกมาเป็น drop ledger** ตอน audit (R15)
รูปแบบ `TC-id · ตัด/ยุบ · เหตุผลสั้น`. Ledger นี้ **ไม่ต้อง render ลงเอกสารคน** — พิมพ์ในแชท/ไฟล์ audit
เท่านั้น เพื่อให้เห็นว่า coverage ที่ AI ทำไว้ครบ ส่วนไหนถูกกันออกจากรอบคน (ไม่ใช่ลืม).
- เคส simulate / ตรวจหลังบ้าน / ข้าม tenant (RLS, optimistic lock, audit log): คนทดสอบทำไม่ได้อยู่แล้ว
  → **Lite = ตัดเข้า ledger** (default ใหม่); **Mirror = คงเป็นเคส `sys:true` แบบจาง** (พฤติกรรมเดิม).

## R15 — Audit gate ก่อน build
ก่อนรัน build.py ต้องรายงาน: MD มี N เคส / M step → เก็บ K เคส (Lite) หรือ N เคส (Mirror),
พร้อม **drop ledger** (เคสที่ตัด + เหตุผล) และ merge note (step ที่ยุบ + จากกี่ขั้นเหลือกี่ขั้น).
ตัวเลข/เหตุผลอธิบายไม่ได้ = กลับไปแก้ cases.json ก่อน — ห้าม build.

## R16 — ★ Mock ≠ Real: ห้าม assert ค่าที่มาจากข้อมูลตัวอย่างใน prototype
prototype มัก seed ข้อมูลปลอมไว้ (list 15 แถว, ตัวเลขสรุป, ชื่อรายการ). บนระบบจริงผู้ทดสอบ
**ยังไม่มีข้อมูลพวกนั้น** → expect **ห้ามผูกกับค่าปลอม**:
- ❌ "เห็นรายการ 15 แถว" / "ยอดรวมด้านบน = 1,250,000" / "แถวแรกชื่อ 'จัดทำใบเสนอราคา'"
- ✅ "หน้ารายการแสดงผลได้ถูกต้อง — จำนวนแถวเท่ากับข้อมูลที่มีจริง (ถ้ายังไม่มีจะเห็นสถานะว่าง)"
- ✅ "กล่องตัวเลขสรุปด้านบนแสดงค่าที่สอดคล้องกับรายการที่มีอยู่จริง"

เขียน expect เชิง **โครงสร้าง/ความสามารถ** (แสดงได้ · กรองได้ · เรียงได้ · คอลัมน์ครบ · มีสถานะว่างเมื่อ
ไม่มีข้อมูล) ไม่ใช่ค่าปริมาณเฉพาะ.
**ยกเว้น:** ค่าที่ **ผู้ทดสอบเพิ่งสร้าง/เพิ่งกรอกเองในเคสนี้** → assert ค่านั้นได้ เพราะเป็นค่าจริงที่เขาป้อน.
`data{}` = "ค่าที่ให้กรอก" ไม่ใช่ "ค่าที่ต้องมีอยู่ก่อน" — จะถือว่ามีอยู่ก่อนได้ต่อเมื่อระบุใน `pre`.

## R17 — ★ ค่า dynamic / ดึงมาจากที่อื่น: ระบุแหล่ง ห้าม hardcode ค่า
ฟิลด์ที่ระบบ **ดึง/คำนวณมาจาก feature หรือ master อื่น** (ราคาต่อหน่วยดึงจากข้อมูลสินค้า, ยอดเครดิต
ดึงจากลูกค้า, เลขที่เอกสารจาก Document Config, ยอดรวมที่คำนวณเอง) — expect ต้องเขียนเป็น
**"ค่าตรงกับที่ตั้งไว้ที่ [แหล่ง]"** ไม่ใช่ค่าตายตัวที่เห็นใน prototype:
- ❌ "ช่องราคาต่อหน่วยแสดง 150.00"
- ✅ "ช่องราคาต่อหน่วยแสดงราคาที่ตั้งไว้ในข้อมูลสินค้าโดยอัตโนมัติ (ตั้งไว้เท่าไรต้องเห็นเท่านั้น) — ไม่ต้องกรอกเอง"

ระบุ **แหล่งที่มา** ให้ชัดทุกครั้งที่ค่าเชื่อมข้ามฟีเจอร์ เพื่อกันปัญหา "ทำ 2 ฟีเจอร์แล้วค่าไม่ตรงกัน"
(ค่าเดียวกันถูกอ้างคนละที่ = เคสขัดกันเอง). ถ้า MD เขียน literal ให้แปลงเป็นรูป "ตรงกับแหล่ง" นี้เสมอ.

## R18 — ★ ภาพต้องตรงกับ "สถานะหลังทำ step นั้น" + ต้องผ่าน capture verify
- regionKey ของแต่ละ step = ภาพของ **หน้าจอ/สถานะ ณ ตอนที่ step นั้นทำเสร็จ** ไม่ใช่ภาพหน้าตื้นกว่า
  หรือหน้าก่อนเปิด drawer/modal. step "เปิด drawer แล้วดูส่วน X" → `shot-spec.setup` ต้องพาไปถึง
  สถานะ drawer เปิด + ไฮไลต์ X จริง (ดู shot-spec-schema).
- **ห้ามใช้ regionKey เดียวข้ามหลาย step ที่คนละสถานะ** เพียงเพื่อประหยัดภาพ — dedup (R7) ยุบเฉพาะ
  ภาพที่ byte เหมือนกันจริงเท่านั้น การจับ key ซ้ำเองทำให้ step โชว์ภาพผิด.
- **Capture verify gate:** หลังรัน capture.py ต้องอ่าน **สรุปผล ok/skip/fail ต่อ key** (จาก `--report`
  หรือ summary ที่ engine พิมพ์ — **ไม่ใช่** base64) ทุกครั้ง. key ที่ skip/fail = ภาพไม่ได้ถ่าย → step นั้น
  จะไม่มีภาพ. ต้อง **แก้ shot-spec แล้วถ่ายใหม่** จน key สำคัญผ่านครบก่อน build.
  ถ่ายจุดลึกไม่ได้จริง ๆ → ตั้ง `regionKey=""` (ไม่มีภาพ) **ดีกว่าปล่อยให้ไปโชว์ภาพผิดจุด**.

## R19 — ★ Lite selection: ตัดอะไรได้ / เก็บอะไรไว้
Lite Mode คัดเคสให้เหมาะกับ "คนกดจริงบน UI" — เอกสารต้องสั้น อ่านไหว ครอบผลลัพธ์ที่ใช้ตัดสินการรับงาน.
- **เก็บเสมอ:** happy path หลักทุกเส้น · validation/error ที่ผู้ใช้เห็นบนจอ (กรอกผิด/ไม่ครบ/เกินสิทธิ์
  ที่กดได้จาก UI) · เคสสิทธิ์ที่คนทดสอบ trigger เองได้ · เคสยืนยันข้อตกลงกับลูกค้า (LOCK).
- **ตัดเข้า ledger ได้:** เคส `sys`/simulate/หลังบ้าน/ข้าม tenant · permutation ซ้ำที่ต่างกันแค่ค่า
  (เก็บ 1 ตัวแทน) · edge เชิงเทคนิคที่คนทั่วไปตรวจไม่ได้/ไม่สื่อความ · เคสที่ AI ครอบไปแล้วและตาคน
  ไม่เพิ่มคุณค่า.
- ไม่แน่ใจว่าเคสไหน "จำเป็น" → ยึด **เกณฑ์รับงาน (acceptance)** เป็นตัวตัดสิน ไม่ใช่ยึดว่า MD มีกี่เคส.
