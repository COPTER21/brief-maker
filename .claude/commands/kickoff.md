# Kickoff — เปิด session ใหม่ของ feature `$1`

> 🚫 **คำสั่งนี้ไม่เริ่มทำงาน** — จบที่รายงานแล้ว **หยุดรอผู้ใช้เคาะ**
> ห้าม gen HTML · ห้ามรัน Playwright · ห้าม commit · ห้ามเดาคำตอบของจุดที่ต้องเคาะ
>
> 🪟 เครื่องนี้ Windows: python ของ venv = `.claude/venv/Scripts/python.exe` · system python = `python` (ตั้ง `PYTHONIOENCODING=utf-8`)

## Phase 0 — เปิดแผนที่ path + ⭐ ถามตำแหน่งแพ็กบรีฟ (ห้ามเดา)

1. อ่าน `.claude/workflow.paths.md` เอาค่าจริงของทุกบทบาทมาก่อน
2. `$1` เป็นแค่ **คำใบ้** (`COA` · `Chart of Accounts` · `F-COA-001`) หรือจะเป็น path ตรง ๆ ก็ได้

```bash
ls -1 "{{BRIEF_ROOT}}"      # ที่เก็บมาตรฐาน — แต่แพ็กอาจถูกวางที่อื่นก็ได้
ls -1 "{{OUTPUT_ROOT}}"     # เช็คว่าเคยทำไปแล้วบางส่วนมั้ย
```

ถามยืนยันตำแหน่ง โดยเอารายการที่เจอมาเป็นตัวเลือก + ช่องพิมพ์ path เอง

| กรณี | ทำยังไง |
|---|---|
| เจอตัวที่ตรงคำใบ้ชัดเจนตัวเดียว | ยังต้อง **ถามยืนยัน** — ตั้งเป็นตัวเลือกแรกพร้อมทำเครื่องหมายว่าน่าจะใช่ |
| เจอหลายอัน / ไม่เจอเลย | ถามอย่างเดียว **ห้ามเลือกให้** |
| ผู้ใช้ตอบ path ที่ไม่มีจริง | บอกว่าไม่เจอ แล้วถามใหม่ **ห้ามหาตัวแทนเอง** |

> **ทำไมต้องถาม:** แพ็กบรีฟคือ contract ของ `qc-coverage-checker` (step 4) —
> หยิบผิดโฟลเดอร์ = ตรวจความครบเทียบผิดใบ แล้วผ่านฉลุยทั้งที่ทำไม่ตรงบรีฟ
> ยิ่ง workflow ปล่อยไหล `1→5` และ `6→12` ยิ่งเดินผิดไปไกลก่อนมีใครทัก

## Phase 1 — โหลด context กลาง

```bash
ls -1 "{{CENTRAL_PLAN}}"
```

**อ่านทุกไฟล์ที่ `ls` เจอ — ไม่ต้องเลือก ห้ามเชื่อรายชื่อไฟล์ที่เขียนไว้ในเอกสารใด ๆ**

| ทำไมไม่เลือกอ่านเฉพาะเลนของ feature | |
|---|---|
| "เลือกตามเลน" คือการเดา | เป็นบั๊กคลาสเดียวกับ *ของไม่ถูกอ่านเพราะมีกฎบอกว่าไม่เกี่ยว* |
| เลนตัดสินยาก | master data หลายตัวตอบไม่ได้จากชื่อว่าอยู่เลนไหน |
| feature มัก cross-lane | อ่านเลนเดียวจะไม่เห็น dependency ที่เลนอื่นวางไว้ |
| ต้นทุนเป็นศูนย์ | ไฟล์แผนรวมกันเล็กกว่าผังภาพรวมที่อ่านทุกครั้งอยู่แล้ว |

`.html` **ไม่ใช่รูปภาพ** — เนื้อหาอยู่ใน markup อ่านได้ปกติ · ยาวมากให้อ่านเฉพาะส่วนที่แตะ feature นี้
แต่ **ต้องเปิดดูจริง** ห้ามข้ามเพราะเป็น `.html`

## Phase 2 — อ่าน memory ให้ครบตัวไฟล์ ไม่ใช่แค่สารบัญ

`MEMORY.md` ที่โหลดอัตโนมัติมีแค่หัวข้อบรรทัดเดียวต่อเรื่อง — **เนื้อจริงต้องเปิดไฟล์อ่านเอง**
memory ที่บอกว่าของอยู่ที่ไฟล์ X → **เช็คว่ายังมีจริงมั้ยก่อนอ้าง** (memory บันทึกสภาพ ณ วันที่เขียน)

## Phase 3 — สำรวจของจริงของ feature นี้

ใช้ **path ที่ผู้ใช้ยืนยันใน Phase 0** เท่านั้น · โครงของแต่ละ feature ไม่เหมือนกัน **ห้ามสมมติว่ามีไฟล์อะไร**

```bash
find "<path ที่ผู้ใช้ยืนยัน>" -type f -not -name ".*" | sort
```

| ไฟล์ | ใช้ทำอะไร |
|---|---|
| `PREBRIEF_*.md` | **เนื้อธุรกิจ** — `qc-coverage-checker` ใช้เป็น contract |
| `FUNCTION_CHECKLIST_*.md` | ตาราง `FN-01..FN-nn` + คอลัมน์ `WF/DEV/QA` + **`FN-40` = ของที่ห้ามมี** · **`e2e` (step 5) ต้องครอบทุก FN** |
| `<Feature>.html` | หัวเชื้อจอ — **input ไม่ใช่ผลลัพธ์** ต้อง vibe ใหม่ผ่าน `html-generator-v9` |

> แพ็กเก่าอาจเป็น `_SEED_NOTES.md` แทน `FUNCTION_CHECKLIST` — เจอแบบไหนใช้แบบนั้น
> **ไม่มี checklist → สกัด FN จาก `PREBRIEF` เอง** แล้วเขียนรายการไว้หัวไฟล์ `e2e`

**grep หัวเชื้อตั้งแต่ Phase นี้** (บั๊ก Esc จาก template upstream):

```bash
F="<path>/<Feature>.html"
grep -c "getElementById('ss-" "$F"   # ต้อง 0
grep -c 'ssId('              "$F"   # ต้อง >0
grep -c 'e.stopPropagation'  "$F"   # ต้อง >0
grep -c 'portalMenu\|menu-fixed' "$F"   # 0 = ยังไม่ทำ #95
grep -c 'page-fill\|table-wrap'  "$F"   # 0 = ยังไม่ทำ #96
grep -c 'PREFLIGHT'              "$F"   # 0 = qc-ux จะ BLOCK
```

> 🚫 **บรีฟชอบเขียนรับรองตัวเอง** เช่น *"วาดด้วย v8 แล้ว"* · *"ผ่าน E2E N เคสแล้ว"* —
> **วัดเอง ห้ามเชื่อ** · เคยเจอบรีฟที่เขียนทั้ง 2 ประโยคแต่ตก grep ครบทุกตัว

## Phase 4 — ไล่หาจุดที่ต้องเคาะ (ข้อไหนไม่เจอให้เขียน "ไม่มี" ห้ามเงียบ)

| # | ตรวจอะไร | ทำไมต้องถาม |
|:-:|---|---|
| 1 | `PREBRIEF` มีจุดที่ยังไม่เคาะมั้ย | ช่องว่างที่นี่จะกลายเป็น gap ตอน step 4 |
| 2 | `FUNCTION_CHECKLIST` ขัดกับ `PREBRIEF` มั้ย · มีกี่ FN · `FN-40` กี่ข้อ | ทั้งคู่เป็น contract — ขัดกันห้ามเลือกข้างเอง · **จำนวน FN คือตัวหารของ `e2e`** |
| 3 | หัวเชื้อ HTML ตก grep มั้ย | ตก = ต้องคืน BASE-KIT verbatim ตอน step 1 |
| 4 | `PREBRIEF` ขัดกับ Global Contracts ของแผนกลางมั้ย | แผนกลางชนะ — แต่ต้องบอก ไม่ใช่แก้เงียบ |
| 4b | บรีฟอ้างมติของ feature ที่ **ยังไม่ได้ทำ** มั้ย | `grep` หาต้นทางจริงก่อน — ไม่เจอ = ยังไม่ใช่มติที่ล็อก · ต้องลง `PROPOSALS_outbound.md` ที่ step 12 |
| 5 | ของใน `{{OUTPUT_ROOT}}` ตัวไหนที่ feature นี้ต้องอิง | รายชื่อที่ตอบตรงนี้จะกลายเป็น **input ของ step 4** ตอบขาด = step 4 ตรวจไม่ครบ |
| 6 | OQ ที่ค้างอยู่ บล็อกงานนี้มั้ย | |
| 7 | ทำไปแล้วบางส่วนรึเปล่า | มีโฟลเดอร์อยู่แล้ว = ทำต่อ ไม่ใช่เริ่มใหม่ · ไล่ว่าค้าง step ไหนจาก 12 |
