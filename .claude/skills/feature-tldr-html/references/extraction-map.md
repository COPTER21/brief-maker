## ② ✅ ทำอะไรได้บ้าง (in scope)

**ดึงจาก:** `00_OVERVIEW` scope-in + `01_UI` (ปุ่ม/action บนหน้าจอ) + `06_TESTS` (Acceptance Test ที่ผ่าน)

- ขึ้นต้นด้วยกริยาที่คนทำจริง: เพิ่ม / แก้ไข / ลบ / ค้นหา / กรอง / ส่งอนุมัติ / พิมพ์ / ดาวน์โหลด / นำเข้าไฟล์

## ⑥ กฎสำคัญห้ามพลาด

**ดึงจาก:** `05_RULES.md` — Business Rules + Cross-field validation + Edge Cases

- **คัดเฉพาะกฎที่ "พลาดแล้วเจ๊ง"** — cross-field validation, กฎเงิน/สิทธิ์, กฎที่ tester จะเทสผิดถ้าไม่รู้
- **ตัดกฎจุกจิก** (format วันที่, required ธรรมดา) ออก — ไม่ต้องใส่หมด
- แปลเป็นภาษาคน + **ยกตัวอย่างตัวเลขจริง** ถ้ามี:
  - FRD: "absolute_timeout must be > idle_timeout; warn_before < idle_timeout; admin ≤ user"
  - หน้าปก: "⚠️ เวลาเด้งออกมี 3 ตัว ต้องเรียงถูก — เวลานั่งเฉย(idle) < เวลาใช้งานรวมสูงสุด(absolute), และเวลาเตือนก่อนเด้ง ต้องน้อยกว่าเวลานั่งเฉย. ของแอดมินต้องเข้มกว่าหรือเท่าผู้ใช้ทั่วไป"
- เป้าหมาย 3-6 ข้อ

## ⑧ อนุมัติ + ความอ่อนไหวข้อมูล (OPTIONAL)

**ดึงจาก:** DOA placeholder (`05_RULES` / field `approval_chain`) + `00_OVERVIEW §0.7.1` Data Classification

- **อนุมัติ:** ถ้าฟีเจอร์มีสายอนุมัติ (DOA) → "ต้องมีคนอนุมัติก่อนมีผล (สายอนุมัติตั้งที่ Policy Center ทีหลัง)". ถ้าไม่มี → ตัด
- **ข้อมูลอ่อนไหว:** แปลง level เป็นภาษาคน:
  - Public → "เปิดดูได้ทั่วไป"
  - Internal → "ข้อมูลภายใน"
  - Confidential → "ข้อมูลลับ ดูได้เฉพาะคนมีสิทธิ์"
  - Restricted → "ข้อมูลลับสุด คุมเข้มพิเศษ"
- ถ้าข้อมูลไม่อ่อนไหว (Public/Internal ล้วน) และไม่มีอนุมัติ → **ตัดบล็อกนี้ทิ้ง**

## การจัดการ Drift (FRD ≠ HTML)

ถ้า HTML จริงกับ FRD ขัดกัน (เช่น FRD บอกมีปุ่ม "ส่งออก" แต่ HTML ไม่มี):

1. **เชื่อ FRD** (source of truth ของ business scope) เป็นหลัก
2. เพิ่ม note เล็กๆ ท้ายหน้า (บล็อก footer) สีจาง: "⚠️ ข้อ [X] FRD ระบุไว้แต่ยังไม่เห็นในตัวอย่างหน้าจอ — ยืนยันกับ BA ก่อนเทส"
3. **อย่าเงียบ** — dev/tester ต้องรู้ว่ามีจุดต้องเช็ค

ถ้ามีแค่ HTML ไม่มี FRD → สกัดจากหน้าจอได้ แต่บล็อก ③ (ทำไม่ได้) และ ⑥ (กฎ) จะบางมาก → เตือน user ว่า "หน้าปกนี้สกัดจาก HTML อย่างเดียว ขอบเขต+กฎอาจไม่ครบ ควรมี FRD"
