# md-to-cases-mapping — แปลง testcases-*.md → cases.json (Pipeline Mode)

ต้นฉบับ = ไฟล์จาก `ai-testcase-md-generator` (มี Meta / Coverage Ledger / Data Sets /
Test Cases ราย group / Coverage Audit / Result schema). งานที่นี่คือ **แปล + คัด (Lite)** ตาม R12–R19.

> **Lite เป็น default (v3):** ไม่ต้องแปลทุกเคสทุก step เท่า MD. คัดเคสที่คนตรวจได้จริงตาม R19,
> ยุบ step ที่ atomic เกินตาม R13, เขียน expect กัน mock/dynamic ตาม R16/R17. เคสที่ตัด → drop ledger (R14).
> Mirror Mode (1:1 เป๊ะ) ใช้เฉพาะเมื่อ user สั่งให้ cross-check ตรงกับ MD.

---

## 1) Mapping ระดับโครง

| ใน MD | ใน cases.json |
|---|---|
| `## Meta` (Feature ID, ชื่อ, เวอร์ชัน) | `meta{}` — feature_id, title ("แบบทดสอบ <ชื่อ>"), code, footer, report_sub |
| `### กลุ่ม X — …` | `groups[]` — id = ตัวย่อกลุ่ม (g-bp ฯลฯ), name = ชื่อกลุ่มภาษาคน |
| `## Data Sets` (ตาราง ฟิลด์/ค่า) | `data{}` — key เดิม (A/B/C…), rows = [[ฟิลด์, ค่า],…] ตรง ๆ |
| `### ไฟล์ทดสอบ (Files)` | rows ในชุด data ของเคสนั้น ("ไฟล์ที่ใช้", "ชื่อไฟล์.csv") + เขียนใน `pre` |
| `#### TC-xxx — ชื่อเคส` | `cases[].id` = TC-xxx (เดิมเป๊ะ), `title` = ชื่อเคสถอดวงเล็บชนิดออกได้ |
| `ความสำคัญ: สูง/กลาง/ต่ำ` | `pri`: high / med / low |
| `trace:` | ไม่ต้องแสดงในเอกสารคน (เก็บใน `why` แบบภาษาคนได้: "ตรวจกฎ…") |
| `actor` | `who` (แปลง role → ภาษาคน: warehouse_staff → "พนักงานคลัง") |
| `Setup: role=… · seed=… · files=…` | `pre` — เขียนรวมเป็นประโยค "ก่อนเริ่ม: เข้าระบบด้วยบัญชี…, มีข้อมูล…, เตรียมไฟล์…" |
| `Start:` | step แรกของเคส (การนำทางแบบคลิกได้จริง — ดูข้อ 2) |
| `ผ่านเมื่อ:` | `pass` |
| ตาราง step | `steps[]` = [do, dataText, expect, regionKey] — Lite: ยุบ atomic เกินได้ / Mirror: 1:1 (R13) |
| เคส stub "สถานะ: ข้าม" / มี `(ต้อง simulate)` ในชื่อ | เคส `"sys": true` + เหตุผลใน `why` (R14) |
| **เคส XT (cross-module — MD v1.1)** | เคสปกติถ้าคนเช็คได้จากฝั่งต้นทาง (toast/สถานะ/ตัวเลข); ต้อง simulate/เห็น module ปลายทางที่ไม่มีใน prototype → `sys: true`. จัด group แยก "การเชื่อมต่อข้ามส่วนงาน" ได้ |
| **เคส verify LOCK (Scope Lock — MD v1.1)** | เคสปกติ — ใน `why` เขียนภาษาคน: "ยืนยันตามข้อตกลงที่ลูกค้าเซ็น" (ห้ามโชว์เลข LOCK-XX ตาม R1) |
| `## Coverage Audit` (รวมบรรทัด XT/LOCK/Manifest cross-check — v1.1) | ใช้ตรวจนับตาม R15 (ไม่ต้อง render ลงเอกสารคน) |

## 2) แปลภาษา step (verb tag → ประโยคจับมือทำ)

| verb ใน MD | รูปประโยคใน `do` |
|---|---|
| `OPEN #/route` | "เปิดหน้า/ไปที่หน้า …" โดยบรรยายการคลิกที่คนทำได้ (เมนู/ปุ่ม) — ห้ามโชว์ hash route (R1) |
| `CLICK ปุ่ม "X"` | "มองหาปุ่ม [สี/ตำแหน่ง] ที่เขียนว่า 'X' … แล้วคลิกหนึ่งครั้ง" |
| `TYPE "ค่า" → ช่อง "Y"` | "คลิกที่ช่อง 'Y' แล้วพิมพ์ค่าจากชุดข้อมูล (กดปุ่ม data sample เพื่อคัดลอก)" |
| `SELECT "ค่า" → Z` | "คลิกช่องเลือก 'Z' แล้วเลือกตัวเลือกที่เขียนว่า 'ค่า'" |
| `TOGGLE "X"` | "กดสวิตช์/ติ๊กช่อง 'X' ให้เปลี่ยนสถานะ" |
| `UPLOAD ไฟล์.csv` | "คลิกปุ่มแนบไฟล์ แล้วเลือกไฟล์ชื่อ 'ไฟล์.csv' (ผู้ดูแลเตรียมไว้ให้แล้ว)" |
| `PRESS Esc / Ctrl+S` | "กดปุ่ม Esc ที่คีย์บอร์ด" / "กดปุ่ม Ctrl และ S พร้อมกัน" |
| `WAIT จน…` | "รอสักครู่ (ไม่เกิน ~3 วินาที) จนเห็น…" |
| `VERIFY …` | "สังเกต/ตรวจดูว่า…" (step ที่ไม่ต้องกดอะไร) |
| `VERIFY+จด …` (R17 ฝั่ง MD) | "จดตัวเลข … ลงกระดาษ/โน้ต (จะใช้เทียบในขั้นถัดไป)" — **ห้ามตัดทิ้ง** เพราะ step เทียบผลพึ่งค่านี้ |

- `Expected` → `expect`: คงสาระเดิม ตัด error code ในวงเล็บ + ศัพท์ระบบออก (R1)
  เช่น "toast **กรุณามอบหมายผู้รับผิดชอบก่อนดำเนินการ** (BP_NO_ASSIGNEE)" →
  "มีข้อความแจ้งเตือนขึ้นมาว่า 'กรุณามอบหมายผู้รับผิดชอบก่อนดำเนินการ' และรายการยังไม่เสร็จ"
- `Input` คอลัมน์ MD → `dataText` (เช่น "ชุด A" / ค่าตรง ๆ / "")
- `⚠ ยืนยัน anchor` ใน MD → คงเป็นหมายเหตุท้าย expect: "(ข้อความบนจอจริงอาจต่างเล็กน้อย)"

### 2.1) กัน Mock ค้างมากับ Expected (R16) — สำคัญ
MD เขียน expect อ้างข้อมูลตัวอย่างใน prototype ได้ (เช่น "เห็น 15 แถว"). **เวลาแปลงลง cases.json
ต้องถอดค่าปลอมออก** เป็นเชิงโครงสร้าง เพราะระบบจริงยังไม่มีข้อมูล:

| MD Expected (อิง mock) | `expect` ที่ถูกต้อง (Lite/คน) |
|---|---|
| "รายการแสดง 15 แถว" | "รายการแสดงได้ถูกต้อง — จำนวนแถวเท่ากับข้อมูลจริงที่มี (ยังไม่มีข้อมูล = เห็นสถานะว่าง)" |
| "ยอดสรุปด้านบน = 1,250,000" | "กล่องตัวเลขสรุปแสดงค่าที่สอดคล้องกับรายการที่มีอยู่จริง" |
| "แถวแรกคือ 'SOW-0001 จัดทำใบเสนอราคา'" | "รายการที่เพิ่งสร้างปรากฏในตาราง พร้อมชื่อและสถานะที่กรอกไว้" (ถ้าเป็นค่าที่ผู้ทดสอบเพิ่งสร้างเอง) |

### 2.2) ค่า Dynamic / ดึงจากที่อื่น (R17)
ถ้า MD/FRD ระบุว่า field ดึงมาจาก feature/master อื่น (ราคาสินค้า, เครดิตลูกค้า, เลขเอกสาร, ยอดคำนวณ)
→ `expect` เขียนอ้าง **แหล่ง** ไม่ใช่เลขจาก prototype:

| ที่มา (จาก MD/FRD) | `expect` ที่ถูกต้อง |
|---|---|
| ราคาต่อหน่วยดึงจากข้อมูลสินค้า | "ช่องราคาต่อหน่วยขึ้นเองอัตโนมัติจากราคาที่ตั้งไว้ในข้อมูลสินค้า (ตั้งไว้เท่าไรต้องเห็นเท่านั้น) — ไม่ต้องกรอก" |
| เลขที่เอกสารจาก Document Config | "ระบบออกเลขที่เอกสารให้อัตโนมัติตามรูปแบบที่ตั้งไว้ (ไม่ใช่เลขที่เราพิมพ์เอง)" |
| ยอดรวมคำนวณจากรายการ | "ยอดรวมด้านล่างคำนวณจากรายการที่กรอกโดยอัตโนมัติ และเปลี่ยนตามเมื่อแก้จำนวน" |

ถ้าค่านี้เชื่อมข้ามฟีเจอร์ (เช่นทำ 2 ฟีเจอร์ในโปรเจกต์เดียว) ให้ระบุแหล่งชัด กันเคสสองฝั่งขัดกันเอง.

### 2.3) ภาพให้ตรงสถานะ step (R18)
เวลาตั้ง regionKey ต่อ step ให้ยึด **สถานะหลังทำ step นั้น**: step เปิด drawer → key ของ drawer ที่เปิดแล้ว,
step กรอกช่องที่ 3 ของฟอร์ม → key ของฟอร์มที่โฟกัสช่องนั้น (ถ้าถ่ายได้). อย่าใช้ key หน้ารายการเดิม
ซ้ำกับ step ที่เข้าไปลึกแล้ว. ถ่ายจุดลึกไม่ได้ → `regionKey=""`.

## 3) regionKey (ภาพ)
MD ให้ `Start` route + ป้าย/ข้อความของทุก step แล้ว → ตั้ง regionKey ต่อ "หน้าจอ+element"
(เช่น `bp-create-modal`, `bp-drawer-footer`) แล้วเขียน shot-spec ให้เปิด route นั้นจริงตาม MD.
step สังเกตล้วนที่ไม่มีจุดชี้ → `regionKey = ""` ได้.

## 4) ลำดับทำจริง (กัน context บวม)
1. อ่าน MD ทั้งไฟล์ → สรุปนับ: กี่กลุ่ม กี่เคส กี่ step (baseline ไว้ใช้ R15)
2. **คัด (Lite):** ไล่ทุกเคสตัดสิน เก็บ/ตัด ตาม R19 → ได้ **keep list + drop ledger** (เคสตัด + เหตุผล)
3. เขียน cases.json **ทีละกลุ่ม** (append) เฉพาะเคสที่เก็บ — คง id เดิม (R12), ยุบ step ที่ atomic เกิน (R13),
   เขียน expect กัน mock/dynamic (R16/R17 · ข้อ 2.1–2.2)
4. **Audit (R15):** รายงานในแชท — MD N เคส/M step → เก็บ K เคส, drop ledger, merge note. ตัวเลขต้องอธิบายได้
5. ต่อ shot-spec (ยึดสถานะ step ตามข้อ 2.3) → capture → **อ่าน capture report ok/skip/fail (R18)** →
   แก้ shot ที่ fail จนครบ → build
