## §1.2 UI-01 — รายการทะเบียนคู่ค้า

**Visible anchors**

- Title: `ทะเบียนคู่ค้า`
- Subtitle: `จัดการข้อมูลคู่ค้า เอกสาร และสถานะการใช้งานในที่เดียว`
- Primary action: `เพิ่มคู่ค้า`
- Search placeholder: `ค้นหา รหัส / ชื่อ / เลขภาษี...`
- Filters: `ทุกประเภท`, `ทุกสถานะ`; reset: `รีเซ็ต`
- Empty state: `ไม่พบคู่ค้า` / `ลองปรับตัวกรอง หรือเพิ่มคู่ค้าใหม่`

**Columns:** คู่ค้า, ประเภท, เลขภาษี, สถานะ, row actions

**Status choices:** `draft`, `pending_kyc`, `pending_approval`, `active`, `blocked`, `inactive`, `blacklisted`

| User action | UI result | API |
|---|---|---|
| เปิดหน้า/ค้นหา/กรอง/เรียง/แบ่งหน้า | refresh table, count และ pagination | F-VENDOR-API-01 |
| คลิกแถว | เปิด UI-03 | F-VENDOR-API-03 |
| คลิก `เพิ่มคู่ค้า` | เปิด UI-02 step 1 | F-VENDOR-API-02 refs, then local form |
| row `แก้ไข` | เปิด UI-02 พร้อมข้อมูลเดิม | F-VENDOR-API-03 |
| row `ตรวจ KYC` | เปิด UI-04 | no mutation until confirm |
| row `อนุมัติ` | เปิด UI-05 | no mutation until confirm |
| row Block/Unblock | เปิด UI-06 | F-VENDOR-API-10/11 on confirm |

**States**

- Loading: skeleton ไม่ทำให้ layout shift
- Loaded: table + count + pagination
- Empty: ข้อความตาม anchor ข้างบน
- Error: แสดงข้อความที่เข้าใจได้และปุ่มลองใหม่
- Read-only role: ซ่อน mutation actions และแสดง `โหมดอ่านอย่างเดียว (...)`

## §1.3 UI-02 — Create/Edit Drawer Wizard

### Header and stepper

| Step | Header label | Main content |
|---|---|---|
| 1 | `ข้อมูล & ภาษี` | legal/display name, vendor type, tax/VAT/company registration, branch, country, currency |
| 2 | `ติดต่อ & ธนาคาร` | contacts, addresses, bank accounts |
| 3 | `เอกสารแนบ & ชำระ` | `เงื่อนไขการชำระเงินเริ่มต้น`, WHT, credit limit, attachments |

Stepper label ต้องอยู่กึ่งกลางกับ step dot ตาม HTML approved state

### Footer actions

| Action | Behavior |
|---|---|
| `ยกเลิก` / close | ปิด drawer; ถ้ามี unsaved change ให้ยืนยันก่อนในระบบจริง |
| `กลับ` / `ถัดไป` | validate เฉพาะข้อมูลที่จำเป็นต่อการไปขั้นถัดไป |
| `บันทึกร่าง` | ชื่อคู่ค้าต้องมี; create/update เป็น `draft` โดยไม่ submit KYC |
| `บันทึก + ส่ง KYC` | create aggregate แล้วเปลี่ยนเป็น `pending_kyc` |
| `บันทึก (amend)` | update aggregate ด้วย optimistic locking |

### Field behavior

- TH tax ID ต้องเป็น 13 หลักและ checksum ถูกต้อง; OT อาจไม่กรอก
- หลัง KYC ผ่าน tax ID เป็น read-only พร้อมข้อความ `ล็อก — ผ่าน KYC แล้ว แก้ไขไม่ได้ (IR-01)`
- active address ต้องมี exactly one billing และ one primary shipping ก่อน save/submit
- draft/new address ที่ไม่ถูกใช้งานลบได้ทันที
- ถ้าลบ address ที่เป็น billing/shipping ระบบต้อง clear role และบังคับเลือกตัวแทนอย่างชัดเจน; ห้ามย้าย role แบบเงียบ
- address ที่ persist แล้วของ vendor `active` ใช้ `ปิดใช้ที่อยู่นี้?` และคงประวัติ
- bank ที่ยังไม่ verified ลบได้ทั้งหมด รวมรายการแรก
- verified bank เป็น read-only; Finance ใช้ `ปิดใช้บัญชี` และต้องเก็บประวัติ
- account number แสดงแบบ masked หาก role ไม่มีสิทธิ์
- attachment รองรับ metadata ชนิดเอกสาร วันที่ออก วันหมดอายุ และสถานะตรวจ

## §1.4 UI-03 — View Drawer

Header แสดงชื่อ, vendor code, vendor status และ KYC status

| Tab | Purpose | Key behavior |
|---|---|---|
| `ภาพรวม` | identity, tax, status, finance summary | Confidential values mask ตาม role |
| `ธนาคาร & ติดต่อ` | banks, contacts, active addresses | Finance เห็น full account และ bank actions |
| `เอกสารแนบ` | read-only attachment list | แสดงชนิด/วันที่/สถานะตรวจ |
| `การอนุมัติ` | approval chain + audit timeline | ไม่มีข้อความ note เชิง implementation เช่น decision ref |
| `สินค้า/บริการ` | Vendor Price List summary | read-only; `ดู Price List เต็ม →` ส่งต่อ feature อื่น |

### Header actions by state

| State / condition | Visible action |
|---|---|
| `draft` / `pending_kyc`, Compliance | `ตรวจ KYC` |
| KYC passed and ready, Procurement | ส่งอนุมัติ |
| `pending_approval`, current approver | อนุมัติ/ตีกลับ |
| `active`, authorized procurement | Block หรือปิดใช้งาน |
| `blocked`, authorized procurement | Unblock |
| non-terminal, Director/Admin | Blacklist ตาม permission |

ไม่มี section `PO ยังไม่พร้อม` หรือ note `รออนุมัติ (0/1)` ใน approved UI

## §1.5 UI-04 — KYC Modal

**Visible anchors**

- Title `ตรวจ KYC (Compliance)`
- Review guide `ตรวจเอกสารแนบ ... ตรวจเลขประจำตัวผู้เสียภาษี และคัดกรองรายชื่อเฝ้าระวัง`
- Checkbox `ผลการคัดกรองพบข้อมูลตรงกับรายชื่อเฝ้าระวัง`
- Action `ผ่าน KYC` และ `ไม่ผ่าน`

### Normal result

- Pass → `kyc=passed`; vendor ยังคง/กลับอยู่ขั้นพร้อมส่ง approval
- Fail โดยไม่พบ sanctions → ต้องกรอก `รายละเอียดผลการตรวจ`; `kyc=failed`, vendor ยังคง/กลับ `pending_kyc` เพื่อแก้ไขและส่งตรวจใหม่

### Sanctions hit

- แสดง `ไม่สามารถให้ผ่าน KYC ได้`
- disable ปุ่ม `ผ่าน KYC`
- บังคับ `แหล่งข้อมูลที่ตรวจพบ`: OFAC, UN, EU หรือ OTHER
- บังคับ `รายละเอียดผลการตรวจ`
- danger action เปลี่ยนเป็น `ไม่ผ่านและบล็อกคู่ค้า`
- บันทึก source, note, reviewer, timestamp และ audit

## §1.6 UI-05 — Approval Modal

- Title `อนุมัติคู่ค้า — ขั้น {current}/{total}`
- แสดง role ที่ต้องอนุมัติจาก Policy Center response
- อนุมัติได้เมื่อ KYC passed, vendor ready, role ตรง current step และ maker ≠ approver
- approve ขั้นกลางเลื่อนไปขั้นถัดไป; ขั้นสุดท้ายเปลี่ยนเป็น `active`
- `ตีกลับคู่ค้า` ต้องมีเหตุผล, เปลี่ยนกลับ `pending_kyc`, clear chain/decision snapshot และให้ submit ใหม่ resolve chain ใหม่
- ข้อความ subtitle/modal ใน implementation ต้องสอดคล้อง state จริง; ห้ามแสดง `draft` หาก backend transition เป็น `pending_kyc`

## §1.7 UI-06 — Availability and Risk Actions

| Action | Required input | Result |
|---|---|---|
| Block | reason | `active → blocked`; ห้าม transaction ใหม่ |
| Unblock | reason/review evidence | `blocked → active` เมื่อ KYC และ policy ยัง valid |
| `ปิดใช้งานคู่ค้า` | reason | non-terminal → `inactive`; รายการใหม่ถูกระงับ |
| Blacklist | reason; Director/Admin | any allowed non-terminal → `blacklisted`; terminal |

UI ไม่แสดงข้อความเทคนิคเกี่ยวกับ `vendor_id`, match key หรือ soft-delete ให้ end user

## §1.8 UI-07 — Address Removal Confirmation

| Case | Modal title | Expected |
|---|---|---|
| draft/new address ไม่ถูกกำหนด role | `ลบที่อยู่นี้?` | ลบจาก form ทันที |
| address เป็น billing/shipping | `ลบที่อยู่นี้?` หรือ `ปิดใช้ที่อยู่นี้?` | แจ้งผลกระทบ, clear role หลังยืนยัน, บังคับกำหนดตัวแทนก่อน save |
| persisted address ของ active vendor | `ปิดใช้ที่อยู่นี้?` | set inactive, keep audit/history |

ถ้าไม่มี billing/shipping หลัง action ให้แสดง `กรุณากำหนดที่อยู่ใบกำกับ` และ/หรือ `กรุณากำหนดที่อยู่จัดส่งหลัก`

## §1.9 Journey

```text
Procurement เปิด #/vendors
  → เพิ่มคู่ค้า → กรอก 3 ขั้น
  → บันทึก + ส่ง KYC → pending_kyc
Compliance เปิด "ตรวจ KYC"
  ├─ sanctions hit → failed + blocked
  └─ passed → Procurement ส่งอนุมัติ
       → Vendor เรียก Policy Center resolve chain
       → pending_approval
       ├─ reject → pending_kyc + clear chain
       └─ approve ทุกขั้น → active
            → PO เลือก vendor ได้
            → PV ใช้ได้เมื่อ non-OT มี verified bank
```

## §1.10 Accessibility, Responsive and Dismiss Rules

- Keyboard tab order ตาม visual order; action ทุกปุ่มมี accessible name
- Focus trapped ใน modal/drawer; close แล้วคืน focus ไป trigger
- Esc ปิดชั้นบนสุด: modal → drawer → ไม่มี action
- click backdrop ปิดเฉพาะเมื่อไม่ทำให้ข้อมูลสูญหาย; dirty form ต้อง confirm
- status ไม่สื่อด้วยสีอย่างเดียว; ต้องมี label/icon
- รองรับ text reflow และ drawer scroll โดย footer/header ยังเข้าถึงได้
- error ผูกกับ field และประกาศผ่าน live region
- UI text เป็น i18n keys ในระบบจริง แต่ข้อความไทยที่ทดสอบต้องตรง approved HTML
