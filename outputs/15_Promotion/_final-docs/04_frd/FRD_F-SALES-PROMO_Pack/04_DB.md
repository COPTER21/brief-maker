# 04_DB — F-SALES-PROMO Promotion

## §4.1 Storage Principles

- PostgreSQL-style relational model; tenant scoped; no hard delete
- money `decimal(19,4)`; quantity `decimal(19,6)`; timestamps UTC
- approval/audit/usage are append-only except aggregate columns on header
- master references use code/id plus minimal snapshot; no cascade from master owners

## §4.3 Relationships

```text
T_promotion 1:N T_promotion_rule
T_promotion_rule 1:N T_promotion_rule_item
T_promotion 1:N T_promotion_approval_step
T_promotion 1:N T_promotion_usage
T_promotion 1:N T_promotion_audit
```

All FKs include tenant identity or are enforced through tenant-scoped repository methods.

## §4.4 Indexes / Constraints

- unique `(tenant_id, code)`
- partial/functional coupon uniqueness `(tenant_id, upper(coupon_code_normalized))` for non-final promotions
- unique `(tenant_id, event_id)` on usage; same id with different payload hash → conflict alert
- unique `(tenant_id, promotion_rule_id, line_no)`
- unique `(tenant_id, promotion_id, approval_round, step_no)`
- indexes `(tenant_id,status,valid_from,valid_until)`, `(tenant_id,promotion_type,priority)`, GIN `scope_refs`
- CHECK priority 1..999, quantities/value non-negative; deeper variant validation in logic

## §4.5 Field Dictionary Notes

- `scope_refs`: master codes only; empty only when scope_type=`all`
- `approval_round`: increments on every resubmit after rejection
- `occurrences`: number of promotion applications in invoice event per PM/BA; not invoice count blindly
- `version`: increment exactly once per successful header mutation
- snapshots never update from master changes after submit/freeze

## §4.6 Data Classification Enforcement

1. **Public:** none stored; promotion marketing text is Internal until published by downstream channel
2. **Internal:** rule structure and UI labels; tenant-authenticated access
3. **Confidential:** amounts, coupon, customer/employee refs, approval/usage/audit; role and tenant restrictions
4. **Restricted:** none declared
5. **PII overlay:** customer/employee/user IDs are PII references; display minimum name/avatar from authorized master endpoint
6. **Enforcement:** DB RLS/tenant predicate, API permission, export audit, log redaction, encrypted transport/backup

## §4.7 Retention / Deletion

- No hard delete through feature API
- final promotions and usage/audit retained per company transaction/audit policy
- customer/employee deletion requests preserve required transaction reference using pseudonymous display where master policy requires
