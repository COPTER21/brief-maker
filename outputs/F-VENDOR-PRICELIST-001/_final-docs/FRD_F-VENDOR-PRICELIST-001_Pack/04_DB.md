**Constraints / indexes**

- PK `id`; CHECK `status in ('active','inactive')`.
- Unique resolution identity: `(tenant_id, company_id, coalesce(site_id, ZERO_UUID), vendor_id, product_id, buy_uom, currency_code)` using an expression index so two null sites cannot bypass uniqueness.
- Partial unique `(tenant_id, external_id) WHERE external_id IS NOT NULL`.
- `IDX_vpl_header_vendor (tenant_id,company_id,vendor_id,status)`.
- `IDX_vpl_header_product (tenant_id,company_id,product_id,status)`.
- `IDX_vpl_header_updated (tenant_id,updated_at DESC)`.
- `active_version_id` must point to a version under the same header; enforce by deferred FK/trigger after version insert.

**Constraints / indexes**

- FK `(tenant_id,header_id)` → Header; UNIQUE `(header_id,version_no)`.
- CHECK `price_type in ('flat','tier')`, valid status enum, `effective_to IS NULL OR effective_to >= effective_from`, `change_pct_abs >= 0`.
- SoD CHECK/trigger: `approved_by IS NULL OR approved_by <> requested_by`.
- Partial UNIQUE `(header_id) WHERE status='pending_approval'` — one pending version per header.
- Partial UNIQUE `(header_id) WHERE status='active'` for current active version. Historical version becomes `superseded`; date history remains in rows/trace.
- `IDX_vpl_version_effective (tenant_id,header_id,status,effective_from,effective_to)`.
- UPDATE/DELETE forbidden after status enters active/superseded/inactive except controlled status metadata transition; price/tier content is immutable.

- Exclusion/transaction validation prevents overlapping quantity ranges per version.
- Flat price stores exactly one row: `min_qty=0`, `max_qty=null`.
- Tier rows inherit immutability from parent version.

## §4.3 Relationships

```text
F-VENDOR.T_vendor (soft 1) ──< T_vendor_price_header >── (soft 1) Product.T_product
                                     │
                                     ├──< T_vendor_price_version
                                     │           └──< T_vendor_price_tier
```

No cross-module database FK is created to Vendor/Product. Every mutation validates the UUID through owned APIs/services and stores display snapshots.

## §4.4 Transaction Boundaries & Migration

- Create/submit: header + version + tiers + history commit atomically; DOA request creation participates through outbox/saga so failure cannot leave a silent pending row.
- Approval: lock pending version, recheck SoD/state/master eligibility/overlap, activate it, supersede prior active version, update header shortcut, append history and outbox event in one DB transaction.
- Batch/import commit: all preview-token accepted rows are committed atomically for the request. Any server-side revalidation failure rejects the commit with row errors; no partial silent commit.
- Idempotency records use the platform-owned store, not a feature table.
- Initial migration creates tables → constraints/indexes → RLS → WORM grants/triggers → verifies rollback in staging.
- Legacy reference files are not imported automatically. A separate controlled data migration is required if real legacy rows exist.

## §4.7 RLS Baseline

Every owned table enforces `tenant_id = current_setting('app.current_tenant')::uuid`. Company scope is added to service queries from authenticated context. Request body values for tenant/company are ignored or rejected; they are never trusted as authority.

## §4.9 Performance

- List/filter: header status/vendor/product indexes plus latest-version join/denormalized read model.
- Resolve: unique header identity → active version effective index → tier min/max lookup.
- Compare: product/company/date candidate query, then pure calculation; cache only with FX/config/master-version keys.
- Summary for F-VENDOR API-20: indexed aggregate/read model owned by VPL; no copy in Vendor tables.
