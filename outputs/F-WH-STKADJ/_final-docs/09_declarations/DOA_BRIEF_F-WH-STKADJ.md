## 2. Approval Actions

| Action | Trigger | สถานะก่อน | ผลเมื่ออนุมัติครบสาย | ผลเมื่อตีกลับ | ผลเมื่อยกเลิก |
|---|---|---|---|---|---|
| **① ส่งอนุมัติใบปรับยอด** | ผู้ใช้กด "ส่งอนุมัติ" ที่ wizard step 5 | `ร่าง` | `อนุมัติแล้ว` — **ปุ่ม "ผ่านรายการ" เปิด (สต๊อกยังไม่ขยับจนกด post)** | กลับ `ร่าง` แก้ต่อได้ · เลขที่ ADJ เดิมคงอยู่ | `ยกเลิก` (ปลายทาง · ไม่มี movement) — ยกเลิกได้เฉพาะ `ร่าง`/`รออนุมัติ` (FRD LD-06/BR-27) |
| **② ส่งอนุมัติซ้ำหลังถูกตีกลับ** | แก้แล้วกดส่งอนุมัติอีกครั้ง | `ร่าง` | `อนุมัติแล้ว` (สายใหม่ตาม **มูลค่าใหม่** — re-resolve · BR-DOA-05) | กลับ `ร่าง` | `ยกเลิก` |
| **③ ส่งอนุมัติ *ใบกลับรายการ* (reversal)** 🔴 FIX-03 | หัวหน้าคลังกด "กลับรายการ" บนใบ `ผ่านรายการ` → ระบบ **สร้างใบกลับรายการใหม่** (`is_reversal_doc`) → ใบนั้นเข้าสาย DOA | `ร่าง` (ของใบกลับรายการ) | ใบกลับรายการ = `อนุมัติแล้ว` → post ได้ → เมื่อ post: ต้นฉบับ = `กลับรายการแล้ว` + movement ทิศตรงข้าม (BR-17/17.1/18) | กลับ `ร่าง` (ของใบกลับรายการ) | — |

> **ตีกลับ / ยกเลิก / กลับรายการ = บังคับกรอกเหตุผล** (PREBRIEF BR-11 · BR-17 · BR-27 · FRD VR-14 `ERR_ACTION_REASON_REQUIRED`)
> **ไม่มี** DOA ที่ transition `อนุมัติแล้ว → ผ่านรายการ` — การ post เป็นงานปฏิบัติการของหัวหน้าคลัง (สิทธิ์ + guard) ไม่ใช่การอนุมัติซ้ำ
> 🔴 **กลับรายการ (reversal) วิ่งผ่าน DOA** — เป็น approval action เต็มตัว (Action ③) โดยใช้ **matrix เดียวกับ §3** แต่คิดจาก **ค่าสัมบูรณ์ของใบกลับรายการเอง** · **ไม่ auto-post** (FRD LD-05/FIX-03 · BR-17) — *แก้จุดที่ reference เก่าเคยเขียนว่า "ไม่ผ่าน DOA" (ดู §8 DOA-Q3)*

## 3. Matrix ที่จะไปตั้งค่าที่หน้า DOA กลาง

**ฐานวงเงิน = `Σ |มูลค่าที่ปรับต่อบรรทัด|` หน่วย = บาท · `amount_to: null` = ไม่จำกัด · ช่วงต่อเนื่องไม่ทับ ไม่มีรู**
**`doaTiers` = 20,000 / 200,000 / 1,000,000 (จุดตัด 3 จุด → 4 ชั้น) — ใช้ matrix นี้กับทั้ง (ก) ใบปรับยอดปกติ และ (ข) ใบกลับรายการ (reversal)**

| set | amount_from | amount_to | departments | chainMode | steps (ลำดับ slot) |
|---|---|---|---|---|---|
| 1 | 0 | 20,000 | merged | sequential | slot 1: หัวหน้าคลัง |
| 2 | 20,001 | 200,000 | merged | sequential | slot 1: หัวหน้าคลัง → slot 2: ผู้จัดการคลังสินค้า |
| 3 | 200,001 | 1,000,000 | merged | sequential | slot 1: หัวหน้าคลัง → slot 2: ผู้จัดการคลังสินค้า → slot 3: ผู้จัดการฝ่ายบัญชี |
| 4 | 1,000,001 | *null (ไม่จำกัด)* | merged | sequential | slot 1: หัวหน้าคลัง → slot 2: ผู้จัดการคลังสินค้า → slot 3: ผู้จัดการฝ่ายบัญชี → slot 4: ผู้อำนวยการสายงาน |

`[DEFAULT — รอยืนยัน]` ทั้ง 4 set — จุดตัดวงเงินและจำนวนชั้นยังไม่ผ่านการเคาะจากเจ้าของกระบวนการ (owner: **Strike** · pin `OQ-STK-01` / `OQ-ADJ-01` · FRD §7.5)

> **จุดตัดตั้งต่ำกว่า RTV และ PO โดยเจตนา** (20,000/200,000/1,000,000 เทียบ RTV 50,000/500,000 และ PO 100,000/1,000,000) — การปรับยอดไม่มีคู่ค้าภายนอกมาถ่วงดุล ความเสี่ยงทุจริตสูงสุดในสามตัว จึงคุมเข้มกว่า `[DEFAULT — รอยืนยัน]`
> **ชั้นบัญชีเข้ามาที่ set 3** เพราะมูลค่าระดับนี้กระทบงบการเงินอย่างมีนัยสำคัญ `[AI-DRAFT]`
> 🔴 **ใบกลับรายการ (reversal) ใช้ matrix เดียวกันนี้** — resolve สายจาก `Σ|มูลค่าใบกลับรายการ|` ตอนกดส่งอนุมัติใบกลับรายการ (โดยปกติเท่าค่าสัมบูรณ์ของต้นฉบับ) · ไม่มี matrix แยกสำหรับ reversal (FIX-03)

**Gate check (skill Quality Gate G1–G7)**
- **G1** role master (`references/doa-contract.md`) **ไม่มีในเลนนี้** → slot เขียนเป็น "นิยามตำแหน่งที่ทะเบียน DOA ใช้ดึงคน" แทน role id · ผู้ตั้งค่าต้อง map เป็น `role-*` จริงตอนกรอกที่หน้า DOA กลาง — **ข้อจำกัดของรอบนี้ ไม่ใช่การแต่ง role เอง** (เหมือน F-PUR-PO / F-PUR-RTV) → ยกเป็น `DOA-Q6`
- **G2** ทุก set มี `amount_from` + `amount_to` ครบ ✅
- **G3** ช่วงต่อเนื่อง 0→20,000 · 20,001→200,000 · 200,001→1,000,000 · 1,000,001→null — ไม่ทับ ไม่มีรู ✅
- **G4** set สุดท้าย `amount_to: null` ✅
- **G5** `approval_scope = document_sign` (1 ใน 3 ค่าที่มีจริง) ✅
- **G6** ค่าที่ยังไม่ยืนยันติด `[DEFAULT — รอยืนยัน]` ครบ ✅
- **G7** ไม่มีสายอนุมัติ hardcode ใน HTML/เอกสาร feature — HTML ใช้ mock ที่ resolve จากรูป DOA entry + marker `FWD-WIRE: DOA engine` ✅
