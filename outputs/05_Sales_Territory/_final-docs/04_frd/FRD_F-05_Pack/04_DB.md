## §4.4 Migration Strategy

1. Create owned Route and audit tables/constraints/indexes.
2. Reuse or provision platform idempotency facility after OQ-FRD-02/architect check.
3. Apply tenant policy only after OQ-FRD-01 resolves canonical context.

5. Rollback before go-live may drop newly empty owned tables; after live data exists, rollback disables feature writes and preserves data/audit—no destructive drop.

## §4.6 Data Classification and Sensitive Data

### §4.6.1 Four levels

- Public: explicitly publishable; none in this schema.
- Internal: authenticated organizational use; safe default.
- Confidential: role-limited identifiers/snapshots containing person references.
- Restricted: person/record ACL; none currently identified.

### §4.6.2 Default rule

Unspecified = Internal. Public must be explicit. Classification downgrade requires governed, audited change outside this feature.

### §4.6.3 Enforcement mapping

| Level | DB | API | UI | Audit |
|---|---|---|---|---|
| Internal | tenant isolation `[AI-DEFAULT]` | authenticated | normal | mutation |
| Confidential | isolation + column access | role/scope check | hide/mask if unauthorized | view where policy requires + mutation |
| Restricted | row ACL registry | ACL | hidden | view/export/mutation |

### §4.6.4 PII overlay

Actor IDs and salesperson soft ref are PII-linked. Do not log display names/raw personal details in transport/application logs. JSON audit snapshots inherit the highest contained classification and PII flag.

### §4.6.5 Security domain mapping

- Authentication/authorization: every read/write.
- PII: salesperson/actor references.
- Audit: all mutations and sensitive denials.
- Tenant isolation: only after platform contract confirmation.
- Asset integrity: geo dataset checksum/version.

### §4.6.6 Policy linkage

Register classification metadata with the platform Data Classification facility when available. No Restricted Resources wire is required unless a field is later promoted to Restricted; that would require FRD revision.
