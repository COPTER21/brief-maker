## 1. DOA สายอนุมัติ (DOA-ACC-DN) — role + จุดตัดวงเงิน

**🟢 ข้อเสนอ:**
- **โครงสาย 3 ขั้น** (mirror Credit Note): ผจก.จัดซื้อ/procurement → ผจก.บัญชี → CFO — ขั้นแรกเป็นเจ้าของความสัมพันธ์กับผู้ขาย, บัญชีคุมภาษี/ผังบัญชี, CFO คุมวงเงินใหญ่
- **จุดตัดวงเงิน: ใช้ 50,000 / 300,000 เท่ากับ CN** เพื่อให้นโยบาย DOA ทั้งบริษัทสอดคล้องกัน (ฐาน = ยอดลดหนี้สุทธิ `grand` หลังหักส่วนลดท้ายบิล) — เว้นแต่ Finance มีนโยบายฝั่ง AP ต่างหาก

**⚖️ ต้องเคาะ (OQ-AP-06 + OQ-DN-02):**
- **role-id จริงยังยืนยันไม่ได้** — prototype ใช้ placeholder `role-mgr-pur` / `role-mgr-acc` / `role-cfo` · ต้องแมปกับ **role master ใน Policy Center** ว่าใช้ตัวไหน (ROLE_PURCHASE_MGR / ROLE_PROCUREMENT_MANAGER / ROLE_PURCHASING_HEAD / อื่น ๆ) — **AI เดา id ไม่ได้ เพราะมีคนเอาไปตั้งสายอนุมัติจริง**
- ยืนยันตัวเลข 50k/300k ว่าตรงนโยบาย AP หรือใช้เลขอื่น
- **ความมั่นใจ:** โครงสาย = สูง · role-id/เลขวงเงิน = ต้องยืนยัน (ห้ามใช้ค่า assumed ไป config จริง)

## 2. กลับภาษีซื้อ ภ.พ.30 — ยึด vendor_cn_date หรือ dn_date

**🟢 ข้อเสนอ: ยึด `vendor_cn_date` (วันที่ได้รับใบลดหนี้จากผู้ขาย) — สมมติฐาน FIX-02 ถูกต้องตามหลักภาษี**

เหตุผล (มาตรา 82/10 ประมวลรัษฎากร ฝั่งผู้ซื้อ):
- เอกสารภาษีที่ทำให้ผู้ซื้อต้อง**ลดภาษีซื้อ** คือ **ใบลดหนี้ที่ผู้ขายออกให้** ไม่ใช่ DN ที่เราออกภายในเอง
- ผู้ซื้อต้องนำภาษีซื้อที่ลดไปหักในเดือนภาษีที่ **ได้รับใบลดหนี้ของผู้ขาย** (= `vendor_cn_date`) — ไม่ใช่วันที่เราออก DN
- ถ้ายึด `dn_date` จะลดภาษีซื้อ "ก่อน" มีเอกสารภาษีของผู้ขายในมือ → เสี่ยงยื่น ภ.พ.30 ผิดงวด

ผลเชิงปฏิบัติ (prototype ทำถูกแล้ว): ถ้ายังไม่กรอก vendorCn → ภ.พ.30 แสดง **"รอเอกสาร"** ยังไม่ลดภาษีซื้อ

**⚖️ ต้องเคาะ (OQ-DN-05):** ให้ **Finance/ฝ่ายภาษี** ยืนยันการตีความ ม.82/10 อย่างเป็นทางการ (AI ให้เป็นการตีความมาตรฐาน ไม่ใช่คำวินิจฉัยทางกฎหมาย)
**ความมั่นใจ:** สูง (ตรงหลักปฏิบัติภาษีมูลค่าเพิ่มทั่วไป) — แต่ต้องมีลายเซ็น Finance

## 3. vendorCn กรอกซ้ำ / งวดภาษีปิดแล้ว

**🟢 ข้อเสนอ (แบ่ง 2 เฟส):**
- **Phase 1 (prototype ปัจจุบัน): แก้ทับได้ + บันทึก audit ทุกครั้ง (append-only)** — เพราะ**ระบบยังไม่มีทะเบียนงวดภาษี** จึงบังคับ "งวดปิด" ไม่ได้จริง · ทุกการแก้มี log ว่าใคร/เมื่อไหร่/เดือนภาษีเปลี่ยนเป็นอะไร
- **ก่อน go-live จริง: ต้องเช็คงวดภาษีปิด** — ถ้า vendor_cn_date เดิมถูกยื่น ภ.พ.30 ไปแล้ว แล้วแก้ให้ย้ายงวด ต้องบล็อก หรือบังคับทำ "ยื่นเพิ่มเติม/ปรับปรุง" แทนการแก้เงียบ ๆ

**⚖️ ต้องเคาะ (Finance + Dev):**
- **มี gap จริง: ยังไม่มีทะเบียน/lock งวดภาษีในระบบ** → ถ้าต้องการ control ระดับ "กันแก้ข้ามงวดปิด" ต้องสร้าง dependency นี้ก่อน (หรือผูกกับ module รายงาน VAT ที่คุมการปิดงวด)
- Finance เลือกระดับ control: (ก) แก้ทับ+audit อย่างเดียว / (ข) แก้ได้จนกว่างวดจะปิด / (ค) ปิดงวดแล้วต้องยื่นเพิ่มเติม
**ความมั่นใจ:** กลาง — ขึ้นกับว่า Finance รับความเสี่ยงระดับไหน + มี resource สร้างทะเบียนงวดไหม

## 4. "ออกเอกสารแก้ไข" (revise-doc) / "ส่งซ้ำ" (resend) — ทำรอบนี้ไหม

**🟢 ข้อเสนอ: ไม่ทำรอบนี้ — คงไว้เป็น forward ภายใต้ OQ-DN-04 (prototype ถูกแล้ว, FRD ที่ค้างเป็นของเกินให้ถือตาม prototype)**

เหตุผล:
- "ยกเลิก/แก้ใบหลังอนุมัติ" อยู่ใน **"สิ่งที่ไม่รองรับ" ของ PREBRIEF** ตั้งแต่ต้น (OQ-DN-04) — ยังไม่เคยเปิด scope
- prototype ที่ **ผ่าน manual test + BA approved** ไม่มีปุ่มนี้ · ที่ FRD มี API เพราะ subagent mirror มาจาก CN เกิน → ผมได้ **mark FORWARD** ทุก layer แล้ว (drift D-3/D-4) ว่าอย่า implement
- ใบภาษีที่ออกเลขแล้วยกเลิกไม่ได้ (ถูกต้องตามหลัก no-gap) · ถ้าต้องแก้จริง = เปิดเป็น **change request เฟสถัดไป** จะได้ไม่ต้องรื้อ gate รอบนี้
- resend ก็เช่นกัน — ไม่อยู่ใน prototype, ไม่จำเป็นต่อ flow หลัก

**⚖️ ต้องเคาะ (BA):** ยืนยันว่าเลื่อน OQ-DN-04 (revise-doc + resend) ไปเฟสถัดไป · ถ้า Finance ยืนยันว่า**ต้องมี**ทางแก้เอกสาร ให้เปิดเป็นรอบใหม่ (มีผลกับ CN ด้วยเพราะ CN มี display-only อยู่แล้ว — ควรตัดสินให้สองฝั่งตรงกัน)
**ความมั่นใจ:** สูง (ยึด scope เดิม + ไม่รื้อ gate)

## 5. เหตุผลลดหนี้ 3 แบบ + ถ้อยคำกฎหมายบน PDF

**🟢 ข้อเสนอ:**
- **หมวดเหตุผล 3 แบบ ใช้ตาม prototype ได้เลย** (ครอบเคสฝั่งซื้อมาตรฐาน):
  1. `RTV` — คืนสินค้า (อ้างใบคืนสินค้า RTV) · mode=จำนวน · ต้องมีใบ RTV
  2. `OVERPRICE` — ผู้ขายคิดราคาเกิน · mode=ราคา
  3. `SHORT` — ของขาด/ไม่ครบตามใบกำกับ · mode=จำนวน
- ปัจจุบัน PDF พิมพ์ **ชื่อเหตุผล + คำอธิบายอิสระ (reasonText ≥10 ตัวอักษร)** — **ยังไม่มีถ้อยคำกฎหมายตายตัวต่อเหตุ**

**⚖️ ต้องเคาะ (Finance/ฝ่ายภาษี):**
- ตัว "หมวด" 3 แบบ = โอเคใช้ได้ (โครงสร้าง)
- แต่ **ถ้อยคำที่พิมพ์ลงเอกสารภาษีจริง** (เช่น ประโยคอ้างเหตุตาม ม.86/10) เป็นสิ่งที่ Finance ต้องเป็นคนกำหนด/ตรวจ เพราะมันคือข้อความบนเอกสารภาษี — ถ้าต้องการ "legal clause มาตรฐานต่อเหตุ" (นอกเหนือ reasonText ที่ผู้ใช้พิมพ์เอง) ให้ Finance ส่งถ้อยคำมา แล้ว dev เติมเป็น template
**ความมั่นใจ:** หมวดเหตุ = สูง · ถ้อยคำกฎหมาย = เป็นสิทธิ์ Finance
